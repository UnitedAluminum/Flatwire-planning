tactical DDD in the domain layer** (`D-29`) — with thin controllers, a DI-swappable stub/real

## Cross-database reads

⚠ **Do not conflate these two.** They are read at the same moment, by the same wizard step, and they are not the same record.

| | **Rod schedule** | **Pass schedule** |
|---|---|---|
| Source | **`united_db..planning_routings`** — genuinely cross-database | **`FlatWireDB..PassSchedule`** — a **local** read since `D-31` |
| What it yields | The rod→order allocation | The **six value groups** the PLC push needs (`[PLC §7.2]`): component active/bypass state · die sizes · roll gaps · edge type · speed · gauge and width targets |
| Repository | `RodRepository` | Read model — **no repository** (`[SVC §3.2a]`); Dapper query + `PassScheduleSnapshot` |
| Status | Table known; **columns unmapped — `OI-33`** | ✅ **Resolved.** `[API §4.2]`'s open assumption chose the **local-query** option: the owning track writes into `FlatWireDB`. `PassScheduleId` now carries a **real FK** |

⚠ **Only one of these two is still a cross-database read.** The table is kept because the two records
are read at the same moment by the same wizard step and are still **not the same thing** — but the
pass-schedule column is now a local query, so *"the pass schedule read is cross-database"* is stale
wherever it survives. **`united_db..planning_routings` is unaffected** and remains the real cross-DB
dependency, still blocked on `OI-33`'s unmapped columns.

**Rod schedule — `RodRepository` reads two shared tables and writes one.** `FR-038` (a cold line's first scan **reveals** the order), `FR-044` (staging **refuses** a rod with no allocation) and `FR-077` (check-in **writes** `actual_start_date` back to `planning_routings` and `routings`). `[API §4.5]`: *"the `order` block is a **cross-database read** … on the same unenforced-link basis as rod alphas."* Follow `[DBD §6.6]`'s established convention — `united_db..alloys` is surfaced as a view named `Alloys` in six consuming databases, giving *"one place to absorb mismatches rather than repeating them at every call site."* The read/write grants are a deployment item.

**Pass schedule.** ⚠ **`scheduleId` is a real, enforced foreign key as of `D-31`** — `FK_FlatWireRun_PassSchedule`, `FK_RodCheckin_PassSchedule`, `FK_SpoolCheckin_PassSchedule` and `FK_CoilOutput_PassSchedule`, all verified enforced and trusted on a live deploy. *It was previously "an opaque external identifier, not an FK — the same class as `PlanId` and `SkidId`", and that description is superseded.* **`PlanId`, `CoilOrderPlanId` and `SkidId` are unaffected** and remain external references with no local parents.

`POST /checkin/rod` still carries only the id. **Unavailable means check-in fails** *"before any PLC write, not after — a partial configuration is worse than none"* — now a `404`/FK failure rather than an unreachable external service. **The snapshot rule survives unchanged**: MVP-1 persists its own copy of what it pushed — schedule id, version and effective configuration — because `[PLC §11.2]` and `OQ-64` need a certificate to stay reproducible **after the owning system later edits the schedule**, which a local FK does nothing to prevent.

⚠ **MVP-1 reads these tables and never writes them.** No create, edit, approve or list; `PassScheduleController` stays scaffolded for MVP-2 handlers. **Something outside MVP-1 must populate them in production** — the seed covers development and the trial only. Tracked as `OI-110`.
