# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repository Is

This is the **planning, analysis, and design repository for the Flat Wire Mill module** of the UAL manufacturing execution system. It contains **no shippable application code** — it holds requirements (SRS), analysis notes, a database schema design with executable DDL, API contracts, UI mockups, and a phase-by-phase implementation roadmap that drive implementation in the sibling code repos.

The actual implementation lands in **`../ual-angular`** (Angular frontend, new library `flat-wire-shopfloor`) and **`../ual-api`** (new `FlatWire` microservice). `MVP-1/ProjectPlan/Flat Wire.code-workspace` opens this folder alongside both. Ecosystem-wide stack conventions live in the parent **`../CLAUDE.md`** (`c:\UAL\CLAUDE.md`) — read it for build/test commands and general Angular/.NET/SQL patterns; this file covers only what is Flat Wire-specific.

When asked to "implement" a feature, the code goes in `ual-angular` / `ual-api`, using this repo's artifacts as the spec.

## Domain in One Screen

United Aluminum is adding flat wire manufacturing: three new **Flattening Lines** that convert aluminum rod into coreless oscillated flat wire coils.

- **FL1** (standalone): rod → wire drawing (DB1/DB2) → 12" mill FM1 → intermediate spool. Gauge trace is **real-time**. FL1 has **no edger**.
- **FL2** (standalone): pre-flattened spool → finishing mill FM2 (**three stands: `S1` 8" → `S2` 6" → `S3` 6"**; **edgers at S2 and S3 only**; **S3 is final and non-bypassable**) → coreless coil. Gauge trace is **historical/profile** (FL2 broadcasts `null` live gauge/width).
- **FL3** (hybrid): FL1 feeding FL2 continuously, no intermediate anneal. Real-time. Drives the same FM2.

**FM2 has three stands, and the four-stand model is retired (4 Aug 2026).** Until then every artifact modelled a separate `8" Roller` component *upstream of* three 6" stands — four components — because the 21 May client note was recorded in `Business/BusinessRules.md` §3 as *"FM2 has three 6" stands (S1, S2, S3)"* and read that way. **The 8" roller *is* S1.** Component identifiers are now **position-only** — `FM2_S1` / `FM2_S2` / `FM2_S3` — and roll diameter is **data**, in `Stand.RollDiameterIn` (FM1 12.000; FM2 8.000 / 6.000 / 6.000); diameter inside an identifier is exactly what let four artifacts hold the same wrong belief for ten weeks. Old → new: `FM2_8in`→`FM2_S1`, `FM2_6inS1`→`FM2_S2`, `FM2_6inS2`→`FM2_S3`, **`FM2_6inS3` withdrawn as never-existent** (it never had a tag path or a seed row). `Stand.Id` 1–4 keep their meaning; Id 5 is gone. PLC stations become `FL2.FM2.S1/S2/S3` pending sign-off as **`PLC-Q04`** / gap **G32**. **Anything showing four FM2 stands, a separate `8" Roller`, or a 6" stand named S1 is stale.** This closed two long-running open items — **`OI-04`** (mandatory stand: `FM2_6inS2` vs `6" S3` — one stand, two names) and **`OI-36`** (the final stand's missing tag path — the map was complete; the phantom stand was not in it). Decision **D-26**, master spec §10.2.

Recurring concepts:

- **Pass Schedule** — the master configuration record (components active/bypassed, die sizes, edge type, roll clearances, gauge/width targets, route mode). **Highest-priority dependency**: operator check-in acknowledges it and the system pushes PLC tags from it on acknowledgement. Phase 2 gates every check-in phase. Schedules are hand-authored *or* drafted by the **Generate-from-Specs** algorithm (FW-013, `PassScheduleGeneratorService`); either way the draft requires Operations approval and PLC tags are never pushed at generate/apply time.
- **The PLC tag surface now has exactly one home.** It previously existed as **six partial, mutually contradictory copies** — `02-SRS.md` §9, `03-HLD-and-ERDiagram.md` §9, `04-APIContract.md` §6, `FlatWire_MasterSpecification.md` §6.8, `HMIAndSCADALayout.md` §6.2 and `RocCheckin.md` §3.6 — none complete and no two agreeing on the tag map (12 rows vs 13 vs 11). Since **4 Aug 2026** the surface is **`MVP-1/ProjectPlan/Architecture/PLCTagSpecification.md`** (client-facing, cited as `[PLC]`, carries its own **`PLC-Q##`** register and a sign-off sheet) plus **`MVP-1/ProjectPlan/Architecture/PLCCommunication.md`** (internal). The five surviving sources are reduced to pointers; the sixth was deleted with the DB13/DB14 descope. **Anti-drift rule: the client doc owns every tag path string and the internal doc contains none** — if you are about to write a tag path anywhere else, you are creating the seventh copy.

  **`[PLC]` was reissued as v1.0 on 4 Aug 2026 — a first issue, carrying no history.** Three things follow, and each will look like a defect if you do not know it was deliberate. **(1) There is no `[CONFIRMED]` tag**: the reading convention is `[PROPOSED]` and `[CLIENT INPUT REQUIRED]` only, because no client artifact contains a single tag path and nothing has been read off a controller — a path becomes confirmed when commissioning test `C1`/`C11` says the controller accepted it. Do not reintroduce the tag. **(2) There is no decision log** — `§12` and `D1`–`D17` are deleted; the interlock rule lives as prose in `[PLC §8.1]` and the *decisions* live in `Analysis/FlatWireOpenQuestions.md` (`Q84`, `Q85`). Do not cite a `D##` into `[PLC]`. **(3) Sections and `PLC-Q##` ids were both renumbered** — `PLC-Q` is now contiguous `01`–`17` in **priority order**, and `§7`→`§2.2`, `§8`→`§6`, `§4`→`§7`, `§5`→`§8`, `§6`→`§9` among others. **Both mapping tables are in [`CHANGELOG.md`](CHANGELOG.md) under `Analysis/FlatWireOpenQuestions.md`**, in the *"reissued as v1.0"* entry (they were in that register's own change log until the 12 Aug 2026 consolidation); use them rather than guessing, and note that change-log entries written before that date cite the old numbering by design.
- **The generation algorithm exists in four copies — know which one you are reading.** In authority order: **(1)** `MVP-2/RequirementDocuments/PassScheduleGenerationSpec.md` (**v1.5, 6 Aug 2026**) is the **engineering basis** — compounding reduction, lateral spread, the width chain, inter-stand pass allocation, edge geometry, mill spring, drawing-vs-rolling separation. **It now wins on *physics and arithmetic both*.** **(2)** `FlatWire_MasterSpecification.md` FR-380–FR-391 + its `POST /passschedule/generate` section wins on *contract shape only*. **(3)** the April elaboration's worked example was **known broken** (REVIEW Tier 1 #1 — it contradicted its own formula) and was **not migrated** when that document was absorbed into `04-APIContract.md` on 13 Aug 2026, because generation is out of MVP-1 scope. **(4)** `PassScheduleManagement.md` §"Pass Schedule Generation Algorithm" (Apr 25) was the original narrative, with wrong Step 3 pass-count branches — **deleted 1 Aug 2026** (recoverable at `2a0426b`), so there are now three copies, not four. Copy 3 is retained for history; do not implement from it.

  **The physics/arithmetic split held until 6 Aug 2026 and no longer does.** Two gap audits took copy 1 to v1.4 and v1.5, and in doing so changed the arithmetic — at which point **`FR-381`, `FR-384`, `FR-385`, `FR-386` and `FR-387` became wrong**, on five counts: the pre-flatten diameter is a *lower bound*, not the answer, and needs the round-edge correction; the final die may not be snapped **down** from that bound (`R36`/`V39`); the roll gap sits **below** gauge by a **load-dependent** mill-spring term, not above it by a fixed alloy "springback" multiplier (a machine stiffness being carried as a material property); the finishing-mill test is **not** the route decision; and the non-hybrid default bypasses `FM2_S1`/`FM2_S2`, leaving the **skim stand as the only active stand**. Arbitration is **`FlatWire_MasterSpecification.md` §10.5**, with a callout above the FR table and a `REVIEW.md` Tier 1 entry. **Contract shape is untouched** — the envelope, `FR-389`, `FR-390` and `FR-391` all stand. **Build `FW-013` to copy 1.** Note that copy 1 deliberately carries **no `FR-`, `FW-` or endpoint references** (it is a client deliverable), which is why the reconciliation lives in the master spec rather than in it.
- **FlatWireRun** — the central run header (one per check-in); nearly every event/quality table hangs off it. A `FlatWireRunDetail` header/detail split is part of the design.
- **Weld traceability** — **induction** welds (laser dropped) join rod-to-rod for continuous feed; the system must trace which source rods produced which output-coil footage (required for welding-wire customer certs). `CoilTraceability` is that genealogy chain.
- **SPC checkpoints** — incoming rod, post-die-change, FM1 output, FM2 final-stand (S3) output; some manual, some automatic (AGC).
- **Alpha formats:** Rod `R#####` · Spool `SP-#####` · Run `RUN-####` · Pass schedule `PS-{alloy}-{line}-{seq}` · Output coil `FW-#####-C##` (mid-run child `…-A`) · Die `D-{size×1000}-{seq}`. Full list in `Business/BusinessRules.md` §3.
- **Terminology rule:** always "flat wire," never "strip." Traveler is **fully digital** (no printing; coil/skid labels are still printed).

**Timeline (authoritative):** development window **17 Aug → 30 Sep 2026** with a hard **Phase-1 gate of 14 Aug 2026**; UAT late Sep, production Q4 2026. The "Jul 1 trial / Aug 1 production, 5-sprint" targets still present in the April-dated docs are **superseded**. Stay within the existing UAL stack — no new frameworks (`MVP-1/ProjectPlan/TechStackRecommendation.md`).

## Working With the Artifacts

### Database schema (`MVP-1/ProjectPlan/Database/Schema/`)

The design exists in three forms that must stay in sync: **markdown design docs** (`FlatWireSchema_*.md`), **executable DDL** (`SQL/FlatWire_DDL_*.sql`), and the **phase-1C spec** (`ProjectPlan/Development/Phases/phase-01c-database-foundation.md`). Read `SQL/FlatWire_ERDiagram_Documentation.md` first — it describes the **as-built** schema.

- Target database is a **new standalone `FlatWireDB`** (not `united_db`), created by `FlatWire_DDL_00_Database.sql`. Older DDL headers said `USE [united_db]`; anything still saying that is stale.
- DDL files are **numbered by execution order**: `00` database → `01` Lookup → `02` Schedule → `03` Materials → `04` Runs → `05` Quality/Output → `06` **all FKs** → `07` Indexes → `08` Programmability. `99` is teardown. Preserve this ordering when adding tables, and put new FKs in `06`.
- Groups: Lookup (`Stand`, `Drawer`, `Edger`, `SpoolConfiguration`, `AlloyProperty`, `PayoffPosition`) → Schedule (`PassSchedule`, `PassScheduleComponent`, `PassScheduleChangeLog`) → Materials (`Rod`, `FlatWireRun`, `Spool`) → Runs (`FlatWireRunDetail`, `RodCheckin`, **`RodStaging`**, `SpoolCheckin`, `RunPauseEvent`, `WeldEvent`, `RollOverride`, `DieChangeEvent`, `RunReading`) → Quality/Output (`SpcCheckpoint`, `SpcMeasurement`, `WipRejection`, `CoilOutput`, `CoilTraceability`, `RodCheckout`).
- **`Rod` is retained — resolved, no longer a divergence.** The now-dissolved `00-foundations.md` decision 3 and older `phase-01c` text said the `Rod` table was *dropped* (rod living only in the shared `coils`). **Master-spec `D-04` (29 Jul 2026, "Hybrid foundation") supersedes that**, and `[ARC §13.1]` records the reversal: `Rod` is a `FlatWireDB`-local master mirroring `coils`, with **enforced** rod-alpha FKs. `coils` remains the source of truth for the rod *lifecycle*; the mirror is what lets the FKs be enforced. **The full design is 28 tables; the MVP-1 build is 25** — the three `PassSchedule*` tables are owned outside MVP-1. Verified by a clean teardown, deploy and idempotent re-run on **13 Aug 2026: 25 tables · 33 FKs · 41 index statements · 1 procedure · 1 trigger**, defined once in `[DBD §6.2]`. **Any "21–22 tables", "24 tables", "27 tables" or "`Rod` is dropped" text you find is stale** (gap `G12`, closed).
- **`RodStaging` (pre-check-in / payoff staging)** is the newest table and carries two invariants worth knowing before touching it: `Blocked` is a **derived** bay state (`Status='Staged'` + any inspection column `='Fail'`), never a fourth `Status` value; and `IsWelded` is a **flag on a `Staged` row**, not a status — so any code branching on "staged" also matches welded and blocked rods unless it says otherwise. See `MVP-1/ProjectPlan/Business/Screens/RodPreCheckin.md` and gap **G21** (the `(LineId, PayoffPosition)` uniqueness scope is unresolved across FL1/FL3).
- `FlatWireRun` is the hub; `RunReading` is the time-series AGC gauge/width store added to close gap **G3**.

**Deploying the schema** (SQLCMD mode required — `:r` includes):

```powershell
# Full build + seed, in order. Run from the SQL folder (paths are relative).
cd "c:\UAL\Flatwire-planning\MVP-1\ProjectPlan\Database\Schema\SQL"
sqlcmd -S "(localdb)\MSSQLLocalDB" -E -C -i FlatWire_DDL_RunAll.sql

# A single script
sqlcmd -S "<server>" -E -C -i FlatWire_DDL_04_Runs.sql

# Drop everything
sqlcmd -S "<server>" -E -C -i FlatWire_DDL_99_Teardown.sql
```

Every script guards its objects, so `RunAll` is idempotent and safe to re-run against an existing `FlatWireDB`. In SSMS use **Query → SQLCMD Mode** before executing `RunAll`.
