## 2. The four details

### 2.1 The hours are the reverse script; the approval is the blocker

The card is explicit — *"the approval itself carries no hours"* — and the two halves fail
differently:

- **The code half** (8 h) can be built today. Nothing blocks authoring and testing a reverse
  script; it needs no decision, only the insert it mirrors.
- **The approval half** blocks `FW-220`, `FW-221`, `FW-223` and `FW-003`, and no amount of
  engineering moves it.

⚠ **Build the reverse script first, and do not wait on the sign-off to start.** It is also the
strongest argument *for* the sign-off: a reviewer asked to approve a one-way write into shared
tables is being asked for much more than one who can be shown the undo.

### 2.2 The reverse script must undo in the opposite order, and delete only what it wrote

The insert's order is fixed because each part consumes keys the previous one minted. **The
reverse runs `4e` → `4c`/`4d` → `4a`**: bindings, then stations, then machines. Deleting a
machine first orphans the binding rows or trips the FK, depending on how `CommonDB`
constrains them.

⛔ **It must delete by the values it inserted, never by a range or a wildcard.** These are
shared tables — `machines` and `WIPStations` carry every other module's rows. A `DELETE`
keyed on anything looser than the exact three machine names and four station codes is a
production incident, and there is no reverse for the reverse.

⚠ **`MachineStationsConfiguration` binds on `WIPStationId` IDENTITY values minted in `4c`.**
The reverse cannot assume those ids; it must resolve them the same way `4b` resolves
`MachineIdx` — by the natural key, at run time.

**Number it `15_`.** The chain uses tens, so `15_` sits immediately after the script it
reverses and before `20_`, and the runner keeps skipping both.

### 2.3 `FL3PO` must stay absent

FL1 and FL3 **share one physical payoff**. `STATION_BY_LINE = {FL1:"FL1PO", FL3:"FL1PO"}`,
client-confirmed under `Q71`, and `RodStaging.Station` carries that value with
`UX_RodStaging_Bay` keyed on it.

⛔ **Seeding an `FL3PO` station would let two rods occupy one physical bay with every
constraint satisfied** — precisely the defect `G21` recorded, and it was **fixed on 15 Aug
2026.** The absence looks like an omission in a four-station set derived from three lines,
which is why the script already carries a comment block against it.

> ⚠ **`G21` is fixed, and four `[TB §7]` cards plus `CLAUDE.md` still describe it as blocking
> the Phase-4 schema freeze.** Do not take those as evidence the station is missing.

### 2.4 One set of values, two documents

AC 5 requires `FW-003`'s `machines` rows and this script to agree, *"since an OPC
registration (`FW-238`) keys on them"*. In practice `4a` **is** `FW-003`'s rows — the story
attribution in the script header says `FW-003` — so the risk is not two scripts diverging
but **the decided values being recorded in one place and re-typed in another**.

**`[DEP §4.2]` step 2 is the record** (AC 1). `machine_type`, the station set and
`StationType` are decided there; the script and `Scripts/README.md`'s manifest cite it.
⚠ **`FW-238` must read them from the same record**, not from the script, or `G60`'s
registration and this insert drift apart the first time either is corrected.

## 3. Build order

1. **Enumerate what `10_` writes**, exactly: three `machines` rows, four `WIPStations`
   (FL1, FL2, FL3, FWPACK), and one `MachineStationsConfiguration` row per station.
   ⚠ **Four stations from three lines** — `FWPACK` is the shared packing station and there is
   no `FL3PO` (§2.3).
2. **Author `15_CommonDB_Delete_WIPStations_FlatWire.sql`** (§2.2): reverse order, natural-key
   resolution, exact-value deletes, idempotent (`IF EXISTS` guards), and a row count reported
   per part.
3. **Test it on a DEV instance by running `10_` then `15_`** and asserting both shared tables
   return to their prior row counts. ⚠ **This is the only test that matters**, and it is the
   only chance to run it before the values are approved.
4. **Add `15_` to `Scripts/README.md`'s manifest** with its `Reversible?` column filled, and
   **flip row 10's `⚠ NO — no reverse script exists`** to name `15_`.
5. ⚠ **Do not add either script to `FlatWire_Scripts_RunAll.sql`.** The runner skips `10_` by
   design; a reverse in the chain is worse than none.
6. **Record the decided values in `[DEP §4.2]` step 2** (AC 1) — that section is the record,
   not the script header.
7. **Run `10_` by hand, per environment, after sign-off** (AC 4), and record the sign-off state
   in both `[DEP §4.2]` and the manifest (AC 6).

## 4. Decisions this plan makes

> The `P-##` series belongs to [`Backend/tasks/`](../../Backend/tasks/)
> and is continuous across the repository; `P-01`–`P-150` precede this story.

### `P-151` — the reverse script is `15_`, and it stays out of the runner

Tens numbering leaves `15_` free, immediately after what it reverses. **It is never chained**
— `FlatWire_Scripts_RunAll.sql` skips `10_` because that script is irreversible and run under
approval; putting its *undo* in an automated chain would make the pair reachable without the
gate that exists to guard them.

**Fallback:** number it `11_` if a future script claims `15_`. The number is not load-bearing;
**staying out of the runner is.**

### `P-152` — build the reverse before the approval, not after

§2.1. The two halves have different blockers, and the reverse script is an input to the
approval rather than a consequence of it.

### `P-153` — `[DEP §4.2]` step 2 is the single record of the three decided values

§2.4. The script, `Scripts/README.md` and `FW-238` all **cite** it. ⚠ Re-stating the values
in `FW-238` is how `G60`'s registration and this insert drift — the same failure mode as the
six PLC tag copies.

## 5. Verification

**No automated tests** — `[TS §1.2]`. Verified on a DEV instance and by manifest review.

| Check | Expected |
|---|---|
| **Round trip** | Run `10_` then `15_`; `machines`, `WIPStations` and `MachineStationsConfiguration` return to their **exact prior row counts** |
| Reverse order | `15_` deletes bindings → stations → machines. Running it in insert order fails or orphans — demonstrate that it does not |
| **Exact-value deletes** | `15_` touches **no** row it did not insert. Verify against a table pre-loaded with other modules' rows |
| Identity independence | `15_` resolves `WIPStationId` and `MachineIdx` by natural key at run time, never by a hard-coded id |
| Idempotency | `15_` re-runs clean after a successful reverse; `10_` re-runs clean after a successful insert |
| **`FL3PO` absent** | Four stations — FL1, FL2, FL3, FWPACK. ⛔ **No `FL3PO`** (§2.3) |
| Bay uniqueness intact | `UX_RodStaging_Bay` still prevents two rods on `FL1PO` across FL1 and FL3 |
| Runner untouched | `FlatWire_Scripts_RunAll.sql` chains **seven** scripts and names neither `10_` nor `15_` |
| Manifest | `README.md` row 10's `Reversible?` cell names `15_`; a row for `15_` exists |
| Record | `[DEP §4.2]` step 2 carries the three decided values and the per-environment sign-off state |
| Agreement | `FW-003`'s values and `FW-238`'s registration both cite `[DEP §4.2]`, not each other |
