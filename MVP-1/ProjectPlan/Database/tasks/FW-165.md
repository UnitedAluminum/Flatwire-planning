## 2. The three details

### 2.1 The procedure decimates an already-decimated series

`FR-018` sets the **data-recording frequency at 4 ft per data point** (20 ft intermediate), and
[`FW-150`](../../Backend/tasks/FW-150.md) is `RunReading`'s **only**
writer — its insert is **gated on footage, not on the tick**.

So the stored rows are already a **distance-sampled** series. This procedure's `resolution`
parameter decimates that again for display.

⚠ **Two consequences:**
- The row rate is **speed-dependent** — `(FPM ÷ 60) ÷ spacing_ft` — so *"a long run"* means a long
  run **in feet**, not in hours.
- ⛔ **A resolution finer than 4 ft returns every row and decimates nothing.** That is not a bug,
  but it makes the parameter silently ineffective below the write spacing.

### 2.2 ⛔ `G9` makes "predictable under load" unverifiable

The user story's justification is that the query *"stays predictable under load"*. `G9` /
`OI-34` records that the **real-time NFRs are undefined** — including `RunReading` **retention** —
so:

- there is no stated row ceiling to size the decimation against;
- the load test **cannot fail**, because no threshold exists;
- and the table grows without a defined bound.

⚠ **`FW-150` recorded the same gap from the other side** — no test case exists for the 100 ms
cadence, decimation or the on-change channels.

⛔ **So this procedure is built, called, and its performance claim is untested by construction.**
That is the honest state.

### 2.3 The grant is a deploy step, not a code change

AC 4's `GRANT EXECUTE` lives in `20_FlatWire_Grants.sql` — **deploy step 3**, run **once per
environment**, and still **Draft**.

⚠ **So a fresh environment can have the procedure and not be able to execute it**, which
presents as a permissions error from `ContextRepository` rather than as a missing object.
**Check the grant before diagnosing the procedure.**

**Nothing to build.** The remaining work:

1. ⛔ **Do not re-create the procedure.** It is deployed and `ContextRepository` calls it (§1.2).
2. ⛔ **Close `G9` / `OI-34`** — the retention policy and the load target (§2.2). Until then the
   AC's performance claim is unverifiable and should be recorded as such.
3. Run `20_FlatWire_Grants.sql` per environment (§2.3) — **deploy step 3**.
4. When `FW-164` lands, confirm the endpoint's decimation parameter is meaningful **above** the
   4 ft write spacing (§2.1) and behaves sensibly below it.
5. ⚠ **Do not "fix" a resolution finer than 4 ft** — it is a property of the writer, not a defect
   here.

§2.2, and it is `P-191`'s rule applied to a procedure rather than an index: **a story whose

on a table with no retention bound.
