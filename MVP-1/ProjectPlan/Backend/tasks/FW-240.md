## 2. The four details

### 2.1 The boundary question is the story; the mapping is the easy half

`RodOrderConsumption` has **five parents spanning three aggregates**. That is why `FW-207`
stopped: an entity with five parents is either

- a **child of one** aggregate, with the other four as plain ids (the DDD-correct shape), or
- a **read model** outside the aggregates entirely, or
- its own **root**, taking the count from seven to eight or nine.

⛔ **A plan cannot pick.** `[SVC §3.2a]` is the boundary table of record and `P-91` is `⚠ ratify`
against it. **Get the signature before writing a configuration**, because each option produces a
different `DbContext` shape and a different navigation surface for `FW-225`–`FW-227`.

⚠ **Note what `P-12` already implies**: not every table needs a repository. `RunReading` is
mapped by **nothing** and written by raw SQL, deliberately. A read model is a legitimate answer
here, not a cop-out.

### 2.2 Verify by column count — `P-70`'s lesson

The two tables were deployed on 22 Aug and then **widened by `ALTER`**: `P-70` records **nine
`ALTER`-added columns** that a reader of `CREATE TABLE` alone will never see.

⛔ **So do not build the entity from the DDL file.** Query the live database's column list and
**assert the count**, exactly as `FW-207`'s harness does at 352 columns. An entity missing a
column compiles, deploys, and silently drops data on write.

### 2.3 The `ROWVERSION` must be mapped as the entity lands

`P-69` decided to map **all eight** `ROWVERSION` tokens rather than the six `[SVC §3.4]` lists,
and named the two unlisted ones: **`SpoolStaging` and `RodOrderConsumption`**. Six are mapped
today; `RodOrderConsumption`'s is not, because the entity does not exist.

⚠ **An unmapped token still populates and still reads back — it simply stops guarding
anything.** So the failure is silent: no exception, no warning, and `FW-146`'s `409` arm never
fires on this table.

**Map it in the same commit as the entity.** A follow-up story to "add the concurrency token"
is a window in which lost updates are silent.

### 2.4 Cite `[REQ §5.28]`, never the design document

`FR-541`–`FR-560` / `ORD003`–`ORD017` in `[REQ §5.28]` are the **requirements** and are citable.
`LatestDocument/RodOrderAllocation.md` and its `_DesignPlan.md` are **rationale** — applied,
propagated, and **explicitly not citable as a requirement**.

⚠ Both facts are true at once and were once merged into one wrong sentence: *applied* and *not
citable*. Cite the design for **why**; cite `[REQ §5.28]` for **what**.

## 3. Build order

1. ⛔ **`[SVC §3.2a]` signs the boundary** (AC 1, §2.1). **Nothing below starts first.**
2. **Read the live column list** for both tables and record the counts (§2.2) — not the DDL file.
3. Entity types in `FlatWire.Domain/AggregatesModel/`, placed per the signed boundary.
   ⚠ If either is a **child**, it goes in a `…Children.cs` file, following
   `FlatWireRunChildren.cs` / `SpoolProcessingChildren.cs`.
4. **Value objects, not strings**, for the alphas — `D-29` made `RodAlpha` and friends
   validating value objects, and `FW-141` built six. ⛔ **`FW-207` had to add 15 `Ignore` calls**
   when EF mapped `RodAlpha` as an entity type; expect the same and check the model.
5. EF configurations in `FlatWire.Infrastructure/EntityConfigurations/`.
6. **Map `RodOrderConsumption`'s `ROWVERSION`** (§2.3) — `P-69`'s mapped count goes 6 → 7.
7. **Run `FW-207`'s harness.** Model validates, the new column counts assert, and the existing
   assertions stay green.
8. Confirm `FW-225`/`FW-226`/`FW-227` can bind to the mapped types (AC 5).

## 4. Decisions this plan makes

> `P-##` is continuous across the repository; `P-01`–`P-171` precede this story.

### `P-172` — the `ROWVERSION` is mapped in the same commit as the entity

§2.3. An unmapped token fails **silently** — it populates and guards nothing — so a follow-up
story would open a window in which lost updates on this table are invisible. `P-69` already
decided the token should be mapped; this decides **when**.

### `P-173` — the entity is built from the live column list, not the DDL file

§2.2, applying `P-70`. Nine `ALTER`-added columns are invisible to a `CREATE TABLE` read, and
an entity missing one drops data on write with no error.

**Fallback:** if the live database is unreachable, read `03_Materials`/`04_Runs` **and** every
`ALTER` in the chain — but the harness assertion still has to run before the story closes.
