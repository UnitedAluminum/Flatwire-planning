> **Why this document exists.** `FlatWire` is **the first UAL service to put behaviour and
> invariants on its aggregates** (`D-29`, 15 Aug 2026), and the most likely failure mode is not
> doing it badly — it is **rewriting machinery that already exists**. `UA.Framework.Domain` ships
> `Entity`, `ValueObject`, `IAggregateRoot`, `Enumeration`, `IBusinessRule`, `BusinessRule`,
> `CheckRule` / `ICheckRule`, `BusinessRuleValidationException` and `Rules/Specifications/`;
> `CoilCheckin` ships **byte-identical copies** of the rule and exception files (verified 27 Aug
> 2026 — they differ only in their `namespace` line) and its own `DispatchDomainEventsAsync`.
> *"If you are writing an `Entity` or `ValueObject` base class, you have missed the one in
> `UA.Framework.Domain`."*
>
> ⚠ **Two corrections to the older framing of that paragraph, both load-bearing.**
> **(1) It is not all dormant.** `IAggregateRoot` is in live use — `CoilReceiving.Domain/AggregatesModel/`
> and `Common.Domain/AggregatesModel/` both declare `: Entity, IAggregateRoot`. What is dormant is the
> *behaviour*: those classes are still anemic `{ get; set; }` bags with no `IBusinessRule` anywhere,
> which is why `D-29`'s substantive claim stands while *"all of it is dormant"* did not. **Follow that
> folder convention** — see §4 step 3.
> **(2) Inheriting is not uniformly right.** `BusinessRule`, the framework's abstract base, implements
> `IsBroken()` as `IsBrokenAsync().GetAwaiter().GetResult()` — **sync-over-async in a request path**.
> Implement `IBusinessRule` directly instead: `P-93`.
>
> The second thing: **the alpha is the identity, but `Entity.Equals()` operates on `Id`.**
> Those two facts coexist and the gap between them is a real bug waiting to be written.
>
> The third: **`CheckRule` throws, and as built nothing catches it.** `P-89`.

## 2. The seven roots, and what each owns

`[SVC §3.2a]` — the boundary table of record. ⚠ **It was written before the 22 Aug 2026 schema
additions and did not place them; the `SpoolProcessing` row below is ahead of it, and `[SVC]` was
corrected at source on 27 Aug 2026 in the same pass.** See §2.1a.

| Root | Contains | Invariants it enforces |
|---|---|---|
| **`FlatWireRun`** | `FlatWireRunDetail`, `RodCheckin`, `SpoolCheckin`, `RunPauseEvent`, `RollOverride`, `DieChangeEvent`, `SpcCheckpoint` + `SpcMeasurement` | Pause/resume state machine and its **four** resume outcomes; SPC mandated after a die change and after a roll adjust; roll-gap override requires authority, and **revert is Operations-Manager-only** (`FR-212`) |
| **`RodStaging`** | bay state | **`G21` — one rod per *physical* station**, keyed on `Station` not `LineId`. `Blocked` is **derived** (`Staged` + any inspection `Fail`), never stored; `IsWelded` is a **flag on a `Staged` row**, not a status |
| **`WeldEvent`** | — | **Its own root, not part of `FlatWireRun`** — welds are recorded at pre-check-in **before a run exists** |
| **`SpoolProcessing`** | completion state, **`SpoolTraceability`**, **`SpoolOrder`**, **`SpoolStaging`** *(§2.1a, `P-91`)* | Prompt raised **once** per `RUNNING → STOPPED` edge; weight **latched at the PLC stop timestamp**. ⛔ **`SpoolTraceability` segments may not overlap, and here the aggregate is the ONLY defence** — footage is nullable because the genealogy is weight-primary, and a non-overlap trigger joining on `NULL` **passes silently**. Unlike DM010 there is no belt-and-braces |
| **`CoilOutput`** | `CoilTraceability` | **DM010 non-overlap is an aggregate invariant** — footage ranges may not overlap. The trigger stays as belt-and-braces |
| **`RodCheckout`** | — | Mode P / A / B; Mode B needs the supervisor stamp and PLC-locked footage > 0; **Mode P must carry null footage** |
| **`WipRejection`** | — | Disposition lifecycle; **the only thing that clears a `Blocked` bay** — and it does so by **publishing a domain event**, never by reaching into `RodStaging` |

### 2.1 The three deliberate exclusions

- **`RunReading`** — *"the most important exclusion in this design."* 10 Hz time series;
  inside `FlatWireRun` it would materialise thousands of rows on every command. Append-only
  write model, read by Dapper via `sp_GetGaugeTrace`.
- **`Rod`** — a `FlatWireDB`-local mirror of `coils` (`D-04`); `coils` owns the lifecycle.
- **`PassSchedule`** — a read model, reached only through `PassScheduleSnapshot`.

> ⚠ **AC 3's *"`PassSchedule` is MVP-2-owned"* is superseded.** `D-31` (15 Aug 2026) moved
> the three `PassSchedule*` tables **into MVP-1** and made `PassScheduleId` a real enforced
> FK. **The read-model status is unchanged and is the operative half** — MVP-1 reads
> schedules and never authors them, so there is still no aggregate and no repository. Only
> the ownership clause is wrong.

⚠ **`Rod` gets no aggregate and no repository — but it does get an entity.** `FW-142`'s `P-69`
names `Rod`, `SpoolStaging` and `RodOrderConsumption` as *"`FW-207`'s to declare"*, because each
carries a `ROWVERSION` that cannot be mapped until a C# type exists. **Read model, mapped for
reading, no write path** — the same standing that `[SVC §3.2a]` gives it, stated a level down.
`PassSchedule` is the one that never gets an entity at all (`P-13`).

### 2.1a ⚠ The five tables added 22 Aug 2026, and where each one goes — `P-91`

**The multi-rod / multi-order spool work and the rod↔order allocation work landed five tables that
this plan modelled a schema without.** They are in the DDL, in the MVP-1 runner, seeded and
deployed; `[SVC §3.2a]` did not place them, so nothing did until now.

| Table | Placement | Why |
|---|---|---|
| **`SpoolTraceability`** | **child of `SpoolProcessing`** | `FK_SpoolTraceability_SpoolProcessing` on `SpoolAlpha`. Its FKs to `Rod` and `WeldEvent` are **cross-aggregate references by alpha, not navigations**. Carries the non-overlap invariant above — **`G42`'s answer, and the welding-wire certificates are produced from it** (`NFR012`) |
| **`SpoolOrder`** | **child of `SpoolProcessing`** | `FK_SpoolOrder_SpoolProcessing`. The order set behind a spool that crosses an order boundary (`G48`) |
| **`SpoolStaging`** | **child of `SpoolProcessing`** | `FK_SpoolStaging_SpoolProcessing` — the FL2 pre-check-in queue (`OI-118`). ⚠ **It is NOT the analogue of `RodStaging`**, and the difference is the whole reason for the split: `RodStaging` had to be its own root because its parent `Rod` is a **read model with no aggregate to belong to**. `SpoolProcessing` is a root, so its staging state belongs inside it |
| **`RodOrderAllocation`** | **outside the seven** | Parents are `Rod` and itself (`FK_RodOrderAllocation_Superseded`). `[SVC §3.2e]` gives it its own service and three cross-row invariants *SQL cannot express* — a rod's active ranges tile the rod, a `PinnedBoth` row is its order's only row, an order with an allocation has at least one rod |
| **`RodOrderConsumption`** | **outside the seven** | Parents are `FlatWireRun`, `RodCheckin`, `Rod`, `RodOrderAllocation` **and** `RodCheckout` — five, spanning three aggregates. Folding it into any one of them would put a foreign root inside an aggregate boundary |

⚠ **The last two are a boundary question this story must not settle alone.** They belong to the
`RodOrderAllocation.md` design and `[SVC §3.2e]`'s three services; the recommendation above —
**their own aggregate, owned by that design, not folded into these seven** — is `P-91` and is
**flagged for `[SVC]` to ratify**, because `[SVC §3.2a]` is the boundary table of record and a plan
document cannot promote itself over it. **Do not build them here until it is ratified.** What *is*
unambiguous and buildable now is the three spool children.

> ⚠ **`RodOrderConsumption` and `SpoolStaging` each carry a `ROWVERSION`.** `P-69` requires the
> token mapped **when the entity lands**, which is here. Four of the eight are mapped today
> (`FlatWireRun`, `RodStaging`, `SpoolProcessing`, `CoilOutput` — see `ExceptionHandlingMiddleware`
> arm 2); `Rod`, `SpoolStaging` and `RodOrderConsumption` are this story's, and `PassSchedule`
> never gets one.

### 2.2 ⚠ The alpha is the identity — and equality is not

`[SVC §3.2a]`:

> ⚠ **The surrogate is not the identity.** `FlatWireRun` carries both `[Id] INT IDENTITY`
> and `[RunId] VARCHAR(20)` — and it is `RunId` that every child table references. […] So
> **repositories are keyed by the alpha value object**. […] Note `Entity.Equals()` and
> `IsTransient()` operate on `Id`, so **equality is surrogate-based**: do not assume two
> instances with the same alpha compare equal before both are persisted.

Both halves are true at once. **Key on the alpha; do not rely on `==` for identity before
persistence.** A `HashSet<FlatWireRun>` or a `Distinct()` over unsaved aggregates will not
behave as the domain reads.

## 4. Build order

### `P-89` — invariant failures **throw**, and `FW-146` owes the fifth arm

⛔ **As built, this story's `422` path returns `500`.** The card, §2's callout and §7 all describe
`IBusinessRule` → `CheckRule` → `BusinessRuleValidationException` → the contracted status. The
built [`ExceptionHandlingMiddleware`](FW-146.md) has **four
arms** — `CustomException` + inner `ValidationException` → `400`, bare `CustomException` → `400`,
`DbUpdateConcurrencyException` → `409`, `DbUpdateException` + unique-index `SqlException` →
`MapUniquenessViolation`, and **`default` → `500 INTERNAL_ERROR`**. There is no arm for the domain
exception, so an aggregate throw is indistinguishable from a null-reference bug.

**The decision is to keep the throw, and to make the arm a named dependency rather than an
assumption.** Three reasons the throw survives `P-57`:

1. **It is the story's reason to exist.** The *"So that"* clause is *"rules cannot be bypassed by a
   caller that forgets to run a validator."* A rule that returns is a rule the caller must
   remember to consult; `CheckRule` inside an aggregate method cannot be skipped.
2. **`P-57` is about where *service-level state checks* live, not about aggregate invariants.** The
   `INSPECTION_FAILED` proof it rests on has **two** paths — `422` from `CheckInService` and
   `201 Blocked` from `PayoffStagingService` — which is a *service* choosing between outcomes, not
   an aggregate defending itself. Both mechanisms coexist: services return; aggregates throw.
3. **`FW-146` already anticipated it** — *"if `FW-207`'s aggregate later throws, the arm is added
   then, to §2.5's list."* This decision is that story being told the answer is yes.

⚠ **One factual correction owed back to `FW-146`, corrected at source 27 Aug 2026:** it says
`BusinessRuleValidationException` *"does not exist in the solution"*. **It does** —
`UA.Framework.Domain/Exceptions/BusinessRuleValidationException.cs`, `sealed`, exposing
`BrokenRule` and `Details`. What is absent is the **arm** and the **convention**, not the type, and
the distinction matters because *"the type does not exist"* reads as *"defining one is inventing
something"*, which would be the wrong reason to refuse the arm.

**Sequencing:** the arm is small — one `case BusinessRuleValidationException` reading the rule's
own status and code (`P-90`) — but it is `FW-146`'s file. Raise it before step 5 lands, and **do
not sign this story off on an unmapped throw**; the symptom is silent and looks like a server bug.

### `P-90` — the status is **per rule**, carried as data. The blanket `422` is withdrawn

⛔ **AC 6's *"`IBusinessRule` … → `422`. Includes `G21` bay occupancy"* is wrong on the status, and
the callout that justified it was wrong on the reasoning.** `[API §1.3]`:

- **`409`** — *"conflict with current state — line already has an active run, **bay already
  occupied**, rod already staged or checked in, payoff mismatch, optimistic-concurrency failure"*
- **`422`** — *"well-formed but violates a business rule … will never succeed as submitted"*

and *"the 409/422 split is load-bearing"*. `[API §1.8]` prices `BAY_OCCUPIED` at **409**, and the
built service agrees twice: `StubPayoffStagingService` returns `409`/`BAY_OCCUPIED`, and
`MapUniquenessViolation` maps a `UX_RodStaging_Bay` violation to `409`/`BAY_OCCUPIED`. **A `422`
here would tell the operator "this will never succeed" about the one condition that clears the
moment someone unstages the other rod.**

**The blanket mapping is replaced by a per-rule one.** Each rule declares its own `StatusCode` and
`[API §1.8]` `ErrorCode`; `P-89`'s arm reads them. Two consequences worth stating:

- **`§2`'s callout reasoning is inverted and is corrected at source.** *"Breakable by state, so
  `422`"* is `[API §1.3]`'s definition of `409`. The two `P-19` rules are still `422` — for the
  right reason, that they will never succeed as submitted.
- **The middleware must not sniff `Message`.** `IBusinessRule` carries only `IsBroken()` and
  `Message`, and `BusinessRuleValidationException` is `sealed` so it cannot be subclassed per
  status. Hence the local `FlatWireBusinessRule` base in step 5. `MapUniquenessViolation` already
  has to match on index names inside a `SqlException.Message` and `FW-146` flags that as a rename
  hazard; **do not add a second instance of the same pattern where a property will do.**

### `P-91` — where the five tables of 22 Aug 2026 go, and which two this story must not settle

§2.1a is the placement. **The three spool children are unambiguous and buildable now** — each has a
single FK to `SpoolProcessing`, and `SpoolStaging` is a child rather than a second `RodStaging`
because `RodStaging` is a root only for want of a parent (`Rod` is a read model).

⚠ **`RodOrderAllocation` and `RodOrderConsumption` are recommended *outside* the seven and the
recommendation is flagged for `[SVC]` to ratify.** `RodOrderConsumption` has five parents spanning
three aggregates, and `[SVC §3.2e]` already gives both tables their own services and three cross-row
invariants. **`[SVC §3.2a]` is the boundary table of record and this plan cannot promote itself over
it** — so the placement is proposed here and settled there. Do not build those two until it is.

**The buildable half carries a real invariant, and it is the reason this decision is not
bookkeeping:** `SpoolTraceability`'s segments may not overlap, and **the aggregate is the only
defence**. Its footage bounds are nullable because the genealogy is weight-primary, so a non-overlap
trigger joining on `NULL` **passes silently** — which is why the 22 Aug work deliberately added no
trigger and assigned the rule here. That is `G42`'s answer, and the welding-wire customer
certificates are produced from that genealogy (`NFR012`).

### `P-92` — the three business keys stay plain strings

`WeldEvent.WeldEventId` `WLD-###`, `RodCheckout.CheckoutId` `CO-####` and
`WipRejection.RejectionId` `REJ-####` are the identities of three of the seven roots and are in
**neither this story's six alphas nor `[BR §3]`'s format list**. `FW-141` raised it as *"either
three more value objects are owed — `FW-207`'s, by `P-66`'s seam — or they are deliberately plain
strings"* and asked for a decision before its step 3. **Step 3 shipped with plain strings**; this
records that as deliberate rather than defaulted.

**Why not value objects.** The whole argument for an alpha value object is that the format is known
and a malformed one should be unrepresentable — that is what closes `G14`. Here the format is *not*
known: **`OI-21` is open on whether `RejectionId` is `REJ-0041` or `REJ-2026-0418`**, so a
validating constructor would bake a guess into a type and the guess would be load-bearing.
Separately **`OI-20` blocks typing `WipRejection.MaterialAlpha` at all** — it is a rod *or* spool
alpha with no FK and no discriminator, so typing it to `RodAlpha` would silently exclude spools.

⚠ **Revisit when `OI-21` closes**, and mint the three then; a `string` narrowed later is a
compile-error-driven change, which is the cheap direction. **`[BR §3]` should carry the three
formats regardless** — they are alphas the operator reads, absent from the list that owns alphas.

### `P-93` — implement `IBusinessRule` directly; do not inherit the framework's `BusinessRule`

The framework ships an abstract `BusinessRule : IBusinessRule` whose only contribution is
`public virtual bool IsBroken() => this.IsBrokenAsync().GetAwaiter().GetResult();` over a
`protected abstract Task<bool> IsBrokenAsync()`. **That is sync-over-async on a request path** —
thread-pool starvation under load, and a deadlock risk in any context with a synchronization
context. It buys an async hook and then consumes it by blocking.

**Implement the two-member interface directly.** `IBusinessRule` is `bool IsBroken()` and
`string Message`; FlatWire's local base adds `StatusCode` and `ErrorCode` (`P-90`) and nothing
else. ⚠ **This is not a licence to write a base class the framework already has** — the rule of
§4 step 1 stands for `Entity`, `ValueObject`, `IAggregateRoot`, `ICheckRule`/`CheckRule` and
`BusinessRuleValidationException`. It is one named exception, for a measured reason. **If an
invariant genuinely needs to await I/O, that check belongs in the handler before the aggregate
method is called, not behind a blocking property.**
