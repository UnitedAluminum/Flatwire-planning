> **Why this document exists.** Four things here are decided and non-obvious. **(1)** There
> are **two distinct cadence knobs** and this layer owns both — confusing them produces a
> hub that drains at the OPC poll rate or an OPC poll at 10 Hz. **(2)** Options binding
> **fails fast at boot**, and emits **one** warning naming the *count* of unconfirmed tag
> paths — not one per path, and **the count is read off the bound map, never written into
> the code** (§4). **(3)** The `ITInhibit` key lives **inside each line's `Tags` block, never
> at the root**. **(4)** This story **binds** the tag map; `[PLC]` **owns** it, and writing a
> tag path into any other file creates the seventh copy of a surface that was deliberately
> reduced to one.

### 2.1 ⚠ Two cadences, and this layer owns both

`phase-01b` L89:

| Knob | Value | Belongs to |
|---|---|---|
| **OPC publish interval** | `NFR005`: **1 s default**, configurable 5 / 10 / 30 s — `[PLCC]`'s `PublishIntervalMs` | the ingest side |
| **Hub drain cadence** | **~100 ms / 10 Hz** | the broadcast loop |

They are unrelated numbers on opposite sides of the bounded channel, which is exactly what
decouples them. Bind them as two settings with two names; never derive one from the other.

### 2.2 ⚠ `ITInhibit`'s key placement is a rule, not a preference

`phase-01b` L112: the config key lives **inside each line's `Tags` block, never at the
root**. One tag per line — `FL1.ITInhibit`, `FL2.ITInhibit`, `FL3.ITInhibit` — built for
**three** lines. It is **written, never read**, and there must be **no operator clear path
anywhere in the surface**, enforced by the *absence* of any endpoint, command or hub method.
A root-level key would imply one interlock across all three lines, which is the opposite of
the line-scoped behaviour `TC-017a` tests.

> ⚠ **Bind three keys even though only two lines behave — and FL3's is the open one.**
> `[PLC §5.2.3]` publishes `FL3.ITInhibit` as `[PROPOSED]`, and whether FL3 carries **its own
> tag** or **asserts FL1's and FL2's together** is `PLC-Q08` / **`G30`** (§7). Per
> [`FW-205`](FW-205.md) `P-26` the surface is built for three and FL3 is
> **configured and inert** until that answers. **Do not collapse the config to two lines** —
> `phase-01b` exit criterion 5 names three, and re-widening later touches every environment
> file. This paragraph carried the *"three"* without the *"why"* until 27 Aug 2026, which is
> exactly the reading that invites the collapse.

### 2.3 The anti-drift rule

`[PLC]` is the **only** tag map in the repository, after six partial and mutually
contradictory copies were reduced to one. `PLCCommunication.md` carries **no tag path
strings by rule**.

> **If you are about to write a tag path into a `.cs` file, a comment or a second
> `appsettings` fragment, you are creating the seventh copy.** The paths belong in the
> environment configuration, sourced from `[PLC]`.

### 2.4 ⚠ Keys are logical names; values are paths — and this is what de-fangs the blocker

`[PLCC §2]`'s first binding rule, and the plan omitted it until 27 Aug 2026:

> **Keys are stable logical names; values are paths. Code references the logical name and
> never a literal path** — that is what makes a commissioning correction a config edit.

`Gauge`, `Width`, `Speed`, `LineState`, `RollGap`, `ITInhibit` are keys. The `[PLC §5.2.x]`
strings are values, and **only the right-hand side ever moves.**

**This is the answer to this story's own blocker.** `PLC-Q05` / `G33` says the *measure
segment* of every path is ours — so if the controls engineer comes back with different
measure names, a correctly-bound map absorbs it as a **values-only edit and an app-pool
recycle**, with no config-contract change and no rebuild. `[PLCC §2]` says so outright, and it
is why the keys were deliberately decoupled from the paths in the 4 Aug realignment
(`GaugeCurrent`→`Gauge` was *readability, not necessity*). **Bind the map key-first and the
blocker costs a config edit; bind it path-shaped and it costs a release.**

## 3. Build order

> ### ⚠ Build to `[PLCC]`'s appendix §2 — it is the implementation contract for this story
>
> **`PLCCommunication.md` Appendix §2 is titled *"Configuration binding"* and carries the
> annotated JSON skeleton plus six binding rules.** It is the shape to build; the steps below
> order the work, they do not replace it. **This plan did not cite it until 27 Aug 2026** —
> §2.3 named the document only to say it holds no tag path strings, which is true and is
> precisely *why* it can hold the key structure. Read it before step 1.

1. **Strongly-typed options classes** — one per concern group. Bind with
   `services.Configure<T>` / `AddOptions<T>().Bind(...)`.
2. **`ValidateOnStart()` with `DataAnnotations` or a validator** — see `P-16`.
3. **The tag map** as a nested structure keyed by line, each line carrying a `Tags` block
   (with `ITInhibit` inside it, §2.2) — **one key per row of that line's map in
   `[PLC §5.2.1]` / `[PLC §5.2.2]` / `[PLC §5.2.3]`**, which is **reads and writes both**.
   `[PLCC §2]`'s skeleton is the worked example, down to the indexed dancer keys on FL2
   (`DancerActive1/2`, `DancerPosition1/2`, `DancerMode1/2`, `DancerTension1/2`).

   > ⚠ **Do not shape the map from `[PLC §7.2]`'s six value groups — corrected 27 Aug 2026.**
   > This step said exactly that, and it is the wrong table. **§7.2 is the *push payload***
   > (component active/bypass · die sizes · roll gaps · edge type · speed · gauge and width
   > targets) — it names **values and their source, and contains no tag path at all**. Built
   > that way the bound map would carry **no read path whatever**: no `AGC.Gauge`, `.Width`,
   > `Speed`, `Payoff{n}.Weight`, `TKUP{n}.Footage`, `LineState`, no `Status.IsActive` /
   > `.IsFaulted`, no dancer row — which is precisely the surface [`FW-N05`](FW-N05.md)
   > subscribes to and the broadcast loop feeds, and it would force every one of them into
   > code, breaking §5's *"zero hits outside configuration"*. **The step was also
   > self-contradictory**: it required `ITInhibit` in the `Tags` block while shaping that block
   > from six groups that do not include it — nor `LineState`. **The six groups are still
   > right, in their place:** they are the payload [`FW-082`](FW-082.md)
   > builds from the pass schedule, and it **resolves each one's path through the map bound
   > here** (`FW-082` `P-41`). Two structures, one of them this story's.

4. **`LineStateMap`** — a **per-line block, sibling to `Tags`**, mapping the controller's raw
   `LineState` values to the application's states (`[PLC §6]`, `[PLCC §1.7]`). ⚠ **This step
   did not exist until 27 Aug 2026 and nothing else in the plan bound it.** It is **empty
   until `C2`** and must therefore validate as *present but empty* — `PLC-Q01`'s answer
   arrives **at commissioning, after code freeze, and must apply without a build**, which is
   the whole reason it is configuration. `enum LineState` has **no `Stopped` member**; the

5. **The two cadences** as separate settings (§2.1).
6. **`SimulatePLCTagPush`** — a plain flag, **at the root, not per line** (`[PLCC §1.6]`
   contrasts it with the interlock key deliberately), `true` in every environment for now,
   selected **by configuration, not by call site**.
7. **The unconfirmed-path warning** — `P-16`, counting **bound minus `Confirmed`** per `P-74`.
   Treat a missing `Confirmed` list as empty.

## 4. Decisions this plan makes

> `P-##` is continuous across this folder; `P-01`–`P-15` precede this story. **This story owns
> two, and they are not adjacent** — `P-16` from the first issue and **`P-74`**, minted on the
> 27 Aug 2026 review because `P-16` turned out not to be implementable as written. New
> decisions across the folder now mint at **`P-75`+**.

### `P-16` — fail fast at boot; warn **once**, with a count

`phase-01b` L89 states both halves and they pull against each other, so the resolution needs
writing down:

> **Options binding is validated at startup and fails fast at boot**, emitting **one**
> warning naming the *count* of unconfirmed tag paths — not one warning per path.

**Fail fast** applies to *structural* problems: a missing connection string, an absent JWT
variable, a line with no `Tags` block, a **logical key the code uses that the map does not
carry** (`[PLCC §2]`), or a publish interval outside its allowed set — **`1000 | 5000 | 10000
| 30000` ms**, named in `[PLCC §2]`'s skeleton. The service must not start.

**One thing that must *not* fail fast: an empty `LineStateMap`.** It is empty until `C2`
supplies the raw values, so validate it as *present*, never as *populated* — the two look
alike in a validator and only one of them lets the service boot before commissioning.

**Warn once** applies to *confirmation status*. **No tag path is confirmed** — the reading
convention has been `[PROPOSED]` and `[CLIENT INPUT REQUIRED]` only since the **v1.0 reissue,
and still is at the current v1.2** *(this said "Under `[PLC]` v1.0" until 27 Aug 2026, which
read as current)* — and a path becomes confirmed when commissioning test `C1`/`C11` says the
controller accepted it. `[PLC §5.2]` says it outright: *"Every row is `[PROPOSED]`, and that is
the honest position. No row in this table has been read off a machine."* So **today the count
equals the whole map** — a warning per path would emit one line per bound tag at every boot, in every
environment, for weeks, which is noise that trains operators and developers to ignore startup
warnings. **One line naming the count** stays legible and still falls to zero as commissioning
proceeds.

> ### ⚠ Count the bound map at runtime. Do not write a number into the code.
>
> **The `41` this section used to assert is the 4 Aug 2026 figure** (`FL1` 15 · `FL2` 14 ·
> `FL3` 23) and **it is stale**: `[PLC]` **v1.1 grew the map on 12 Aug 2026** with the dancer
> read surface (`PLC-Q18`, `G35`), and the published tables now carry **17 rows on FL1 and 22
> on FL2** against those 15 and 14. `41` is still what `G33`, `phase-01b` L192, `[TB §7]` and
> the sibling plans quote, so **it is left standing here as the cited register figure rather
> than silently re-baselined in a leaf plan** — re-counting is the register owner's, and the
> divergence is logged in §7.
>
> **None of that should reach the implementation.** The warning counts the entries in the bound
> options object; the number is a property of configuration, and it moves whenever `[PLC]`
> moves. A hardcoded `41` is a constant that was already wrong on the day it was written, and
> it would then under-report the very thing the warning exists to surface.

**So: unconfirmed is not a startup failure.** If it were, the service could not boot until
commissioning, and `SimulatePLCTagPush = true` exists precisely so it can.

### `P-74` — the count needs somewhere to read confirmation from, and nothing has one

> Minted 27 Aug 2026 on the third review pass. **`P-16` is not implementable as it stood**, and
> the defect is in the source rule, not only in this plan.

`[PLCC §2]` requires the warning to *"let that count **fall** as `C1` and `C11` confirm them. A
count that reaches zero is the signal worth having."* **There is nothing for it to fall
against.** The bound map is `key → path` and no more — `[PLCC §2]`'s own skeleton carries no
confirmation field — and **`[PLC]` retired the `[CONFIRMED]` tag from the specification
entirely** at the v1.0 reissue, so the document cannot supply it either. `P-16` inherited
*"still falls to zero as commissioning proceeds"* without a mechanism, and a developer reaching
build step 7 has to invent a config element to satisfy it — **exactly the invention §2.3
forbids everywhere else.**

**Two ways out, and the cheap one is wrong:**

| | |
|---|---|
| **A — count every bound path, always** | Zero new schema, and honest. But the number **never moves**: a warning that says the same thing at every boot forever trains people to ignore it just as reliably as one line per path would, which is the whole failure `P-16` exists to prevent. **It also silently abandons a stated requirement** rather than recording that it was dropped |
| **B — an optional per-line `Confirmed` list of logical keys, populated at `C1` / `C11`** ✅ | Count = bound − confirmed, so it falls and reaches zero. **Values-only, applied without a build, corrected by an app-pool recycle** — the same property as every other rule here (§2.4). Costs two lines of schema |

**Build B.** It is what makes the already-decided behaviour true, and it stays inside the
config-not-code principle the whole story rests on. Absent the list, treat it as empty — so a
map with no `Confirmed` block behaves exactly as A, and **B degrades to A rather than failing.**

⚠ **The schema addition is owed to `[PLCC §2]`, which this story does not own.** Raise it with
that document's owner; do not let the field's absence there become an argument for A, and **do
not put the key anywhere else** — one home, per §2.3. Until it lands, the plan's position is
recorded here and the build is unblocked either way.
