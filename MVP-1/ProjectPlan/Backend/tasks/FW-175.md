## 2. The four details

### 2.1 ⛔ Deferring it means the trial demonstrates the defect

`FW-177`'s status reads *"`FW-175` deferred — notification is transient."* So during the trial,
**a supervisor who is not connected when a disposition is raised never learns of it**, and the
material stays locked.

⚠ **That is exactly `G7`**, and the trial will exercise the path. **Two honest options:**

- ✅ **Record it as a known trial limitation**, with the manual workaround (someone tells the
  supervisor), the way `[TRP §7]` greys deferred controls and states the scope.
- ⛔ **Say nothing**, and let it present as an intermittent bug — which is what an unreliable
  notification looks like from the floor.

**Take the first.** ⚠ **And note the asymmetry**: the *rejection* is persisted (`P-46`), so
material is not lost — only the **prompt** is transient. **The recovery is a screen refresh, not
a data repair**, which makes the workaround genuinely viable.

### 2.2 The durability pattern already exists — follow `G38`, not a message broker

The repository has solved *"server-owned state that survives a refresh and is re-delivered on
join"* once already: **`G38`'s five `FlatWireRun` prompt columns**, plus `FW-080`'s `P-100`
replay-on-join.

⚠ **This is the same problem shape**, and the same answer applies: **persist the pending state,
and let the hub replay it on connect.** ⛔ **Do not introduce a queue technology** — no broker, no
outbox, no polling service. `[ARC §14]` keeps the stack as-is, and `[TS §1.2]` means anything new
arrives untested.

**Where it differs from `G38`:** a prompt belongs to **one run**; a pending disposition belongs
to **a role**, and any supervisor may claim it. So the state is a **row per pending item**, not
columns on a parent.

### 2.3 A claim is a concurrent state change, and the guard is missing

AC 3: *"Items are claimable, and a claim is recorded with the supervisor id."*

⛔ **Two supervisors claiming the same item at once is precisely the lost-update case**, and
**`WipRejection` has no `ROWVERSION`** — it is one of `D-30`'s three. So today
`DbUpdateConcurrencyException` never fires and `FW-146`'s `409` arm guards nothing there.

⚠ **`FW-243`'s `P-174` argues the decision turns on *concurrent* mutability**, and **this story
is the strongest evidence that `WipRejection` has it**: a durable queue with multiple claimants
is a concurrent mutation by design.

✅ **So this story should be cited into `D-30`'s decision**, not merely wait on it. **The queue
row itself must carry a token regardless** — whatever `D-30` decides about `WipRejection`.

### 2.4 The queue is a projection, and the disposition stays the record

`P-46` settles that **`FW-174` persists PENDING DISPOSITION** and *"the queue is `FW-175`'s"*.

⛔ **So the queue must not become a second source of truth for whether material is held.** The
`WipRejection` / `RodCheckout` row is the record; the queue entry is **the work item that points
at it**.

⚠ **Consequence for AC 4**: *"Resolution closes the queue entry **and** writes the approval
stamp"* — **two writes, one transaction**. A closed queue entry with no stamp loses the approval;
a stamp with an open entry re-presents resolved work.

## 3. Build order

1. ⚠ **Record the trial limitation** (§2.1) before anything else — it costs nothing and it is
   the item most likely to surface as a support incident.
2. A **queue table**: item, the disposition it points at, state, claimant, claim time, resolution,
   resolver, resolution time, **and a `ROWVERSION`** (§2.3).
   ⚠ **FKs in `06`, indexes in `07`**, guarded for idempotency; ⛔ **`[DBD §6.2]` states the
   count, not this plan.**
3. The service: enqueue on PENDING DISPOSITION, claim, resolve.
4. **Claim is atomic and idempotent** — a second claimant gets a clear refusal, not a silent
   overwrite (§2.3).
5. **Resolution writes the queue close and the approval stamp in one transaction** (§2.4).
6. **Replay on connect** via `FW-080`'s existing mechanism (§2.2) — ⛔ **no new transport.**
7. Cite this story's concurrency requirement into **`D-30`** (§2.3).

## 4. Decisions this plan makes

> `P-##` is continuous across the repository; `P-01`–`P-232` precede this story.

### `P-233` — durability is persistence plus replay-on-join, not a queue technology

§2.2. `G38` and `P-100` already implement this shape, `[ARC §14]` holds the stack, and
`[TS §1.2]` means a new component ships with no automated tests. **A table and the existing hub
replay meet all four acceptance criteria.**

**Fallback:** if throughput ever demanded a broker, the interface would not change — the queue is
behind a service either way.

### `P-234` — the queue row carries its own concurrency token regardless of `D-30`

§2.3. `D-30` is about `WipRejection`, `RodCheckout` and `WeldEvent`. **The queue row is new**, so
its token is this story's call and needs no decision — and **a claimable item without one is a
lost update by construction.**

⚠ **And this story is evidence for `D-30`**: multiple claimants make `WipRejection` concurrently
mutable in practice, which is `P-174`'s test.

### `P-235` — the queue points at the disposition and never replaces it

§2.4, extending `P-46`. Two sources of truth for "is this material held" would drift, and the
drift releases held material or holds released material.

## 5. Verification

**No automated tests** — `[TS §1.2]`. Verified in the QA0 walkthrough with two clients.

| Check | Expected |
|---|---|
| **Disconnected supervisor** | Raise a disposition with **no supervisor connected**; a supervisor connecting afterwards **sees it** (AC 2) — the `G7` fix |
| Durable | Survives a service restart, not only a reconnect |
| **Two claimants** | Two supervisors claim simultaneously: **one succeeds, one is refused clearly** — ⛔ not a silent overwrite (`P-234`) |
| Claim recorded | Supervisor id and time stored |
| **Resolution atomic** | Queue close **and** approval stamp in one transaction — kill mid-way and confirm neither half lands alone (`P-235`) |
| Accept / Hold / Reject | All three close the entry and stamp |
| **Single source** | The `WipRejection` row remains the record of hold; the queue points at it (`P-235`) |
| **No new transport** | ⛔ No broker, no outbox, no poller — replay via `FW-080` (`P-233`) |
| Counts | `[DBD §6.2]` updated **there**; `verify_schema_counts.py` green |
| Trial note | The deferral and its workaround are **recorded** (§2.1) |
