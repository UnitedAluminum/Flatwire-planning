## 2. The five details

### 2.1 ⛔ `OI-103` — nothing bounds a value written to the machine

`OI-103` was raised on 11 Aug 2026 precisely because **there is no bound on a roll-gap change**,
and the Roll Adjust dialog writes straight to the machine.

⚠ **This is not a validation nicety.** `FR-018`-era gauge control aside, a roll gap is a
physical setting; an operator typo of one decimal place is a machine command.

**Until `OI-103` closes, the honest options are:**

- ⛔ **No bound** — ships the hazard.
- ✅ **A configured bound with a loud default**, recorded as provisional, so the number exists in
  configuration rather than in nobody's head.

⚠ **`FR-212`'s Ops-Manager revert is the compensating control** — and §2.2 shows it does not
work yet either.

### 2.2 ⛔ The revert is specified, role-gated, and unrecordable

`FR-212` restricts reverting to **Operations Manager**. `G49`'s **B4** records what is missing:
`RollOverride` has **no `IsReverted` / `RevertedBy` / `RevertedAt` / reason columns**, so **a
reverted override is indistinguishable from one still in force.**

Three separate gaps, and they compound:

| Gap | Owner |
|---|---|
| The **columns** | [`FW-244`](../../Database/tasks/FW-244.md) B4 |
| The **endpoint** | ⛔ `OI-32` — **unowned** |
| The **role** | `FW-145` — ⚠ unbuilt, and the six claim **values** are unmapped |

⛔ **So AC 6 cannot be met by this story alone**, and saying so is better than implementing a
revert that leaves no trace. ⚠ **The Operations Manager role definition itself lives in
`PassScheduleManagement.md` §3.3–§3.4 — an MVP-2 document** — which is the one place MVP-1
still reaches into MVP-2.

### 2.3 The SPC checkpoint is written, and the link back is missing

AC 2 logs an `SpcCheckpoint` of type **`RollAdjustTrigger`** at footage. The type exists in the
`CHECK` at `05_QualityOutput.sql:39`.

⛔ **`G49` B6: there is no link in either direction between `RollOverride` and the checkpoint it
produced.** `FW-244` adds `RollOverride.SpcCheckpointId` — **one direction only** (`P-161`).

⚠ **And the response carries `spcCheckpointId`** (AC 5), so the value is already in flight — it
simply has nowhere to be persisted. **Build the service to write it as soon as the column
lands**, and record the gap until then.

### 2.4 The schedule half has nowhere to go, and that is by design

The card's own note: this **subsumes the MVP-1 half of `FW-014`**, whose sink
`PassScheduleChangeLog` is an **MVP-2 table**.

✅ **The run-level `RollOverride` row IS written** — that is the MVP-1 obligation.
⛔ **The schedule-level record is not**, and cannot be: **MVP-1 reads pass schedules and never
authors them** (`OI-110`, `P-13`), so there is no write path to a schedule's change log by
design.

⚠ **This is consistent, not a gap** — but it reads like one, because `PassScheduleChangeLog`
**exists** in `02_Schedule` (`D-31` brought the three `PassSchedule*` tables into MVP-1).
**Owning the table is not owning the data.**

## 3. Build order

1. ⛔ **Get a bound for `OI-103`**, even a provisional configured one (§2.1). **Do not ship an
   unbounded write to a machine silently.**
2. `RecordRollOverride` handler on the built `RollAdjustController`.
3. `RollOverrideService`: write the override → **per-roll `PLCTagService` write** → log the
   `RollAdjustTrigger` `SpcCheckpoint` at footage.
   ⚠ **Order matters**: the audit record precedes the push (`FR-072`), and `FW-151` already
   implements attempt-then-outcome.
4. ⛔ **All deltas zero → no write** (AC 4) — matching the dialog's short circuit. **No override
   row, no PLC write, no checkpoint.**
5. ⛔ **Never touch `PassSchedule`** (AC 3, §2.4).
6. Response: adjustments, delta, `plcTagWritten`, `spcCheckpointId`.
   ⚠ **`plcTagWritten` must not claim more than `G58` permits** — a `200` from `OPCConnection`
   is not evidence of a write (§2.1, `P-105`).
7. **Record what AC 6 cannot do yet** (§2.2) rather than implementing a traceless revert.
8. Write `SpcCheckpointId` as soon as `FW-244` lands (§2.3).

## 4. Decisions this plan makes

> `P-##` is continuous across the repository; `P-01`–`P-211` precede this story.

### `P-212` — `plcTagWritten` reports what was attempted and confirmed, never what the controller did

§2.1, applying `P-105`/`G58`. `OPCConnection` returns `200` regardless of outcome, `IsGood` is
never set, and `OPCUAManager.cs:362` verifies by reference equality. `FW-151` already works
around this with a **confirm read using a `Value = null` sentinel**.

⛔ **So `plcTagWritten: true` must mean "written and confirmed by read-back"**, not "the call
returned". Otherwise a roll adjustment reports success while the mill keeps its previous
setting — `G33`'s silent-failure case, on the one screen that writes to the machine.

### `P-213` — the revert is not implemented until it can be recorded

§2.2. A revert that leaves no trace is worse than no revert: the override reads as still in
force, and the operator believes it is not. **Ship the forward path; record the gap.**

**Fallback:** if a revert is needed before `FW-244`, write it as a **new compensating override
row** with zero deltas and a reason code — visible, auditable, and it needs no new columns.
⚠ **But it is not the same thing as `FR-212`'s revert** and must not be labelled as one.

### `P-214` — a provisional bound is configured, not hard-coded, and is recorded as provisional

§2.1. `OI-103` may close with a different number, and a hard-coded one becomes invisible.
**Follow `FW-144`'s pattern** — bind it, assert it at boot, warn once with a count.
