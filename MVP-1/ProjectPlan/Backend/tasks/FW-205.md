> **Why this document exists.** `ITInhibit` blocks the machine. It is the one thing in
> Phase 1B whose *correct* implementation is defined largely by what must **not** exist:
>
> **There is no operator clear path, and there must not be one.** `TC-016` attempts a clear
> *via every UI surface* and must find none. The rule is enforced by the **absence** of any
> endpoint, command or hub method — so a developer who "helpfully" adds a reset button has
> broken a P1 test by writing code, not by omitting it.
>
> Three more inversions: the tag is **written, never read**, so it is a `PLCTagService`
> operation and not a subscription; the config key sits **inside each line's `Tags`
> block, never at the root**, because a root key surfaces the first time an idle line blocks
> a running one; and the watchdog **must not open its own reader on the reading channel** —
> the channel is single-reader by construction and a second consumer breaks the broadcast
> loop without raising anything (`P-129`).

## 2. What the three conditions actually watch

All three are **watchdogs over the footage tag** that OPC ingest delivers — one shared
watchdog, not three separate ones.

| # | Condition | Set when |
|---|---|---|
| 3 | Feet data **unavailable** | **sustained silence** — nothing usable has reached the line for the configured window, or every snapshot that does arrive carries `FootageFt = null` |
| 4 | Feet data **invalid** | **a negative footage.** That is the whole rule (`P-128`) — a *decrease* is a counter reset and means something else already |
| 5 | **Two or more consecutive recordings missing** | **a short gap — ≥ 3 × `PublishIntervalMs` of silence** in an otherwise-live feed, and **additionally raises the data-recording alert** |

⚠ **`[PLC §8.2]` gives no operating definition of any of the three** — the rows above are
ours. `P-128` draws condition 4 and `P-130` draws the boundary between 3 and 5, which differ
by **degree, not kind**: that is why the card calls them *one shared watchdog* rather than
three. All three watch the **feed**, never `RunReading` rows (`P-130`).

Condition 5's alert goes out on the **existing `AlertRaised` event**. **Do not add a hub
event** — the contract is closed at **fourteen** events plus six markers, twenty payloads in
all (`[SIG §5.2]`, `[SIG §5.4]`, the latter published 28 Aug 2026 by `P-117`).

### 2.1 The alert is a **pair**, or DB1's alert bar sticks

`AlertRaised` is event 8 and **`AlertCleared` is event 9** — both built, both on
`IFlatWireClient`, both driving the same DB1 alert bar. Condition 5 raising `AlertRaised`
and nothing ever sending `AlertCleared` leaves the operator looking at a data-recording
alert on a line that recovered minutes ago.

**Raise on the set edge, clear on the clear edge, same `AlertType` string both times.**
`AlertClearedEvent` carries only `{LineId, AlertType}`, so the string is the join key — pick
one constant and use it in both places.

### 2.2 Where the watchdog gets its readings — **not from its own channel reader**

⛔ **`ReadingChannel` is `BoundedChannelOptions { SingleReader = true }` and `FW-150`'s
broadcast loop is the one drain.** A watchdog that resolves `IReadingChannel` and reads it
**competes with that loop for snapshots**: each one goes to whichever reader takes it first,
so DB3's traces thin out, `RunReading` rows go missing, and **nothing throws** — the channel
is doing exactly what it was configured to do.

**Ride the drain for the stamp; evaluate on your own timer** (`P-129`). ⛔ **Not "evaluate on
the drain"** — a callback that fires on arrival cannot detect an absence, and `TickAsync`
**returns early on an empty tick**, which at a 1 s publish against a 100 ms drain is nine
ticks in ten. So the two halves separate:

| Half | Where | Cost |
|---|---|---|
| **Stamp** last-seen `(ReadAt, FootageFt)` per line | in `TickAsync`, **after** the empty-tick return, once per line in the batch | ≤ 3 dictionary writes per tick; the empty-tick contract is untouched |
| **Evaluate** conditions 3–5 | the watchdog's **own `PeriodicTimer`**, at the publish interval's order — not at 100 ms | a handful of comparisons per line per second |

⚠ **The interlock flag is written on the watchdog's thread and read on the loop's**, once per
candidate reading inside `PersistAsync`. A plain `Dictionary` mutated on one thread while
another reads it is a genuine race, not a theoretical one — use a
`ConcurrentDictionary<LineId, bool>` or three volatile fields. *Line-scoped* and
*thread-safe* are two requirements and the build order used to state only the first.

⚠ **FL2 keys on footage and is not blocked by its own contract.** `[SIG §5.3]` suppresses
FL2's gauge and width — `null` on every FL2 reading, by design. **Footage is not suppressed**
(`FL2.TKUP2.Footage`), and the watchdog reads footage only. A watchdog widened to "any
missing measure" blocks FL2 permanently the moment it is switched on.

### 2.3 The gate on `RunReading` — **built; swap the stub**

*"While set, no rolling data is recorded without an active coil."* The interlock therefore
sits **inside `FW-150`'s broadcast loop, immediately before it persists `RunReading`** — not
around the whole loop and not at the API boundary. Telemetry continues to broadcast;
**persistence** is what stops.

✅ **The call site exists.** `BroadcastLoopService.IsRunBlocked(LineId)` returns `false`
today, with a comment reserving it for this story and forbidding a local interlock. It sits
in `PersistAsync` between the null/negative footage filter and the `FR-018` footage gate.
**This story publishes the interface and replaces that body.** Do not move the gate, do not
widen it around the send, and do not add a second one.

⚠ **It is `private static`, so the swap is not quite one line:** it becomes an instance
method and `BroadcastLoopService` gains an **eighth constructor parameter**. That constructor
is exactly where a wrongly-scoped registration fails at boot — see `P-131`.

## 3. Build order

0. **Settle `G59`'s audit half first** (`P-127`) — a service `OperatorId` or a sentinel.
   `PlcWriteContext` requires one and `AuditEntry.OperatorId` is non-optional, so the first
   set cannot be written without an answer. The token half can wait for commissioning.
1. **`ITInhibitService`** in `FlatWire.Infrastructure`, behind an interface in
   `FlatWire.Domain/Services/` (the convention every sibling follows), **registered
   `AddSingleton`** and resolving `IPLCTagService` **through `IServiceScopeFactory`, one scope
   per edge write** (`P-131`) — never by constructor injection. The call is
   `SetITInhibitAsync(new ITInhibitRequest(new PlcWriteContext(line, operatorId, runAlpha), set), ct)`
   — one boolean per line, written, never read. ⚠ **Zero confirm reads**; a `ReadTag` on the
   interlock path is a defect, and `Unconfirmed` is the best this operation can report.
2. **One shared watchdog** on its **own `PeriodicTimer`**, reading the per-line stamps
   `FW-150`'s drain leaves (§2.2), evaluating conditions 3–5 per line. **Only condition 3
   needs a new config key** — condition 5's threshold is `3 × PublishIntervalMs` and
   condition 4 needs none. ⛔ **The key goes at the `FlatWireOpc` root, not in `Tags`**, which
   is `Dictionary<string, string>` mapping logical name → path; a number does not typecheck
   there. *(The card's "inside each line's `Tags` block" rule is about the **tag path** and
   still holds.)*
3. **Line-scoped AND thread-safe state** — a `ConcurrentDictionary<LineId, bool>` or three
   volatile fields, never a single flag and never a plain `Dictionary` (§2.2). `TC-017a`
   catches the shared-flag error; nothing catches the race but a production incident.
4. **Write on the EDGE only** (`P-127`) — set when a line transitions unblocked → blocked,
   clear on the reverse, and **never re-assert per tick**. A simulated set already emits four
   audit records; per-tick writes would put those on the 10 Hz path.
5. **Condition 5's alert pair** — `AlertRaised` on set, `AlertCleared` on clear, one shared
   `AlertType` (§2.1), severity **`Critical`** (the machine is being blocked), sent through
   the singleton `IFlatWireBroadcaster.Line(lineId)`. ⚠ **No `AlertType` constants class
   exists** — `AlertRaisedEvent.AlertType` is a bare `string` and `AlertClearedEvent` joins on
   it. Add one constant beside `TagNames` in `FlatWire.Domain/Constants/`; do not write the
   literal twice.
6. **The `RunReading` gate** — make `BroadcastLoopService.IsRunBlocked` an instance method and
   replace its body with a call into this service (§2.3), adding the constructor parameter.
   Nothing else in that loop changes, and **the stamp from step 2 goes in the same edit**.
7. ✅ **Config surface for three lines — already built and boot-asserted** by `FW-144` (§1.1).
   Honour it; do not narrow it to two.
8. **Audit every set and clear** — tag path, value, timestamp, result — which `PLCTagService`
   already does on this story's behalf, including under `SimulatePLCTagPush`, because the
   audit runs *before* the simulate branch returns. Nothing to add here beyond the identity
   from step 0.
9. **Add no clear path.** See `P-25`.

## 4. Decisions this plan makes

> `P-##` is continuous across this folder. The series ran to **`P-126`**; this story owns
> `P-25`/`P-26` from first issue and **`P-127`–`P-132`**, so the folder now mints at
> **`P-133`+**. ⚠ **Each decision names the reading it rejects**, because on this story the
> intuitive reading is twice the wrong one.

### `P-25` — the absent clear path is a deliverable, and it needs a guard

The requirement is *"clears automatically only … enforced by the **absence** of any
endpoint, command or hub method."* An absence cannot be unit-tested, and with backend tests
withdrawn (`[TS §1.2]`) nothing mechanical protects it. `TC-016` is a **manual** sweep of
every UI surface.

**So make the absence visible rather than incidental:**

- **No `ITInhibitController`**, no MediatR command, no hub method — and a comment at the
  service saying why, citing `TC-016`, so the next developer reads it before adding one.
- **`SetITInhibit` is `internal` to the service's own call path** where the language allows,
  so a handler cannot reach it.
- Add it to `FW-138`'s **QA0 checklist** (item 7) as a review item, since that is the only
  verification this layer has.

**A reset button is the failure mode this story exists to prevent.** It will look like a
helpful addition to whoever writes it.

### `P-26` — build the surface for three lines, the behaviour for two

Per §1.1. `FL1` and `FL2` behave now; `FL3` is configured and inert until `G30` decides
whether it carries its own tag or asserts the other two together. **Do not collapse the
config to two lines** — exit criterion 5 names three, and re-widening later touches every
environment file. ✅ **Now enforced in code**: `Program.cs` throws at boot if any of the three
is missing, quoting this decision.

### `P-127` — `G59` splits in two, and only one half waits for commissioning

`G59` reads as one blocker on an unbuilt integration. Against the built `PLCTagService` it is
two, with different due dates — and reading it as one is how the near half gets missed.

| Half | When it bites | Why |
|---|---|---|
| **The bearer token** | **At commissioning**, when `SimulatePLCTagPush` goes `false` | The simulate branch returns **before `GetOPCInfo`** — no HTTP call, so no `HttpContext` to lack. `G60` is behind the same door |
| **The audit `OperatorId`** | ⛔ **On the first set, in every environment** | The `Attempted` record is written **before** that branch (`[PLC §11.1]` audits simulated writes too) and `AuditEntry.OperatorId` is required — *"an unattributable audit record has no compliance value"* |

**So the identity question must be answered before this story is written, but only its
cheaper half.** A service badge via the `Login` service is `CoolingChamber`'s precedent and
answers both at once; a sentinel `OperatorId` answers the near half alone and leaves the
token to commissioning. **Either is acceptable; silence is not** — a `PlcWriteContext` needs
a string, and whatever a developer invents under deadline becomes the audit trail.

**And the write is edge-triggered, which is the same decision seen from the performance
side.** One simulated set emits four audit records. Re-asserting the tag on every watchdog
evaluation would multiply that by the tick rate for as long as a line stays blocked — on the
one operation whose audit trail is the evidence that it engaged.

### `P-128` — condition 4 is a **negative** footage, and nothing else

⛔ **The reading to reject, because it is the intuitive one: that a footage *decrease* is
invalid data.** It would set `ITInhibit` on **every new run**. The built loop reads the
identical input the opposite way and says so in a comment at the point it handles one — *"a
footage counter that went **BACKWARDS** is a new run or a counter reset, not a reading inside
the spacing"* — so it **records** the row and drops the cached run so the next reading
re-resolves it. **A counter reset at check-in is the normal course of a shift.**

**So condition 4 is a negative footage.** `RunReading.FootageFt` is `CHECK >= 0` — the
schema already says a value below zero is not a footage — and on the built `Reading`,
`FootageFt` is `decimal?`, so nothing else is representable. `null` and silence are
**condition 3**; a decrease has a documented meaning already and it is not "invalid".

⚠ **Ours to define, not a client question.** What is worth confirming at `C7` is whether the
controller's counter can ever go negative at all. If it cannot, condition 4 is unreachable in
practice — which is a finding, not a defect, and `TC-014` is where it would surface.

### `P-129` — the loop **stamps**, the watchdog **evaluates on its own timer**

Two readings to reject, and they fail for opposite reasons.

⛔ **The watchdog must not open its own reader.** `ReadingChannel` is **`SingleReader = true`**
with exactly one drain loop, so a second consumer is not blocked and does not throw — it
**splits the stream**, and the broadcast loop silently receives a fraction of the snapshots.
Thin DB3 traces and missing `RunReading` rows, neither pointing at the interlock.

⛔ **And it must not evaluate on the drain either.** *"Once per drained snapshot"* is a
callback that fires **on arrival**, and **conditions 3 and 5 are absence conditions** — an
absence never fires it. Worse, `TickAsync` **returns early on an empty tick** — *"at a 1 s
publish interval this is nine ticks in ten per line, and it must cost nothing"* — so there is
no call to hang the evaluation on even if one wanted to.

**So the two halves separate**, and the split is what keeps both contracts intact:

- **The loop stamps.** After the empty-tick return, once per line in the batch, record
  last-seen `(ReadAt, FootageFt)`. ≤ 3 dictionary writes per tick, no allocation, no scope,
  no query — `FW-150`'s hot-path contract is untouched.
- **The watchdog evaluates**, on its own `PeriodicTimer` at the publish interval's order.
  Absence detection needs a clock.

**The rejected alternative** — a second bounded channel fanned out from the ingest — buys
isolation this story does not need and adds a buffer that can itself fall behind, which would
have the interlock evaluating stale footage.

### `P-130` — all three conditions watch the **feed**, never `RunReading` rows

*"Two or more consecutive data **recordings** are missing"* reads as though it counts
`RunReading` rows. **It cannot**, and the reason is a `Must` that landed after `[PLC §8]` was
written: `FR-018` gates the write on **footage**, not on time, so rows arrive at
`(FPM ÷ 60) ÷ spacing` — about 1.25 a second at 300 FPM and 4 ft, fewer as the line slows,
and **none at all on a paused or stopped line, correctly**.

Two consequences, and the first is disqualifying:

- **A legitimate pause would set the interlock** and raise a `Critical` data-recording alert
  on a line an operator deliberately stopped. `FW-170`'s pause is a normal state with its own
  event table; blocking the machine for entering it is the opposite of the requirement.
- **There is no period to measure "missing" against.** The expected interval between rows is
  a function of line speed, so "two consecutive" has no fixed meaning.

**So condition 5 is ≥ 3 × `PublishIntervalMs` of silence on the feed, and condition 3 is
sustained silence** — the same measurement at two thresholds, which is why the card describes
conditions 3–5 as *one shared watchdog* rather than three. It also means the watchdog needs
**no run state at all**, which matters: the only run state available is `FW-150`'s
`RunContext` cache, whose lifecycle invalidation is that story's known unwired loose end.

⚠ **This is the one reading on this story worth putting in front of the client**, because it
changes behaviour materially and `[PLC §8.2]`'s wording genuinely admits both. It goes on the
`C7` sheet with `P-128`'s question.

⛔ **The threshold is 3 × the interval, not 2 × — corrected on the build, where 2 × blocked a
healthy machine.** Publishes fall due at `t+1`, `t+2`, `t+3`…, so a gap of **two** intervals
means the reading at `t+1` is missing and the one at `t+2` is due *this instant* — that is
**one** missing, and the condition says two or more. A gap of three means `t+1` and `t+2` both
failed to arrive.

**Measured, not reasoned.** At 2 ×, the interlock **set on FL1 four seconds after boot against a
perfectly healthy feed** and cleared a second later, because the first publish came in behind
startup work. At a 1 s publish a 2 s threshold leaves **zero jitter margin** — one slow poll or
one GC pause blocks a running line, on the mechanism whose entire purpose is to stop production
the system cannot account for. 3 × leaves a full interval, and condition 3's floor moves to
**4 ×** so the two stay ordered however they are configured.

### `P-132` — a line is **unarmed until its first reading**, or the interlock blocks a system that has not started

⛔ **Found by executing it.** With no publisher on the channel — `FW-N05` deferred, `FW-203`
unbuilt — a watchdog that treats *"never seen a reading"* as *"stopped seeing readings"*
blocks **both lines within two seconds of boot, in every environment**, raising a `Critical`
alert on every developer's machine and gating `FW-150`'s `RunReading` persistence: the very
thing the trial exists to demonstrate.

**So each line arms on its first sighting.** Until a line has delivered one snapshot, `Assess`
returns `None` and the interlock stays clear. A line that has delivered nothing has not
*stopped* delivering — it has not started.

**This is not a hole in the interlock.** Conditions **1 and 2** — *no coil or rod checked in*,
*no active material-tracking identifier* — are what guard a line with nothing running on it,
and they are `FW-206`'s in Phase 4. **This watchdog guards a feed that FAILED**, which is a
different claim and needs a baseline to fail from. The startup log states the unarmed state by
name so it is visible rather than inferred.

⚠ **`FW-206` should not re-derive this.** When conditions 1–2 arrive they will block an idle
line on their own terms, and the two must not double-block or fight over the same tag.

### `P-131` — singleton service, scoped write, and the gate stops being `static`

⛔ **`IPLCTagService` is registered `AddScoped`; a watchdog is an `IHostedService`, which is a
singleton.** Injecting it directly is a captive dependency: the host's default scope
validation **throws at startup in Development**, and in Production — where validation is off —
it silently captures a scoped `PLCTagService`, its scoped `IAuditLog` and its `DbContext` for
the process lifetime. **The environment nobody watches is the one where it appears to work.**

`OpcIngestService` is the precedent and it is in this same folder's scope: it takes
`IServiceScopeFactory` and calls `CreateScope()` per operation. **Do the same, one scope per
edge write** — which `P-127` already made rare, so the cost is nil. The scope must wrap the
whole `SetITInhibitAsync` call, because `IAuditLog` is scoped too and the audit happens inside it.

**And `ITInhibitService` itself is a singleton**, because `BroadcastLoopService` — also a
singleton — injects it to read the gate. That read is on the 10 Hz path and must stay a
dictionary lookup: **never open a scope to answer `IsRunBlocked`.**

⚠ `IsRunBlocked` is `private static` today, so this is where the story touches
`BroadcastLoopService`'s constructor. **If the registration is wrong, that is the line the
host fails on** — and it fails at boot, by name, which is the good outcome.

## 5. Verification

**No automated tests** — `[TS §1.2]`. These are **QA-owned P1 cases**, unaffected by the

| Case | Asserts |
|---|---|
| **`TC-013`** | Condition 3 — feet data unavailable |
| **`TC-014`** | Condition 4 — feet data invalid |
| **`TC-015`** | Condition 5 — two or more consecutive recordings missing |
