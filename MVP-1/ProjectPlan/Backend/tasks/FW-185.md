## 2. The five details

### 2.1 ⛔ `OI-104` — the 2-per-skid rule has no skid

AC 5 enforces **2 coils per skid**. `CoilOutput` carries `SkidId`, `SkidStatus` and
`StagingLocation` — but ⛔ **`SkidId` has no target table** (`OI-104`).

⚠ **So "2 per skid" is enforceable only as a count over `CoilOutput` rows sharing a `SkidId`
string.** That works, and it has two consequences worth stating:

- **There is no skid lifecycle** — nothing creates, closes or lists a skid except by aggregation.
- ⛔ **`FW-187` AC 2 broadcasts *"skid closed → packing-queue update"***, which needs a skid
  state. **Derived from the count**, it is *"two coils exist with this `SkidId`"* — which is not
  the same as an operator closing a part-full skid.

⚠ **`G49`'s B1 compounds it**: there is **no slot / position-on-skid column**, so *"1-of-2 versus
2-of-2"* is **unrecordable**. [`FW-244`](../../Database/tasks/FW-244.md)
supplies it.

### 2.2 The certificate is the reason this phase is MVP-1

Phase 9 returned to MVP-1 on 11 Aug 2026 **because the coil genealogy behind the welding-wire
customer certificates is an MVP-1 obligation** (`NFR012`).

⛔ **So `sourceTraceability[]` is not a reporting nicety** — it is the deliverable a customer
receives. The rule *"no coil exists without its traceability"* in the user story is therefore a
**transactional** requirement, not an aspiration: alpha, genealogy and skid close in **one
transaction**.

⚠ **And the genealogy's integrity rests on an aggregate rule, not a trigger.**
`SpoolTraceability`'s footage bounds are **nullable** because the genealogy is weight-primary, so
a non-overlap trigger joining on `NULL` **passes silently** — which is why 22 Aug added none and
why `SpoolSegmentsMustNotOverlapRule` is *"the ONLY defence"*.

### 2.3 The snapshot is for a future MVP-1 does not have

AC 6: *"the pass-schedule id **+ snapshot** is written to the coil record so a certificate stays
reproducible after the schedule is later edited."*

⚠ **MVP-1 never edits a pass schedule** — it never authors one at all (`OI-110`, `P-13`), and
`PassScheduleChangeLog` has no write path. **So nothing in MVP-1 can invalidate the reference.**

⛔ **Build the snapshot anyway.** The certificate outlives MVP-1, the schedule-authoring track
exists separately, and a certificate that de-references a mutable row is wrong the moment that
track ships. ⚠ **`FW-207` already built a `PassScheduleSnapshot` quantity** — use it rather than
inventing a second shape.

**This is the same immutability principle as [`FW-228`](FW-228.md)'s
basis + factor + version and [`FW-225`](FW-225.md)'s
consumption snapshot. Three stories, one rule.**

### 2.4 `Q10` blocks the weight, and the reserve is real

*"Footage→weight via the alloy factor"* — and `AlloyProperty.LbPerFtFactor` is seeded `NULL`.

⛔ **`Q10` is `Critical` on this card** and `[CE §2]`'s **16–32 h reserve applies to Phase 9**.
Consume [`FW-228`](FW-228.md); ⛔ **do not reimplement the formula.**

⚠ **`P-206`'s rule applies to the caller too**: an unresolvable factor returns **unknown**, and
this service must not write `0` as a coil weight or print one on a label.

### 2.5 `finalSpc` and the in-spec columns are already nullable — keep them that way

AC 1 returns `finalSpc`; AC 5 asks for *"gauge/width target-when-in-tolerance"*.
`CoilOutput.GaugeInSpec` and `WidthInSpec` are **`BIT NULL`**, commented *"NULL until
evaluated"* — the **correct** pattern, and the one
[`FW-245`](../../Database/tasks/FW-245.md) is
fixing one table down.

⛔ **`SpcMeasurement.InSpec` currently stores a WRONG verdict for an asymmetric band** (`G51`), so
a final-SPC roll-up reading it inherits the error. ⚠ **Sequence `FW-245` first**, or the
certificate's in-spec claim is computed from a symmetric approximation.

## 3. Build order

1. ⛔ **`Q10`** (§2.4) and ⛔ **`OI-104`** (§2.1) — the weight and the skid.
2. ⚠ **Sequence [`FW-245`](../../Database/tasks/FW-245.md)

3. `CompleteCoil` handler on the built `CoilController`; `GetCoilLabel` handler.
4. `CoilCompletionService`, **one transaction**: alpha → genealogy from **weld boundaries** →
   weight via `FW-228` → 2-per-skid → mark the run complete.

5. **Write the pass-schedule id + `PassScheduleSnapshot`** (§2.3).

   [`FW-235`](FW-235.md) owns that.
8. **Operator+ authorization** — ⚠ `FW-145` is unbuilt, so no role claim is issued today.

## 4. Decisions this plan makes

> `P-##` is continuous across the repository; `P-01`–`P-241` precede this story.

### `P-242` — the skid is a derived grouping until `OI-104`, and the derivation is documented

§2.1. `SkidId` has no parent, so *"2 per skid"* is a count over `CoilOutput`. ⛔ **That means
there is no operator-closed skid**, which `FW-187` AC 2 assumes — so the two stories must agree
on what "closed" means before either ships.

**Fallback:** if `OI-104` yields a skid table, the count rule becomes a constraint and
`FW-187`'s broadcast gains a real state change.

### `P-243` — the pass-schedule snapshot is built even though MVP-1 cannot invalidate the reference

§2.3. The certificate outlives MVP-1 and the authoring track ships separately. **Reuse
`FW-207`'s `PassScheduleSnapshot`**, do not invent a second shape.

### `P-244` — an unresolvable weight is never written or printed as zero

§2.4, applying `P-206` at the consumer. A coil label bearing `0 lb` is worse than one bearing a
blank, because it looks like a measurement.
