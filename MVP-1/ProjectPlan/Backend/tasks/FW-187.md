## 2. The four details

### 2.1 ⛔ AC 1 cannot reach Dashboard 1 until `C2`

*"`LineStatus` → IDLE on completion, reaching Dashboard 1."*

`TryMapLineState` returns `false` until commissioning test `C2`. The consequences are already
recorded across three stories:

- [`FW-150`](FW-150.md) is **silent on `LineStatus`** pre-`C2`.
- [`FW-154`](FW-154.md)'s `P-181` requires the snapshot to
  report **unknown**, never a fabricated state.
- [`FW-202`](FW-202.md)'s `P-223` refuses to promote speed ≈ 0 to a trigger
  for the same reason.

⚠ **But this story is different from those three**, and the difference is worth stating: **a
completion is a fact this service knows.** `FW-150` cannot map a *machine* state word; this
handler is told by its own transaction that the run completed.

✅ **So AC 1 is buildable** — the server may assert IDLE on completion without reading
`FL{n}.LineState`. ⛔ **What it must not do is contradict the stream**: `FW-150` will keep sending
nothing, and `FW-154`'s snapshot will keep saying unknown. **Three sources, one field** — the same
problem `P-181` names, now with a third source.

⚠ **And DB1 left MVP-1 scope**, so *"reaching Dashboard 1"* has no MVP-1 screen behind it.

### 2.2 ⛔ AC 2's "skid closed" is a derived count, not an event

`SkidId` has **no target table** (`OI-104`), so there is no skid entity to close. `P-242` records
what remains: *"2 per skid"* is a **count over `CoilOutput` rows sharing a `SkidId`**.

⚠ **So "skid closed" can only mean "a second coil now shares this `SkidId`"** — which is:

- ⛔ **not** an operator closing a part-full skid (a real workflow, per `G49` B1's *1-of-2 vs
  2-of-2*), and
- ⛔ **not distinguishable** from it, because **no slot column exists** to say which position was
  filled.

**So the broadcast can honestly announce "this skid now has two coils" and nothing more.**
⚠ **`FW-244`'s B1 changes that**, and until then the payload should not imply a skid *state*.

### 2.3 Three broadcasts, one action

On one completion: `LineStatus` → IDLE, the packing-queue update, and **`CoilCompleted`**
([`FW-235`](FW-235.md), if `OI-140` says yes).

⚠ **They are genuinely different facts** and a client must not render three notifications for one
event. ⛔ **Neither story can see this alone** — `P-246` makes the moment a joint design, and this
plan restates it because the two stories are in different batches and may be built by different
people.

### 2.4 Unbatched is a delivery guarantee

AC 3. Same reasoning as [`FW-160`](FW-160.md) §2.2 and
[`FW-N06`](FW-N06.md) §2.3: `FW-150`'s loop is **decimated and newest-wins**
for scalars and **sends nothing on an empty tick**.

⛔ **A completion arriving on a tick with no readings would never be sent at all** — and a
completion is precisely the moment readings stop.

**That last point is the sharp one**: the line has just gone idle, so the telemetry loop is at its
quietest exactly when this event fires.

## 3. Build order

1. ⚠ **Reconcile with [`FW-235`](FW-235.md)** on what the
   completion moment emits (§2.3, `P-246`) — **before** either payload is published.
2. ⚠ **Confirm a packing-queue member exists** among `IFlatWireClient`'s 20; if not, adding one is
   **breaking under `[API §8]`** and belongs in `FW-235`'s single pass, not a second one.
3. **AC 1**: assert `LineStatus` → IDLE from the completion transaction (§2.1), **not** from
   `TryMapLineState`. ⛔ **Record that it must not contradict `FW-150`'s silence or `FW-154`'s
   unknown.**
4. **AC 2**: broadcast the derived skid fact (§2.2) — ⛔ **do not imply an operator-closed skid**
   or a slot position.
5. **Unbatched**, through `IFlatWireBroadcaster`, on `FW-208`'s post-commit lane (§2.4).
   ⛔ **Never `IHubContext<>`** (`P-101`).
6. ⚠ **Post-commit only** — a broadcast before the transaction commits would announce a completion
   a rollback then undoes. `FW-208`'s lane already guarantees this, and `P-138` guards a throwing
   broadcast.

## 4. Decisions this plan makes

> `P-##` is continuous across the repository; `P-01`–`P-246` precede this story.

### `P-247` — the completion may assert IDLE, and the three `LineStatus` sources must be reconciled

§2.1. This service **knows** the run completed; it is not inferring a machine state. So AC 1 is
buildable pre-`C2`.

⛔ **But `LineStatus` now has three writers** — this broadcast, `FW-150`'s stream (silent) and
`FW-154`'s snapshot (unknown). **`P-181` required two to agree; this makes it three.**

**Fallback:** if the reconciliation is not settled, **hold AC 1** rather than adding a third
disagreeing source. A board that flips to IDLE and is then contradicted by the next snapshot is
worse than one that does not flip.

### `P-248` — the skid broadcast announces a count, not a state, until `G49` B1 lands

§2.2. Without a slot column there is no *1-of-2 versus 2-of-2*, and without a skid table there is
no close. ⛔ **A payload implying either would be unfillable** — `P-245`'s rule.
