## 2. The four details

### 2.1 ⛔ Do not re-derive the arming rule — `P-132`

`FW-205` owns **how the interlock arms and clears**. This story adds **two inputs to that
evaluation**, not a second evaluation.

The failure mode if ignored is nasty and quiet: two evaluators both decide the line should be
inhibited and both write the tag. **The second write is invisible** — the tag is already set —
so nothing looks wrong until one evaluator's condition clears, writes `false`, and the other
still believes it should be `true`. Depending on ordering the line is then either **inhibited
with nothing explaining why**, or **released while a condition still holds**.

⛔ **AC 3 says it outright: "no second write path."** One evaluation, one writer, two more
inputs.

### 2.2 Condition 2's subject does not exist yet

`PLC-Q12` is not a detail — the *"active material-tracking identifier"* has **no specified
format**, and **whether it is the same identity as the run is unresolved**.

That second part is the load-bearing half. If it **is** the run, condition 2 is nearly free —
`FlatWireRun` has a status and `UX_FlatWireRun_ActiveLine` already enforces one active run per
line. If it is **not** the run, it is a separate concept with its own lifecycle, its own
orphaning behaviour, and probably its own storage.

⛔ **The two readings produce different stories at different sizes.** Do not build against a
guess; the 8 h is priced for the first reading.

### 2.3 Condition 1 is buildable now, and can ship without condition 2

*"No coil or rod is checked in on the line"* is answerable from state that exists: `RodStaging`
and `RodCheckin` are built, and `FW-157`/`FW-061` own the check-in that populates them.

⚠ **`RodStaging` is FL1/FL3 only** — `FW-150` already had to handle this, and FL2 sends no
payoff weight for the same reason. **FL2 checks in a spool**, so condition 1 on FL2 reads
`SpoolCheckin`, not `RodStaging`. **A single query shape will not serve all three lines.**

**So split the delivery**: condition 1 now, condition 2 when `PLC-Q12` closes. The card treats
them as one story; the blocker only touches one of them.

### 2.4 The runbook step is a deliverable

AC 4 covers the reconciliation step for an **orphaned identifier**, which `[PLC §8.4]` names the
most common cause after an interrupted transaction.

⚠ **This is where `G2`'s narrowing matters.** `[ARC §10]`/`FR-526` made the two database halves
one transaction, so the interrupted-transaction case is **narrower than `[PLC §8.4]` assumed** —
but not gone: a PLC write is still not transactional (`G2`), and compensation is a re-clear,
never a rollback.

**The runbook step must reflect the narrowed case**, not the original.

## 4. Decisions this plan makes

> `P-##` is continuous across the repository; `P-01`–`P-178` precede this story.

### `P-179` — condition 1 ships without condition 2

§2.3. `PLC-Q12` blocks only condition 2, and holding condition 1 back means the interlock
enforces three of five when it could enforce four — with no compensating benefit.

⚠ **Record the partial state explicitly**, as `FW-205` recorded its inert interlock. *"Four of
five conditions"* is a defensible position; *"we thought all five were on"* is not.

**Fallback:** if `[PLC]` requires all five to arrive together, condition 1 still builds and sits
behind a flag — but the flag is then a thing to remember, which is why this is not the default.

### `P-180` — condition 1's source is per line, not one query

§2.3. `RodStaging` is FL1/FL3 only; FL2 checks in a spool. A single *"is anything checked in"*
query would read FL2 as permanently uninhibited or permanently inhibited depending on which
table it read.

⚠ **Same class as `FW-150`'s FL2 payoff-weight branch** — the line asymmetry is real and recurs.
