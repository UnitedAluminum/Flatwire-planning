## 2. The three rules that shape the code

### 2.1 The real ingest is not modified — that is the whole test

AC 2 is the story's purpose: E2E must exercise the **real** path rather than bypass it. The moment
`OpcIngestService` gains a branch, a flag or a test hook, the thing under test is no longer the thing
that ships. **The double is selected by configuration outside it**, exactly as `AddFlatWireOpcIngest`
already selects between the simulator and the real ingest.

### 2.2 Never the production OPC servers

`[PLC §5.3]` A5. The double is test-only, and it must be impossible to point a commissioned
environment at it by accident — the same *"absent, not forbidden"* posture `[SIM §2.4]` takes with
`/sim`.

### 2.3 No tag path is written anywhere but configuration

`[PLC]` owns **every** tag path string — CLAUDE.md's one-home rule, and the reason six copies of the
tag surface once existed. The double answers from the **bound path map** and hard-codes nothing.

## 4. Decisions this plan makes

> `P-##` is continuous across this folder; `P-01`–`P-294` precede this story.

### `P-295` — the double sits at the HTTP seam `FW-N05` actually uses, not at an OPC UA endpoint

Per §1.2. `FW-N05` reads `OPCConnection/GetOPCInfo` and `OPCConnection/ReadTag` over HTTP and has no
OPC namespace in the file. **An OPC UA server would be connected to nothing**, so AC 1 as written and
AC 2 as written are mutually unsatisfiable, and AC 2 is the one that carries the story's purpose.

**Three things this buys, and they are the argument:**
- **No new package.** There is **no `Opc.Ua.Server` package in `ual-api`** — the four OPC Foundation
  packages present are client-side and belong to another service — so the literal reading needs a new
  dependency, against CLAUDE.md's *"stay within the existing UAL stack — no new frameworks"*.
- **`OPCConnection` is untouched**, which `[ARC §2.2]` requires: it is the layer to **integrate with**,
  not to rebuild or to fork a server into.
- **It is smaller.** Two routes and a mapping, against a server host, a certificate story and a
  three-process topology.

⛔ **`[SIM §3.1]`, `[SIM §3.3]` and `[TS §3.1]` all say *"OPC server sidecar"* and all three are owed
an amendment.** This plan raises it and makes none — §7. **Fallback:** if the client or QA require a
genuine OPC endpoint for commissioning rehearsal, that is the larger story above, and it should be
sized as one rather than absorbed into this 24 h.

### `P-296` — selected by configuration alongside the existing branches; `IReadingSource` stays unminted

`P-265` established that the seam is `AddFlatWireOpcIngest`'s `if`/`else` and that the sketched
interface would re-declare `IHostedService.StartAsync`. **That holds here.** The double is not a third
`IReadingSource` implementation, because there is no such type — it is a configuration-selected host
that `FW-N05` reads from, with `FW-N05` registered exactly as in production.

⚠ **A reader arriving at `[SIM §3.1]`'s diagram cold will believe `IReadingSource` exists**, because
the diagram draws it. `P-265` already records the amendment as owed; this decision is the second story
to depend on it.

### `P-297` — the double re-hosts the same `ILineModel` instances and mints no snapshot type

`[SIM §3.1]`'s *"the physics is written once"* is the one part of the card that survives intact, and
it is satisfied by **hosting**, not by porting. `Tick` returns `Reading` — `P-268` declined
`LineModelSnapshot` — so the mapping is `Reading` → the tag values `ReadTag` returns, and **no second
model, no second snapshot type and no second noise generator** is created (`P-288`).

### `P-298` — no tag path string is written in the double; it answers from the bound path map

`[PLC]` owns every path. The double resolves a requested tag against the same configuration `FW-144`
binds — 72 paths measured on the deployed configuration — so a correction under `G32` / `G33` is one
config edit that moves both sides together.

⛔ **The consequence for what this story proves:** the paths are `[PROPOSED]` throughout, so a double
that serves them proves the **pipeline**, never the **map**. `[SIM §10]` says exactly this, and the
pass condition is therefore that `FW-N05` runs **unmodified**, not that any path is correct. Path
correctness is `C1` and `C11`, in the commissioning window.

### `P-302` — the double is mapped INSIDE `FlatWire.API`, not built as a separate host *(minted by the build)*

The plan said *"a minimal HTTP host"* and left where it lives open. **It lives in the service under
test, at `api/v1/OPCConnection`, and the plan's own step 4 is what decides it** — *"only its
`OPCConnection` base address differs"*. Two reasons, and both are `P-298`'s:

- **ONE configuration source.** `P-298` requires that a correction under `G32` / `G33` be *one* edit
  moving both sides together. A separate process carries **its own copy of the 72-path map**, and a
  copy is a second home for the fact `FR-022` exists to keep in one place.
- **No second deployable, no second seeded environment, no third process in the test topology.** The
  fixture becomes a *configuration state* of the service under test, which is what makes *"`FW-N05` is
  registered exactly as in production"* literally rather than approximately true.

⚠ **The consequence to accept:** the ingest's HTTP hop is a loopback to its own host. That is a
property of the **fixture**, not of the path under test — the ingest still resolves an `OPCInfo`, still
batches, still posts, still parses the `ActionResultBase` envelope, and is byte-identical while doing
it. ⚠ **The route prefix is the CLIENT's and not a choice:** both callers hold
`"OPCConnection/GetOPCInfo"` as a route constant and `RestClient.WithRoute` appends it to an endpoint
ending in `/api/v1/`, so the group reproduces the real controller's `[Route("api/v1/[controller]")]`
exactly. Those two route strings are now a **third** copy of a string `OpcIngestService` and
`PLCTagService` already share; keep the three in step.

### `P-303` — one read advances one line by one tick of the CONFIGURED interval; the reader is the clock *(minted by the build)*

The plan did not say what drives the models behind the double, and the intuitive answers — a background
timer, or the measured elapsed time between reads — are wrong twice over.

- **`OpcFeedSimulator` passes the FIXED interval to `Tick`**, so passing the same thing is what makes
  the trace through this route **identical to the in-process adapter's for the same seed**. That is
  §5's own verification row. Measured elapsed would put clock jitter inside a fixture whose entire
  value is reproducibility. ✅ **Measured: two fresh processes, identical over 10 ticks × 7 tags.**
- **A reader that stops reading FREEZES the line** rather than letting it run on unseen — which is what
  is wanted of a fixture, and is the same choice `Tick` already makes for a comms drop.

⚠ **So the double needs no `IHostedService` and no second cadence knob.** It is a concrete singleton
that answers requests and **publishes nothing** — which is why `P-134`'s one-publisher rule is
untouched: with the double on there is still exactly one publisher, and it is `FW-N05`'s real ingest.
⚠ A per-line lock serialises `Tick`, because `ILineModel` is not documented thread-safe and the ingest's
one-loop-per-line shape is a property of the caller rather than a guarantee.

### `P-304` — a silent tick answers 503; never a 200 carrying nulls *(minted by the build)*

`Tick` returning `null` is **silence** — a comms drop — and `ILineModel` is emphatic that this is *not*
a reading whose fields are null. **On an HTTP transport, silence is a read that did not complete**, so
the double answers `503`. The ingest's `ReadAsync` then branches on `StatusCode != OK`, returns null and
**writes nothing to the channel** — which is exactly the gap between sightings `FW-205`'s watchdog
measures.

⛔ **The alternative would have broken the watchdog quietly.** A 200 carrying every value null makes the
ingest publish a snapshot with null footage — *a live feed reporting nothing* — which the codebase names
as **a different fault entirely**. ⚠ 503 is also not retried: the ingest's Polly policy handles
`Result.IsFailure`, a call that never completed, so **one drop costs exactly one tick**.

### `P-305` — the double answers null where a line's model has no instrument, and invents no fallback *(minted by the build)*

Building the projection surfaced a real hole, and it is the **tag map's** rather than the model's.
`Fl2LineModel` reports its single load cell at **`PayoffPosition.TraversingTakeup`**; the tag surface
carries only `Payoff1Weight` and `Payoff2Weight`, which the ingest lands on `Payoff1` / `Payoff2`. So
`FL2.Payoff1.Weight` answers **null** through the double.

**Making that arm fall back to *"the line's only load cell"* was rejected.** It would invent a mapping
the tag surface does not have, and inventing one is how a fixture comes to prove something the real path
cannot do — the fixture's job is to expose that divergence, not to smooth it. Raised as **`G71`**.

⚠ **The same rule governs every other null the double returns, and they are structural facts rather
than gaps:** `ITInhibit` is written and never read (`[PLC §8.1]`); no FM2 stand or die block has a fault

deliberately: that is the shape `G33` warns about — *a wrong path fails silently* — and a fixture that
shouted about it would hide the failure mode commissioning exists to find. Both sides log it once.
