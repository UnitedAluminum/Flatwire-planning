**The trap is that `GaugeOffsetIn` and `DriftPerTickIn` are command echo, not measurement.**
`Steer(line, gaugeOffsetIn, driftPerTickIn)` wrote both straight onto `LineSim`
(`OpcFeedSimulator.cs:163–164`, pre-build) and `Peek` read them back. ⚠ **Not *unchanged*, and the

that was deleted**.

This is the story's real design problem and the reason the work is not a mechanical swap. `P-267`
settles it.

## 2. The three rules that shape the code

⚠ **These three OUTLIVE the closure, and that is why this section is not struck.** [`FW-212`](FW-212.md),
[`FW-213`](FW-213.md), [`FW-215`](FW-215.md) and [`FW-217`](FW-217.md) are all still `has_plan: false`, and every one of them edits
the simulator or the surface over it. Until each has a plan of its own, this is the written guidance
they inherit — which is what the **Audience** line above promises.

### 2.1 Exactly one publisher, and the `if`/`else` is what enforces it

`P-134` holds unchanged. `FlatWireOpcOptions` states the rule in prose — *"exactly one publisher
may write to the bounded channel … registering both would double-write every tick, two snapshots
per line from alternating sources, and a gauge trace that looks like noise."*

The `if`/`else` in `AddFlatWireOpcIngest` makes that **unrepresentable**. **Do not add a second
flag** for the line models, and do not turn the branch into two independent registrations: a
second flag would leave double-writing as a deployment mistake nobody would diagnose from the
symptom.

### 2.2 Downstream must not be able to tell

`P-37` holds unchanged, and it is the reason `[TRP §1.4]` left `FW-150` and `FW-151` unreduced.
**If either grows a branch that can distinguish a modelled feed from the previous synthetic one,
the substitution has failed** and October's ingest drop-in is no longer a drop-in.

The concrete test: the `Reading` this story writes to the channel must stay **shape-identical**.
`FL2` still leaves `GaugeIn` and `WidthIn` **null** — never zero, never the target — and
`FW-150`'s existing *"no sample, no send"* rule does the rest, with **no branch on the line**.

### 2.3 `SimLineState` is neither widened nor redefined

`[SIM §9.2]`, and both halves bind. **Widened** is forbidden because the panels' speed, payoff
weight, percent remaining, gauge and width actuals, line state and run status come from
`[SIG §5.2]` events 1–7 over the hub. **Redefined** is forbidden by `P-267` — the fields keep the
meaning `FW-218` shipped and `FW-214` was designed against.

## 4. Decisions this plan makes

`P-265`–`P-267` are minted here and defined **once**, in this section.
[`Orchestration.md`](Orchestration.md) §4a carries pointers only.

### `P-265` — the seam is already built, and `IReadingSource` is not minted

**Settled.** `AddFlatWireOpcIngest`'s `if`/`else` over two `IHostedService` implementations
satisfies AC 2, 3, 4 and 5 exactly as the card words them: the same bounded channel at the same
cadence, selected by configuration rather than by call site, against a strongly-typed options
class validated at startup.

Declaring `IReadingSource { ValueTask StartAsync(CancellationToken ct); }` as `[SIM §3.2]` sketches
it would **re-declare `IHostedService.StartAsync` under a new name** and add a wrapper at every
registration site to adapt one to the other. `[SIM §2.1]` forbids that in terms — *the simulator
adds no interface of its own* — and the rule does not exempt the simulator's own seam.

**AC 1 is struck.** The interface's *purpose* — two implementations, neither aware of the other,
swapped by configuration — is met in full; only the named type is not created.

⚠ The card's own rate-card basis reads *"an interface, one implementation and options binding,
against a contract that already exists."* Two of those three were already built. **The 12 h was
re-aimed rather than reduced** — swapping the state machine and preserving a live control surface
is the harder half of the original estimate, not a leftover of it. ⚠ **That was the position at plan-writing
time, and the closure superseded it twice over**: the work reached steps 2–6, not two steps, and
where the hours now land is the re-baseline's call — §1.

### `P-266` — `OpcFeedSimulator` is extended in place, and keeps its type name

**Settled.** `SimControlSurface`'s four handlers take `OpcFeedSimulator` **concretely**
(`SimControlSurface.cs:132, 167, 193, 231`), and `FW-218` is `done`, `Critical`, S1 and the only
control surface the acceptance run has. Introducing an abstraction over the class, or renaming it
to something like `SimulationHost`, would edit a built and verified control surface for **no
behavioural gain**.

The name becomes mildly inaccurate once the class hosts line models rather than generating a feed.
**Document that on the class; do not churn it.** This follows `P-39`'s shape — `FW-218` is a
*subset* of `FW-215`, not a variant of it — and the same reasoning applies to the type it drives.

⚠ `OpcFeedSimulator` is registered **twice on purpose** — as a concrete singleton *and* as a hosted
service resolving that same instance — because `FW-218`'s endpoints steer that instance. Preserve
both registrations; collapsing them to one gives the endpoints a different object from the one
that is ticking.

### `P-267` — `SimLineState`'s steer fields stay COMMAND ECHO, not recomputed state

**Settled, and it reverses the obvious reading.** `GaugeOffsetIn`, `DriftPerTickIn` and
`DropTicksRemaining` report **what was asked for**, not what is observed. `Steer` writes its two
arguments onto the simulated line and `Peek` reads them back, so every field is a **commanded
quantity** — which is what lets `FW-214`'s console seed its controls to their current positions.

⚠ **"Echo" does not mean "frozen", and the difference is worth stating once.** `GaugeOffsetIn` is
the **running commanded bias**: the steer seeds it and the commanded drift advances it each tick, as
`LineSim` did at `OpcFeedSimulator.cs:374`. `DriftPerTickIn` and `DropTicksRemaining` are the
command verbatim and its countdown. So a steered line's `/sim/state` moves between ticks — it is not
idempotent — and that is correct, because what it echoes is *the commanded trajectory*, still never
a measurement.

**The values are therefore carried as commanded state and echoed as such.** Mapping `GaugeOffsetIn`
to actual-minus-target — the intuitive move once a real model exists — would silently change the
endpoint's meaning from *the commanded offset* to *the observed deviation*, under a console already
built against the first. Nothing would fail; the numbers would simply start meaning something else.
`[SIM §9.2]` uses the command vocabulary too, which is the independent confirmation.

✅ **As built** (`FW-210`), the commanded state lives on the model as `GaugeBiasIn` /
`DriftPerTickIn` and `Peek` projects it (`OpcFeedSimulator.cs:237`), rather than being retained
separately in the adapter. **The meaning is unchanged, which is all this decision governs**; where
the commanded values are stored is not.

**The record is preserved, never widened.** Speed, payoff weight, percent remaining, gauge and
width actuals, line state and run status are **not** in it and come from `[SIG §5.2]` events 1–7.
A console polling this endpoint for them would be *"a second telemetry path competing with the
hub"*, and `[SIM §2.1]` forbids the simulator growing an interface to serve its own console.
