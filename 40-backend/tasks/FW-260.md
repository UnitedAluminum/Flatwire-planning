## 1. What to build

**Hours:** 10 h BE · **Priority:** Medium · **Sprint:** S2 · **Phase:** 6 · **Stream:** BE

**As** the Tooling Inventory tab,
**I want** a register service for roll sets,
**So that** the fourth tool type reads and writes like the other three.

> **This is the die register's sibling, and deliberately thinner.** `FW-252` carries a *lifecycle*
> service because a die accumulates footage every run and `DieHistory` explains the total. A roll
> set has **no footage counter** — it is reground to a minimum OD — so there is no per-run write
> path, no denormalised total to keep honest and no history log. What is left is a register.

**Acceptance Criteria:**
- [ ] Read and write endpoints for `ToolingInventoryRollSet`, following `API/Domain/CoilCheckin` as the template — ⚠ **`SlitterInterface` is explicitly not a reference**
- [ ] **`CK_TIRS_Mount` enforced in the aggregate as well as the database**: exactly one of `StandId` / `DrawerId`, agreeing with `RollType`. The database CHECK is belt-and-braces, not the only defence — the same bargain `UX_RodStaging_Bay` strikes
- [ ] A mount violation answers **422**, not 500. A `Mill` row naming a `Drawer` is an invariant breach, not a server fault
- [ ] `LineId` restricted to `FL1` / `FL2` at the API boundary. ⚠ **An `FL3` roll set is a client error** — FL3 uses a combination of the two (`D-42`)
- [ ] ⚠ **`NominalDiameterIn` is not derived from, validated against or reconciled with `Stand.RollDiameterIn`.** They are separate values with separate owners: the machine's roll diameter is `D-26` and `[PLC §5.4]` data; this is the physical tool's own size
- [ ] Retirement sets `LifecycleStatus`; it does not delete. Same discipline as `FR-250`
- [ ] Unit tests cover both mount shapes, the `FL3` rejection and the `MinOdIn < OdIn` edge

**Rate-card basis (§2):** one register service with a non-trivial invariant, below `FW-252`'s 16 h because there is no lifecycle, no history log and no denormalised counter = **10 h**
