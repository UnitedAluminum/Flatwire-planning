## 2. The three rules that shape the code

### 2.1 Replace the throw; do not add a layer

Both methods exist, both throw **by name**, and both messages already name this story. The whole of
the work sits behind those two signatures. **Do not mint a scenario engine, a fault registry or a
strategy interface** — `P-265` declined an interface the specification sketched and `P-268` declined
a type it sketched, both because the built code already carried the concept.

### 2.2 One seeded generator, and `Erratic` scales it

`[SIM §5.7]` requires the trace to be reproducible tick for tick, and AC 6 is that requirement. The
model already owns the only generator, seeded per line. **A scenario that constructs its own
`Random` breaks reproducibility while still producing a plausible-looking trace** — it fails
silently, which is the worst failure mode in this subsystem. `Erratic` therefore multiplies
`sim.GaugeNoiseIn` into the existing `Noise(boundIn)` call and adds nothing.

### 2.3 A scenario writes the commanded fields, and `/sim/state` cannot tell it from a steer

`ApplyScenario` sets `gaugeBiasIn` and `driftPerTickIn` — the same fields `Steer` sets — so
`GET /sim/state` reports a scenario selection and a manual nudge identically. **That is accepted,
not fixed.** `SimLineState` carries six fields, `[SIM §9.2]` forbids widening it, and `P-267` fixes
their meaning as command echo. The console's scenario picker is greyed at trial in any case, and
`FW-215` carries the scenario on `POST /sim/{lineId}/run`, where the caller already knows what it
asked for.

## 3. Build order

1. **`ApplyScenario` — `InSpec`, `Drifting`, `OutOfSpec`, `Erratic`.** Four presets over
   `gaugeBiasIn`, `driftPerTickIn` and a scenario-scoped multiplier on `sim.GaugeNoiseIn`. Store the
   selected scenario on the model so it keeps acting; do **not** put it on `SimLineState` (§2.3).
   `OutOfSpec` sets a bias beyond the **active tolerance band** rather than a hard-coded inch value —
   the band is `PassSchedule` data, and `P-135` is the precedent for why a compiled figure here goes
   wrong by a factor of three.
2. **`ToTarget` — the decline path** (`P-289`). Reachable, compiled, throwing by name and citing
   `Q10` / `OI-45` when `LbPerFt` is unset. When it **is** set it runs: the arithmetic is one
   comparison against `RemainingWeightLb`, so the behaviour ships complete and inert.
3. **`InjectFault` — the five buildable new kinds.** `Stall` (speed → 0, run still `Running` —
   `[SIM §4.4]`'s distinction, and `SetRunState` is *not* called), `WireBreak` (stop plus an
   in-memory marker), `DieWear` (accelerated footage against `Drawer.LastGrindingFeet`),
   `PushFailure` (the next `ApplyConfiguration` / `ApplyComponent` is refused and the line keeps its
   previous configuration — `FW-212`'s `P-279` decorator and `P-284` pin store are what it must not
   disturb), and `LineStop` (§3.1).
4. **`WeightVariance` — the second decline path**, same shape as step 2.
5. **`CommsDrop` — touch nothing.** Re-run `FW-211 §5.2`'s bracket as a regression, no more.
6. **Reject an out-of-range `ticks`** exactly as the built `InjectFault` already does, and keep the
   existing *"rejected rather than ignored"* message shape — an unapplied fault must never read as a
   system that tolerated it.

### 3.1 `LineStop` — the fault, not the endpoint

`DELETE /sim/{lineId}/run` already produces a `RUNNING → STOPPED` edge, and `TC-171` / `TC-172` are
executable from it today (`FW-218 §1.1`). **`FaultId.LineStop` is not that.** What it adds is
`FR-143`'s **weight latched at the stop timestamp** and `FR-141`'s **exactly once per stop**.

⛔ **Do not re-implement the edge inside the fault.** Two stop paths that can disagree is precisely
how an *"exactly once"* assertion fails — the fault calls the same `SetRunState` transition and adds
the latch and the guard around it.

⚠ **The latch latches a `null` today**, for §1.2's reason. That is correct, and it is not
`WeightVariance`'s problem: the *edge* and the *once-per-stop* guarantee are both testable with a
null weight. Only the weight's **value** is unavailable.

## 4. Decisions this plan makes

> `P-##` is continuous across this folder; `P-01`–`P-284` precede this story.

### `P-285` — the vocabulary is already minted, so this story fills bodies and adds no types

`ApplyScenario`, `InjectFault`, `ScenarioId` and `FaultId` are all declared by `FW-210`, and both
methods throw by name with `FW-213` in the message. The story is met by **replacing two throws**,
not by adding a layer — and four of the five scenarios are presets over `gaugeBiasIn`,
`driftPerTickIn` and `sim.GaugeNoiseIn`, which are built.

**This is `P-265`'s and `P-268`'s reasoning a third time**: the specification sketches a shape, the
built code already carries the concept, and the right move is to decline the new type. **Fallback:**
none needed — a new abstraction here would have to be threaded through three line models that
already share `LineModelBase`.

### `P-286` — six faults, not seven; `CommsDrop` is built and stays built

`CommsDrop` is implemented at `LineModelBase.cs:454`, reached from `OpcFeedSimulator.cs:212` through
`FW-218`'s `POST /sim/{lineId}/fault`, and verified from both sides by `FW-211 §5.2`. It is
`FW-205`'s **only** route to conditions **5 and 3** — a held drop past `ITInhibitSilenceMs`
escalates — which is why it was the one fault in `FW-218`'s scope.

This story **re-verifies it and does not touch it.** ⛔ **`[TB §7]`'s `FW-213` card says *"the seven
faults"* while its own `FW-214` card says *"six of the seven"*.** The amendment is **owed, not
made** — §7.

### `P-287` — `FaultId`'s member names are the wire vocabulary, and `"DroppedReadings"` stays an alias

The enum member is `CommsDrop`; the string `SimControlSurface` accepts is `"DroppedReadings"`
(`SimControlSurface.cs:74`). **One fault, two names**, and both are shipped: `FW-218` is built and
measured, and `FW-214` is specified against the string.

So when `FW-215` widens the surface to the full catalogue it accepts **the `FaultId` member names**
and **keeps accepting `DroppedReadings`** as an alias. That is `P-39`'s *"a superset, not a
replacement"* applied to a value rather than to a route, and it is what stops a console built
against the trial breaking on the day the catalogue lands.

**Recorded here because `FW-213` owns the catalogue; `FW-215` executes it.** **Fallback:** rename the
literal in `SimControlSurface` — rejected, because it is a shipped, measured surface and `P-38`'s
both-ways verification would have to be re-run to change one string.

### `P-288` — one seeded generator; a second `Random` is forbidden

`LineModelBase.cs:139` seeds `new Random(sim.Seed + (int)line)` and `:790` is its only consumer.
`[SIM §5.7]` requires reproducibility tick for tick, and AC 6 is that requirement.

**A scenario that constructs its own generator produces a trace that still looks right and is no
longer reproducible** — the failure is silent. And `SCS0005` is already suppressed at `:789` with a
comment explaining that the seed *is* the feature, so the next reader has every reason to believe a
local `Random` is acceptable here. It is not. `Erratic` scales `sim.GaugeNoiseIn` into the existing
`Noise(boundIn)` call.

### `P-289` — `ToTarget` and `WeightVariance` build to the null and decline by name

Both are weight-driven, and `RemainingWeightLb` returns `null` while `LbPerFt` is unset (`P-271`).
They are therefore **built complete and inert**: reachable, compiled, and throwing by name with
`Q10` / `OI-45` in the message — the same *"refuse rather than guess"* posture as `P-271` itself and
as `LineModelBase`'s existing throws. Setting `LbPerFt` in `appsettings` brings both alive with no
code change, which is `[SIM §5.6]` row `A2`'s labelled-assumption route.

⛔ **Do not substitute footage for weight.** It is the obvious workaround and it is wrong: it would
give `ToTarget` a plausible stopping point derived from the very dimensional basis nobody has agreed,
and `WeightVariance` a variance against a number the project has twice refused to invent. **That is
`G39` in miniature** — an assumption wearing the clothes of a measurement — and `[SIM §5.3]` calls
`lbPerFt` *"the single most load-bearing unverified number in this model"*.

⚠ **Neither is a defect in this story.** They are the two places where an open question reaches the
code, and this plan's job is to make that visible rather than to close it.

### `P-299` — the gauge tolerance band becomes DATA, and excursions are sized in bands *(minted by the build)*

⛔ **§3 step 1 named something that does not exist.** It said `OutOfSpec` should set a bias *"beyond the
**active tolerance band** rather than a hard-coded inch value — the band is `PassSchedule` data"*. It is
not: **`SimLineNominals` carries gauge, width and start weight and no tolerance**, and
**`PassScheduleSnapshot` carries targets, route mode and components and no tolerance** either. The only
place the band existed was **prose** — `GaugeNoiseIn`'s own remark reads *"0.0002 against the seeded
gauge tolerance of ±0.0020 — a tenth of the band"*.

So the band is promoted from a comment to `FlatWireSimulationOptions.GaugeToleranceIn`, defaulting to
**0.0020**, with a per-line override on `SimLineNominals`. **It takes a default because it is a
FIXTURE**, the same treatment `Lines` gets and deliberately **not** `LbPerFt`'s — 0.0020 is right for
both trial schedules (`PS-1100-FL1-001` 0.1100 ± 0.0020, `PS-1100-FL2-002` 0.1000 ± 0.0020).

**Every excursion is then sized in bands**: `Drifting` walks `band ÷ 60` per tick, `OutOfSpec` steps to
`band × 2`, `Erratic` scales the noise bound ×5 to half a band. ⛔ **The alternative was a hard-coded
inch figure, which is precisely `P-135` and `P-277`** — a plausible compiled number that stops meaning
anything the moment a schedule changes, and fails nothing while doing it.

⛔ **The model judges nothing against this value.** In-spec is decided downstream against the schedule's
own tolerance — `SpcMeasurement.InSpec` is a PERSISTED computed column — and a second opinion here is
how one question quietly acquires two answers. It sizes a scenario and does nothing else.

### `P-300` — the wire-break marker is observable on the MODEL, never on the wire *(minted by the build)*

`[SIM §7.2]` specifies `WireBreak` as *"stop + a break marker"*, and **the marker had nowhere to be
seen**: `G34` leaves it with no persistence target, `Reading` has no field for it, and `[SIG §5.2]`
carries nothing like it. **An unobservable marker is not a marker** — §5's row asserts against it, and
without an accessor the fault is indistinguishable from a plain stop.

So `ILineModel` gains **`bool WireBroken`**, joining the observable state (`State`, `FootageFt`,
`GaugeBiasIn`, `DriftPerTickIn`, `DropTicksRemaining`) that exists for exactly this purpose. ⛔ **It is
deliberately NOT added to `SimLineState`**, which is six fields and which `[SIM §9.2]` forbids widening.
When `G34` settles a target, this property becomes the thing that **feeds** the real home rather than
the thing that replaced it.

⚠ **This is `P-269`'s shape, one member over**: a hole in the contract rather than a preference. The
marker is cleared when the line runs again, because a break belongs to the stop it caused.
