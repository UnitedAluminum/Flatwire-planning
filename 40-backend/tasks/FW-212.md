### 1.2 What the card gets wrong, and what it gets free

**(a) The seam is the payload, and the snapshot cannot stand in for it.** `[SIM §3.1]`'s diagram
has `SimulatePLCTagPush payload → CORE`; `[SIM §6]` opens *"today a simulated push logs the write it
would have made and discards it — `FW-212` feeds it back"*. Both are right, and two facts make them
binding rather than stylistic: the snapshot **carries no speed**, and no snapshot can express *one
component's gap*, which is AC 2. `P-278`.

**(b) AC 2 has no mutator on the built interface.** `ApplyConfiguration` takes a whole schedule and
`Steer` is per-line; **nothing addresses one component.** That is the same hole `P-269` found for
`/steer` one story earlier, and `P-280` fills it with **one** member.

**(c) ⛔ Edge TYPE is not on the wire, and AC 1 is therefore not buildable as written.** The payload
writes `Fm2S2EdgerActive` / `Fm2S3EdgerActive` — booleans. `PassSchedulePushPayload.cs:242` states
it: *"the edge TYPE itself (`Round` or `Square`) has no tag anywhere on the surface, so the
controller learns that an edger is engaged and not which profile it should form."* `G29` is open,
`[PLC]` owns every tag string, and `G33` means a wrong path **fails silently** — so a geometry tag
must not be invented. `P-283` observes **engagement**, and `[SIM §6]`'s edge-type row plus AC 1 are
owed an amendment.

⚠ **Two corrections to that, both in the story's favour.** The engagement is **visible**: FL2 and FL3 publish an `EdgeSet` component row whose `IsActive` is `IsComponentLive(EdgeSet)`, and both models seed it `Active` — so a pushed disengagement moves the panel, and this is not a value stored for nobody. And **the two edger tags cannot disagree**: `AddEdgeType` writes *the same* `component.IsActive` to both (`PassSchedulePushPayload.cs:273`), from one `EdgeSet` row, so mapping both names onto `EdgeSet` is idempotent rather than lossy.

**(d) AC 4 is free, and the card understates it.** It asks that the model see the push *"after the
record exists"*. `CheckInService`'s built order is stronger: the acknowledgement audit and the run
record **commit** at step 4 and the push is step 5, *outside* the transaction — `P-258` refused a
MediatR command precisely so `TransactionBehaviour` could not pull the push inside it. An observer
on the push therefore cannot run before the records are durable. **No work, and nothing to test but
the order itself.**

**(e) AC 3 is already built.** `IsComponentLive` gates on `Active` and `Fm2Chain` redistributes
reduction across the **active** stands only. It needs the states to *arrive*, which is step 5, and no
new arithmetic. ⚠ **Corrected on re-review:** `StateOf`'s `Skip` default is the **base's**, and it is
reached only by a component no model seeds — each model seeds `DefaultComponentStates` in the
constructor (`LineModelBase.cs:143`), so a push always merges onto a complete configuration rather
than into a hole. FL2's default is `S1`/`S2` **`Bypass`** with `S3` and `EdgeSet` `Active`, which is
also why a trial FL2 panel shows **one** active stand.

**(f) AC 5 is free once the gate is right, and its demonstration is not this story's.** With
`P-279` observing only `Success && Simulated`, a failed push is **never seen** and the line keeps
its previous configuration by construction. ⚠ **Injecting `PushFailure` is `FW-213`'s** —
`InjectFault` throws `NotImplementedException` for all six non-`CommsDrop` kinds by name
(`LineModelBase.cs:346`), deliberately. **Do not implement it here.**

## 2. The three rules that shape the code

### 2.1 The loop lives inside the simulation boundary, and nothing outside it changes

`P-37`, and [`FW-211 §5.2`](FW-211.md) turned it into a **file-level measurement**:
`BroadcastLoopService.cs` and `PLCTagService.cs` unchanged, **zero** references to `ILineModel`,
`LineModelBase`, any `Fl*LineModel` or `FlatWireSimulationOptions`. That measurement will be re-run.

So: **do not edit `PLCTagService`, and do not edit `CheckInService`.** A hook in either would put
the simulator inside the production write path and make the check-in behave differently under
simulation — which is the substitution failing, not the loop succeeding. `P-279` decorates instead.

### 2.2 Selected by configuration, and absent when simulation is off

`[SIM §2.2]` and `[SIM §2.4]`. The decorator is registered **only** when `SimulateOpcFeed` is true —
the same flag that creates the models — so when the feed is real there is no model to configure and
**no wrapper exists to look for one**. ⚠ **Do not add a third flag.** `SimulatePLCTagPush` remains
the *write* half and is read where it already is, inside `PLCTagService`; the decorator reads
`PlcWriteResult.Simulated` instead of the flag, which is the same fact arriving as a value.

### 2.3 No tag path is written anywhere but configuration

`[PLC]` owns every path string. This story reads **logical names** (`TagNames`) and never a path:
`PlcTagValue.LogicalName`, never `PlcTagOutcome.Path`. ⚠ The distinction is not cosmetic — logical
names are ours and stable, paths are `[PROPOSED]` and will move at commissioning (`G33`). A reader
keyed on paths would break at `C1` for no reason.

## 3. Build order

**Step 0 — read first.** [`FW-210 §4`](FW-210.md) (`P-268`–`P-274`), [`FW-211 §2`](FW-211.md),
`[SIM §6]`, `[PLC §7.2]`, and `TagNames.cs`'s block comment at `:65`–`:86`. Then §1.2 and §1.3
above. **Do not start by writing a payload reader** — start by confirming §1.3 still holds; if the
two rows have been bound, the verification in §5 gets a whole row back.

1. **Store one pushed gap per component.** `LineModelBase` gains
   `private readonly Dictionary<ComponentName, decimal> rollGapsIn = []` beside `dieSizesIn`
   (`:77`), and a `protected decimal? PinnedGapIn(ComponentName)` accessor beside `DieSizeIn`. ⚠ This
   is the field the built model has no room for, and it is why the story is not a two-line wiring
   job. ⛔ **Unlike `DefaultDieSizesIn`, it takes NO default** — empty means *derive every gap*, which
   is exactly today's behaviour, so **this step changes nothing on its own**. Do not seed it with the
   fixture gaps; a seeded pin would silently override the chain on a line nobody had pushed to. ⚠ The
   accessor is **not** named `RollGapIn`: that name is taken by the forward mill-spring term at
   `:454`, and one letter of overload between a *pin* and a *derivation* is how the two get confused.
2. **Invert mill spring, once, beside the term it inverts.** `RollGapIn(entry, exit)` at `:454` is
   `exit − (entry − exit) × f`. Add
   `protected decimal ExitGaugeForGap(decimal entryGaugeIn, decimal gapIn)`, immediately below it,
   with a comment tying the two. **One arithmetic, two directions** — `P-281`. Do not scatter `f`.
   The derivation, so a reviewer can check it rather than trust it:
   `gap = exit − (entry − exit)·f = exit(1 + f) − entry·f` → `exit = (gap + entry·f) / (1 + f)`.
   ⛔ **And it must carry the forward term's own no-load branch, which the first draft of this step
   omitted.** `RollGapIn` returns `exitGaugeIn` unchanged when `reduction <= 0`; so
   `ExitGaugeForGap` returns **`gapIn`** when `gapIn >= entryGaugeIn`. Without that guard a gap
   pushed at or above the entry gauge yields an exit *below* the gap — `P-272`'s sign error
   re-entering from the inverse side, on the one input a controls engineer is most likely to try.
3. **Pin the pinned stands, in one forward pass.** `Fm2Chain` (`:491`) walks `S1`→`S2`→`S3`. A
   **pinned** active stand's exit is `ExitGaugeForGap(running, pin)`. An **unpinned** active stand's
   exit is `running − (running − effectiveTarget) / n`, where `n` is the count of active unpinned
   stands **at or after** it — so what remains is always distributed and the last unpinned stand
   lands exactly on target. ⚠ `effectiveTarget` is **`gaugeTargetIn + gaugeBiasIn`**, which is what
   the built `totalReduction = entry − target − bias` already computes; dropping the bias term here
   would quietly un-steer a steered line. A pinned **final** stand (`FM2_S3`, and `FM1` on FL1) also
   sets `gaugeTargetIn` — `P-281`. `Fl1LineModel.cs:114` needs no change; it calls `RollGapIn` and
   picks the new exit up through the target.
   ⛔ **`Fl3LineModel.cs:184` needs no change EITHER, and for the opposite reason: on FL3 the `FM1`
   gap is NOT applied.** `Fm1ExitGaugeIn` is a `const` and `FW-210` recorded why — the intermediate
   gauge is a property of the machine order, not of a schedule, and `P-275`'s speed coupling reads
   the same constant, so pinning it would move FL3's take-up speed as a side effect nobody asked
   for. What *does* move FL3's `FM1` gap is a pushed **DB2 die size**, through `MillEntryGaugeIn`.
4. **One new member on `ILineModel`.**
   `void ApplyComponent(ComponentName component, ComponentState? state, decimal? dieSizeIn, decimal? rollGapIn)`

## 4. Decisions this plan makes

> `P-##` is continuous across the repository. `P-277` was the last minted, by
> [`FW-210`](FW-210.md)'s build.

### `P-278` — the loop reads the PAYLOAD, and the layering objection to it is wrong

`ILineModel.cs:56` declines `[SIM §3.2]`'s `PassSchedulePush` parameter because *"the built
`PassSchedulePushPayload` is an INFRASTRUCTURE SERVICE … so naming it here would drag Infrastructure
into Domain"*. **The service is Infrastructure; the payload is not.** `PlcTagValue` is declared at
`IPLCTagService.cs:218` in `FlatWire.Domain.Services` and `TagNames` in `FlatWire.Domain.Constants`
— so neither `IReadOnlyList<PlcTagValue>` nor the `PlcTagOutcome` list the observer actually reads
(step 6) crosses a boundary — both records are declared in the same Domain file — and AC 1 of
`FW-210` ("no infrastructure dependency") is untouched.

Two facts then make the payload the only workable seam, and neither is a preference:

- **Speed is not on the snapshot.** `Build` takes `startSpeedFpm` as a third argument (`P-261` —
  the bottom of the schedule's speed window). A snapshot observer cannot see AC 1's speed item at
  all without a second channel for it.
- **AC 2 is a single tag.** `Fm2S2RollGap` arriving through `WriteComponentAsync` is what the roll
  adjust *is*. One reader over logical names serves AC 1 and AC 2; a snapshot observer serves
  neither and would need a second mechanism beside it.

⚠ **`ApplyConfiguration(PassScheduleSnapshot)` is NOT deleted and NOT called by the loop.** It is
the typed path a `/sim` schedule action would use, and it belongs to [`FW-215`](FW-215.md). Two
members, two genuinely different inputs — an acknowledged snapshot the application holds, and the
values a machine is sent. That is not `P-268`'s *"second contract for one fact"*; it would only
become so if the payload reader duplicated the target arithmetic, which step 5 avoids by delegating
to the same mutators.

### `P-279` — the observation is a DECORATOR on `IPLCTagService`, and it observes only success

`PLCTagService` and `CheckInService` are not edited (§2.1). A decorator registered only under
`SimulateOpcFeed` (§2.2) gives four things at once:

1. **`P-37` survives** — [`FW-211 §5.2`](FW-211.md)'s file-level measurement still passes, because
   the changed files are a new one and a registration.
2. **AC 4 is inherited** — the wrapper wraps the very call `CheckInService` makes at step 5, after
   the records commit. The ordering cannot be inverted from here.
3. **AC 5 is structural** — gated on `result.Success && result.Simulated`, a failed push is never
   seen, so the line keeps its previous configuration. Nothing is undone, because nothing was
   applied. ⚠ **This is also why the word `[G16]` prohibits never arises**: there is no recovery
   path in this story to misname.
4. **It goes inert at commissioning by itself** — once `SimulatePLCTagPush` is false, `Simulated` is
   false on every result, and a real controller is configuring a real line.

⚠ **Both flags matter and they are not the same flag.** `SimulatePLCTagPush` (write) is true in
every environment until commissioning; `SimulateOpcFeed` (read) is what creates the models. The
decorator is registered on the **read** flag and gated on the **write** flag's outcome, so a real
feed with a simulated push has no wrapper and nothing to configure.

### `P-280` — MERGE semantics, one member, and AC 1 and AC 2 become one code path

`ApplyComponent` merges: a named component's stated fields change and nothing else is touched. **No
replace, and no "everything unnamed becomes `Skip`"** — which sounds like the safe choice and is not
needed:

- **`Bypass` arrives as a tag.** `AddComponent` returns early only for `Skip`; a bypassed component
  is pushed as `{X}Active = false`. So a disengagement is *observed*, not inferred from absence.
- **`Skip` is a property of the route, not of a push.** A component the line cannot address is
  filtered by that line's tag map (`P-260`) and can never have been set `Active` on it in the first
  place.
- ⚠ **Added on re-review — the model is never empty to begin with.** Each model seeds
  `DefaultComponentStates` and `DefaultDieSizesIn` in its constructor (`LineModelBase.cs:143`), so a
  merge lands on a complete configuration. A replace would therefore be **worse than unnecessary**:
  it would discard a line default the FL2 trial screens were verified against.

The gain is that a whole-schedule push and a one-tag roll adjust need **no distinction at all** —
same lever, same member, and AC 2 is satisfied by the code AC 1 needs. ⚠ **The residual is named
rather than engineered away:** a component `Active` in schedule A and *absent as a row* from
schedule B keeps its state. §7.

### `P-281` — a pushed gap sets that stand's exit target through the mill-spring INVERSE

`[SIM §6]` says roll gaps *"set each stand's gauge target via §5.5"*, and §5.5's term is
load-proportional — so the mapping is arithmetic, not assignment: **the gap is not the target.**
Publishing a pushed gap as a target would re-ship `P-272`'s sign error from the other side.

The inverse lives immediately below `RollGapIn` (`LineModelBase.cs:454`) so mill spring stays **one
expression of `f`**, and it **mirrors that term's no-load branch** — a gap at or above the entry
gauge is its own exit (step 2). And a pinned **final** stand's gap sets the line's `gaugeTargetIn`,
because otherwise the published final exit and the converging trace would disagree — two sources for
one finished gauge. `FM2_S3` is final and non-bypassable (`D-26`); on FL1 that stand is `FM1`.

⛔ **The carve-out, added on re-review, and it is the correction worth reading.** `[PLC §7.2]` pushes
roll gaps for **`FM1` and all three FM2 stands** on FL3 — and **FL3's `FM1` gap is not applied.**
`Fl3LineModel.cs:53`–`:61` had already decided it: *“a pushed schedule carries per-stand roll gaps
and will move the stands around this; the intermediate gauge itself is a property of the MACHINE
ORDER rather than of a schedule, which is why it is a constant here and the stand gaps are not.”*
Pinning it would also move FL3's published speed, because `P-275`'s gauge-ratio coupling reads the
same constant (`:150`) — a side effect no push asked for. ⚠ **The first draft of this plan would have
stored that gap and consumed it nowhere**, which is the silent omission `P-41` refuses; it is now
accepted and **logged by name**. On FL1 and FL2 nothing is carved out, and a pushed **DB2 die size**
remains what moves FL3's `FM1` gap.

⚠ **Assumption `A5` is not strengthened by this.** The inverse is exactly as unverified as the term
it inverts, and `G39` is unchanged — see §7.

### `P-282` — speed and both targets reach the model through the EXISTING `Steer`, and the push never touches bias or drift

`LineSteer` already carries `SpeedSetpointFpm`, `GaugeTargetIn` and `WidthTargetIn`, with *"every
member optional; a null member is left unchanged"* — which is precisely a partial configuration.
**No new member for AC 1's per-line items.**

⛔ **`GaugeOffsetIn` and `DriftPerTickIn` stay null on every pushed `LineSteer`.** `P-267` makes them
**command echo** from `POST /sim/{line}/steer`; a check-in is not a steer command. Writing them here
would let an acknowledgement silently clear a bias the console had applied, and would change what
`GET /sim/state` reports without anything failing — the exact failure mode `P-267` exists to
prevent.

### `P-283` — edge type is observed as ENGAGEMENT, and no geometry tag is invented

The payload carries `Fm2S2EdgerActive` / `Fm2S3EdgerActive`, booleans. `Round`/`Square` has no tag
on any line (`G29`, `PLC-Q07`), and `[PLC]` owns every tag string while `G33` makes a wrong path fail
**silently** with the audit recording success. So the model learns that an edger is engaged and not
which profile it forms, and `[SIM §6]`'s *"affects the width target only"* has nothing to act on.

⚠ **Stronger than first written, and re-verified:** engagement is not a value stored for nobody.
FL2 and FL3 **publish** an `EdgeSet` component row (`Fl2LineModel.cs:169`, `Fl3LineModel.cs:203`),
both models seed it `Active`, and FL1 carries no such row at all — matching `[PLC §7.2]`'s *“not
applicable — FL1 has no edger.”* So a pushed disengagement **moves the panel**; what is missing is
the geometry, not the response.

⚠ **The alternative was available and is refused:** the *snapshot* does carry `EdgeType`
(`PassScheduleSnapshot.cs:78`). Reading geometry from the snapshot while reading everything else
from the payload would give the model a fact **the real feed structurally cannot deliver** — `P-37`
undone at the one point where it is hardest to notice, because the demonstration would work. AC 1's
edge-type item and `[SIM §6]`'s row are owed an amendment instead (§7).

### `P-284` — the finished-gauge target is DERIVED on read, not written on push *(minted by the build)*

⛔ **Step 3 said a pinned final stand *sets* `gaugeTargetIn`, and implementing that exposed two
faults in one line of code.** `ApplyComponent` would have to invert the gap against that stand's
**entry** gauge — and on FL2 and FL3 the final stand's entry is `FM2_S2`'s exit, not
`MillEntryGaugeIn`, so the first cut was taken against the wrong number. Worse, computing it at
write time makes the answer depend on **the order the three stand gaps arrive in**, which is a
property of a `foreach` over a tag list and of nothing physical.

So the pin is **stored** and `EffectiveGaugeTargetIn` derives the target on read:
`ExitGaugeForGap(EntryGaugeForStand(FinalStand), pin)` when the final stand carries a pin, and the
stored target otherwise. `EntryGaugeForStand` is a **forward** walk from the FM2 entry — so it
cannot be circular — and `Fm2EntryGaugeIn` is where FL3 says its FM2 is fed `FM1`'s exit rather
than the rod-side mill entry. Both `Tick` and `Fm2Chain` read the derived value, so **one target,
no competing sources**, which is what `P-281` asked for and this is how it is actually achieved.

⚠ **Two consequences worth stating.** A steered `GaugeTargetIn` now **clears the final stand's
pin** (`Steer`), so the last writer wins — without that, steering the target on a line whose
schedule pinned the final gap would appear to do nothing at all, silently. And the derivation is a
**three-step walk once per tick** on a one-second cadence; nothing on the hot path changed.

⚠ Two structural members carry it, and both are STRUCTURE rather than values — the same test
`FW-210` used for the three models: `FinalStand` (`FM1` on FL1, `FM2_S3` on FL2 and FL3) and
`AcceptsPinnedGap` (`FL3` declines `FM1`, `P-281`). Neither is a flag on a shared model.
