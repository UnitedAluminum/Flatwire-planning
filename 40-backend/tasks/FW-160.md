## 2. The four details

### 2.1 Two vocabularies, and `Blocked` wins

`P-139` records it precisely: the domain says `Staged`/`Welded`/`CheckedIn`/`Unstaged`;
`[SIG §5.2]` publishes `NotStaged`/`Staged`/`Active`/`Blocked`. **Different lists.**

The translation rules, already built:

- **`Blocked` is tested first** — it is layered on `Staged` and **must win**.
- **`Welded` maps to `Staged`**, with the flag carried separately as `isWelded`.
- **A word outside the four broadcasts nothing and logs at error level**, rather than being
  passed to a client with no rendering for it.
- **`RodSeqno` 0 publishes as `null`** — `Stage` assigns no seqno.

⛔ **Do not "simplify" this into a direct enum cast.** The lists differ in both directions.

### 2.2 Unbatched is a correctness rule, not a performance one

AC 3 forbids this event entering the ~100 ms / 10 Hz batch. The reason is not latency: the
batch is **decimated and newest-wins** for scalars, so a rare state change riding it could be
**dropped entirely** when two changes fall in one window.

**Live weight keeps coming from the batched `PayoffWeight`** — the two are different channels
with different delivery guarantees, and that split is deliberate.

⚠ **`FW-150` sends nothing on an empty tick.** A state change routed through the loop on a tick
with no readings would therefore never be sent at all.

### 2.3 The suppression rules are two, and both are "broadcast nothing"

| Trigger | Rule |
|---|---|
| **Failed weld** | Changes no bay state → **broadcasts nothing** (AC 2) |
| **Failed PLC push** | **No broadcast** — state is compensated first (AC 5) |

⚠ **AC 5 is the harder one and it is already half-solved.** `FW-208`'s post-commit lane fires
**after** the transaction commits, and `P-27` established that the PLC compensation is three
steps this service owns — `ClearPayoffTags` → a small local transaction → `500 PLC_PUSH_FAILED`.

⛔ **So the broadcast must be raised from a path that runs only after the push succeeds** — not
from the aggregate's commit, which happens first. If the event is raised in the aggregate and
the push then fails, `FW-208` will have already dispatched it.

**That ordering is this story's real content.**

### 2.4 `LineStatus {status: Running}` is silent until `C2`

AC 4 asks for `LineStatus {status: Running}` on check-in success so Dashboard 1 flips to
RUNNING. ⚠ **`FW-150` is deliberately silent on `LineStatus` pre-`C2`** because
`TryMapLineState` returns `false`.

**These are different senders and can legitimately differ** — a check-in *knows* the run
started, without needing the PLC's line-state word. But the board must not receive
`Running` from here and then unknown from the stream.

⚠ **Agree with [`FW-154`](FW-154.md)'s `P-181`** — the
snapshot, the stream and this broadcast are three sources for one field.

## 4. Decisions this plan makes

> `P-##` is continuous across the repository; `P-01`–`P-185` precede this story.

### `P-186` — the broadcast is raised after the PLC push, not on the aggregate's commit

§2.3. `FW-208`'s post-commit lane dispatches as soon as the transaction commits, and the PLC
push happens after that. An event raised in the aggregate is therefore **already broadcast** by
the time a push failure is known, and AC 5 is unsatisfiable.

**Fallback:** raise it in the aggregate and publish a compensating `PayoffStateChanged`
reverting the state. ⛔ **Rejected** — the board would flicker through a state that never
existed, and `[SIG]`'s markers are not durable, so a client that missed the correction keeps
the wrong state forever.

### `P-187` — the existing handler is extended, never replaced

§1.2, §2.1. `FW-208` built the handler and `P-139` recorded its translation rules. A second
handler for the same event would broadcast twice, and the duplicate is invisible — the client
renders the same state.

## 5. Verification

**No automated tests** — `[TS §1.2]`. Verified in the QA0 walkthrough with a live client.

| Check | Expected |
|---|---|
| **One handler** | Exactly one handler broadcasts `PayoffStateChanged`; no duplicate send (`P-187`) |
| Stage / unstage | Event received immediately with `state`, `rodAlpha`, `rodSeqno`, `isWelded` |
| **`Blocked` wins** | A `Staged` row with a `Fail` publishes `Blocked`, not `Staged` (`P-139`) |
| `Welded` → `Staged` | With `isWelded: true` carried separately |
| Unknown word | Broadcasts **nothing** and logs at **error** level |
| `RodSeqno` 0 | Published as **`null`** |
| **Unbatched** | Arrives immediately, not on a 100 ms boundary; **not dropped** when two changes fall in one window (§2.2) |
| **Failed weld** | **No broadcast**, no state change |
| **Failed PLC push** | **No broadcast**; compensation ran first (`P-186`) — verify by forcing a push failure |
| Check-in success | `PayoffStateChanged` + `LineStatus {Running}` + `ComponentStatus` |
| `LineStatus` agreement | Does not contradict `FW-150`'s pre-`C2` silence or `FW-154`'s snapshot (`P-181`) |
| `Position` | Never sent as `0` when unresolvable |
