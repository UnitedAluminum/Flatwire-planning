## 2. The five details

### 2.1 ⛔ Ship with `FW-230`, or the scheme reissues names

The 26 Aug change `[N]` **withdrew the ignore list**: the mint passes `''` and relies on
`GenerateCoilAlpha`'s **own sweep** to find prior segments. That sweep reads the **shared** coil
master.

⛔ **So `FW-230` built alone reissues `R00001A` on every spool** — `FW-230`'s own card says so, and
`OI-138`/`G54` is the gap.

**The dependency is circular in appearance and not in fact:**
- `FW-231` writes segment alphas to `proddb..coils`.
- `FW-230` mints them, relying on `FW-231`'s rows being there.
- ⚠ **The *first* mint has nothing to collide with**, so the order within one deployment does not
  matter — **but shipping `FW-230` without `FW-231` is a silent duplicate-name generator.**

✅ **`OI-139` is the residual**: whether an FL2-standalone spool can arrive with **no segment at
all**. If it can, the sweep must tolerate an absent parent.

### 2.2 ⛔ Tonnage multiplication — the one to settle before production

`coil_link_master_coil` groups **flat** under the six-character root. So after this story, one
rod's material exists as:

| Level | Alpha | Weight |
|---|---|---|
| Rod | `R00041` | full |
| FL1 segment | `R00041A` | a portion |
| FL2 coil part | `R00041AA` | a portion of that |

⛔ **A report summing children under the root triple-counts.** And it does so **silently** — every
row is legitimate, the link table is correct, and the total is wrong.

⚠ **The card says *"establish which reports do that before the first production write"*, and that
audit has no owner.** ⛔ **`D-32` cancelled the 40 h impact audit** that would have found which
reports care — and raised **`OI-111`** for the related loss. **This is the same class of exposure
and it is not covered by `OI-111`.**

**So the audit is a real, unowned deliverable**, and it is cheaper before the first write than
after.

### 2.3 `coil_status` comes from the existing vocabulary

⛔ **`D-32` bars a new shared value.** `INFLAT` is **`FlatWireDB`-local only** — `Rod.Status`,
`SpoolProcessing.Status`, `RodCheckout.NewRodStatus` — and `FR-077`'s `coils.coil_status` write is
**struck**.

⚠ **The output coil's own status is still open as `Q35`** (`coil_status = 'ONSKID'`), so **the two
decisions are related but separate**: `Q35` is about the FL2 output coil at
`50_…CompleteCoilOnSkid`; this is about the **FL1 segment**.

**Pick from what exists**, and record the choice where `Q35` will be recorded, so the two do not
diverge.

### 2.4 Atomicity, and the pattern is already established

*"Mint and insert in one transaction, or a crash leaks a name."* The pattern is
**`THROW 51011` re-check under `UPDLOCK, HOLDLOCK`** — the same guard
[`FW-230`](FW-230.md) must replicate from the existing caller.

⚠ **A leaked name is not merely untidy**: `GenerateCoilAlpha`'s sweep would then see an alpha with
no row, or a row with no `SpoolTraceability` parent, and the next mint's collision detection is
built on exactly that sweep.

### 2.5 ⚠ It cannot be tested on LocalDB, and that is a stated project trap

No `proddb`, no `CommonDB`. ⚠ **`CLAUDE.md` already warns that the LocalDB line is a developer
convenience and that a build validated only there silently loses atomicity** — because the
check-in transaction model needs `FlatWireDB` **co-located** with the shared databases under the
local transaction manager, with no MSDTC.

⛔ **This story is one of the places that bites.** Prove co-location with the query in
`20_FlatWire_Grants.sql` before relying on any test result.

## 3. Build order

1. ⛔ **Do the tonnage audit first** (§2.2) — which reports sum children under the root. **This is
   the only step that gets harder after the first production write.**
2. ⛔ **Decide `coil_status`** from the existing vocabulary (§2.3), recorded alongside `Q35`.
3. ⛔ **Confirm `OI-139`** — can an FL2-standalone spool arrive with no segment? It decides whether
   the sweep must tolerate an absent parent.
4. Write one `proddb..coils` row **per FL1 segment alpha**, at spool completion — inside
   [`FW-202`](FW-202.md)'s transaction.
5. **Atomicity**: mint + insert in **one** transaction, `THROW 51011` re-check under
   `UPDLOCK, HOLDLOCK` (§2.4).
6. ⚠ **Test on a shared instance**, never LocalDB (§2.5). Prove co-location first.
7. **Ship with [`FW-230`](FW-230.md)** (§2.1).
8. Revisit **`OI-115`** — whether narrowing the spool to one shared face is still wanted now every
   segment has its own shared identity, *"the way `Q89` retired `D6`'s narrowing at the coil hop"*.

## 4. Decisions this plan makes

> `P-##` is continuous across the repository; `P-01`–`P-227` precede this story.

### `P-228` — the tonnage audit is a precondition, not a follow-up

§2.2. Every other item here is reversible; a wrong tonnage figure that has reached a report,
a customer or a month-end is not. ⛔ **And `D-32` cancelled the audit that would have found the
affected reports**, so nothing else is looking.

**Fallback:** if the audit cannot be completed before the first write, **write the rows with a
distinguishing marker** so a report can exclude them, and treat that as temporary. ⚠ **A marker
in an existing column** — `D-32` bars a new one.

### `P-229` — `FW-230` and `FW-231` ship together, and `FW-230` alone is a defect

§2.1. `FW-230` built alone **reissues `R00001A` on every spool** — a silent duplicate-name
generator whose only alarm is the `UNIQUE` index firing later, on unrelated work.

⚠ **`FW-230`'s card already carries this** as *"ship them together or keep this story blocked"*.
This records the same thing from the gating side.

### `P-230` — `coil_status` is chosen from the existing vocabulary and recorded with `Q35`

§2.3. Two adjacent decisions about a shared status column, made in different stories, will
diverge unless they land in one place.
