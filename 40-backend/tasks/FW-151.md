> **Why this document exists.** Four things, and the first is a wording rule that is
> actually a design rule.
>
> **OPC writes are not transactional, so the word "rollback" must not appear** — in this
> service's code, in a comment, or in a log message. Recovery is **compensating re-clears**. A
> developer who writes `RollbackAsync` has not made a naming slip; they have described a
> guarantee the hardware does not give. *(The check is scoped — `FlatWireDbContext` genuinely
> rolls a database transaction back, and it is right to say so. See `P-107`.)*
>
> **Second:** the operations are built here in Phase 1 and **first exercised in Phase 4**
> — so this story ships code nothing calls yet, and that is correct (`[PLCC §4]`).
>
> **Third:** `SimulatePLCTagPush` is `true` in **every** environment until commissioning. It
> is not a dev-only mode, and it is selected by configuration, never by call site.
>
> **Fourth, and it is the one that will surprise you:** ⛔ **`OPCConnection` never tells you a
> write failed.** It answers `200` whether the tag took the value or not, and it sets no
> per-tag status. Everything in §2.4 and §2.5 follows from that single fact.

### 1.1 ⚠ Five real operations, one transport, one mode

Three sources give three counts, and the disagreement is not about scope — it is about what
counts as an operation.

| Source | Says | What it is counting |
|---|---|---|
| The card | **two** | The two the check-in path needs |
| `phase-01b` L108 | **six** | The two, plus per-component, hold/restore, `SetITInhibit`, **and "batch write"** |
| `[PLC §7.1]`, `[PLCC §1]` | **five** | The two, plus per-component, hold/restore, **and "simulated push"** |

**Resolved as five real operations** (`P-103`). Build these, and build nothing else:

| # | Operation | Signature *(`[PLCC §1]`)* | First called |
|---|---|---|---|
| 1 | Pass-schedule push | `PushPassSchedule(scheduleId, lineId, payoffPosition)` | Phase 4 — `CheckInService` |
| 2 | Payoff clear | `ClearPayoffTags(lineId, payoffPosition)` | Phase 4 / 7 — `CheckOutService`, Modes A and B only |
| 3 | Per-component write | one call per **changed** component | Phase 6 — `RollOverrideService`, roll adjust *Apply* |
| 4 | Hold / idle **and restore** | drive enable + speed to idle, reversed on resume | Phase 6 — `RunControlService`, pause/resume |
| 5 | `SetITInhibit(lineId, bool)` | one boolean per line | [`FW-205`](FW-205.md) |

**The two that are not operations, and why building them as methods is a defect:**

- **Batch write is the transport, not an operation.** `OPCConnection`'s `WriteTag` already takes
  `OPCInfo.Tags`, a list — **one POST writes N tags** (§2.5). Every one of the five uses it;
  operation 1 sends many tags and operation 5 sends one. A separate `BatchWrite` method is a
  second code path that will drift from the first.
- **Simulate is a mode, not an operation.** `[PLC §7.1]` lists it as a row because that table is
  about *behaviour visible to the client*. In code it is one branch inside the shared transport
  (§2.3), which is what makes it impossible to select by call site.

> ⚠ **`SetITInhibit` is in neither five-row table** — `[PLC §7.1]` and `[PLCC §1]` both omit it,
> while `[PLC §8]` and `[PLCC §1.6]` require the write and `phase-01b` L112 calls it *"a
> `PLCTagService` operation and not a subscription."* It is a real operation and the tables are
> short by one. **`[PLCC §1]`'s parameter is `scheduleId`, not `passScheduleId`** (`[PLCC §1.1]`;
> `phase-04` still has the old name).

Later phases add rules **on top of** these, not new operations: Phase 7 adds the line-state
gate before `ClearPayoffTags` and the **never-send-a-stop** invariant (`FR-302`, `FR-304`);
Phase 8 the FL2 push; Phase 10 the FL3 single-batch push.

## 2. The rules that shape the code

### 2.1 Compensating re-clears — and the banned word

`phase-01b` L111: OPC writes are **not transactional**. Recovery is a **compensating re-clear**
— *"write the clears for what did land"*, an action that can itself fail — not *"undo"*.
**The code and comments say so, and `rollback` appears nowhere in this service's PLC path.**
Error codes: `PLC_PUSH_FAILED` → `500`, `LINE_STILL_RUNNING` → `422` (`[API §1.8]`).

**The requirements are `FR-073` and `FR-074`, and the card cites neither.** `FR-073` is where
*"as one batch"* comes from. `FR-074` is the compensation itself: *"If any individual tag write
fails, an exception shall be raised, compensating writes shall re-clear the tags already
written … and the check-in shall be aborted"* — and it already carries the wording rule.
`[PLC §7.5]` is its prose form; `[PLC §7.4]` is the ordering rule §2.2 implements.

> ### ⛔ AC 4 is satisfiable today. The sequence is written down.
>
> `[ARC §10]` was corrected on **19 Aug 2026** (`FW-220`): `FlatWireDB` is **co-located** with
> `united_db` / `proddb` / `SlitterDB` / `CommonDB` / `wiplogdb` on one instance, so a single
> `SqlConnection` with a single `SqlTransaction` spans both database halves under the **local**
> transaction manager — no MSDTC. `FR-526` states it as a requirement. **The database half of
> check-in is one ACID transaction and may be described as one.**
>
> So the boundary AC 4 asks you to document has **two participants, not three**, and the
> compensation this service owns is exactly three steps:
>
> 1. **`ClearPayoffTags(lineId, payoffPosition)`** — re-clear what landed.
> 2. **One second, small local transaction** — run `Aborted`, `PlcTagsPushed = 0`, the staged row
>    back to `Staged`.
> 3. **`500 PLC_PUSH_FAILED`** — the operator sees the abort and starts again; the machine is
>    left in its prior state.
>
> ⚠ **The Mermaid diagram in `[ARC §10]` still shows the old shape** — two sequential database
> commits and two compensation paths. `[ARC]` says so itself: the correction *"removes two of the
> three failure windows in the diagram below and one of its two compensation paths."* **Document
> the three steps above, not the diagram.** `[PLCC §1.2]` has the same residue — it describes
> committing local *then* shared.

### 2.2 The audit record is written **before** the push

`FR-072`. Not after, not in a `finally`. A push that fails must still leave an
**incomplete-push marker**. `FR-075`: every write **and clear** is audited.

`IAuditLog` is **built**, and its contract is more specific than the card:

- **Four sinks** — `PlcTagsPushedAsync`, `PlcTagWrittenAsync`, `PlcTagsClearedAsync`,
  `ScheduleOverrideAsync`. On a batch push, `PlcTagsPushed`'s `TagPath` **names the group, not
  one tag**; each tag additionally gets a `PlcTagWritten`.
- **Every write is a PAIR** — `AuditOutcome.Attempted` first, then the outcome. **A failed push
  therefore leaves three records: attempt, failure, and the compensating clear.** Do not collapse
  them.
- **`AuditEntry` requires `OperatorId` and carries `RunAlpha`** — the two query keys `FW-143` AC 3
  names. ⛔ **`[PLCC §1]`'s signatures carry neither**, so as written they cannot produce a
  compliant record. See `P-106`.
- **`Simulated` is a field on the record**, because the flag is on in every environment until
  commissioning — without it the trail cannot tell a real write from a logged intention.

**Beyond the log, each write leaves a durable flag on the caller's record** (`[PLC §11.2]`):
`RodCheckin.PlcTagsPushed` / `SpoolCheckin.PlcTagsPushed`, `RollOverride` per component,
`RodCheckout.PlcTagsCleared`. **This service does not write those columns** — it returns a result
the caller stamps. That is what makes `TC-085`'s `PlcTagsPushed = 0` and `TC-382`'s
`PlcTagsCleared = false` assertable, and it is why the operations must not return `void`.

> **Performance note, and it is the only one that matters here.** The pre-push audit is a loop
> over the batch: for FL3's largest push that is a few dozen structured Serilog events, in
> process, on a human-paced operator action — free. ⚠ **If `P-15` ever lands a `PlcTagAudit`
> table, that loop becomes N inserts and must become one set-based insert.** Do not write the
> loop so that swapping the destination turns it into N round trips.

### 2.3 Simulate mode

`SimulatePLCTagPush` is **`true` in every environment until commissioning completes** and is
selected **by configuration, not by call site**. A simulated write **logs the write it would
have made** — which is what makes the whole audit path exercisable now rather than at `C1`.

**`[PLC §10.2]` is stricter than "does not write": it makes *no machine connection*.** So the
branch sits **before the outbound call**, and in simulate mode there is **no HTTP request, no
Polly, no timeout and no confirm read** — the push is a log write and returns immediately. That
is what makes the demo fast, and it is why Polly must wrap only the real branch.

> ⚠ It is one of **three** independent simulation switches. See
> [`FW-140 §2.2`](FW-140.md) — collapsing them is a real and
> easy mistake. ⚠ And `opc.reachable` on `/health` **must not be keyed off this flag**
> ([`FW-148`](FW-148.md) `P-87`) — the health check probes for real and lets the
> flag set only the severity.

### 2.4 Polly, and the silent-failure problem

**Polly on outbound OPC calls** (`phase-01b` L97) — this service owns that. **Retry a transient
transport failure; do not retry a rejected write, and do not retry a non-success status code.**
The built precedent is `OpcHealthCheck`: `Policy.Handle<HttpRequestException>()
.Or<TaskCanceledException>().WaitAndRetryAsync(1, _ => 200 ms)` behind a **1 s** attempt timeout
— **one** retry, not three. Match it. A write is not more retryable than a probe, and a second
attempt at a write the controller refused is just the same write twice; `HttpClient.Timeout`
surfaces as `TaskCanceledException`, not `TimeoutException`, which is why that arm is there.

> ### ⛔ Two silent failures, not one. The second is checkable today.
>
> **`G33` / `PLC-Q05` — the path.** The measure segment of **every** tag path is ours, not the
> controller's, and **a wrong path fails silently: the write reports success while the line keeps
> its previous settings.** Polly cannot see it and the audit records success.
> **Do not treat a green write as proof the line took the value** until `C1`/`C11` confirms the
> path. `IAuditLog`'s own remarks say the same thing.
>
> **⛔ The response — and this one is a defect in `OPCConnection`, measured 28 Aug 2026.** A
> `200` from `WriteTag` means *the request was accepted* and nothing more (§2.5). Both OPC
> managers catch every failure and log it — `OPCUAManager` at `LogInformation` — the controller
> returns `200` regardless, and `IsGood` comes back **null**. **So `FR-074` cannot be
> implemented from the response.** Confirm with one batched `ReadTag` (`P-105`, **`G58`**).
>
> ⚠ *The `41`-path figure that used to sit here is stale.* It was FL1 15 · FL2 14 · FL3 23 on
> 4 Aug 2026, before `[PLC]` v1.1 added the dancer rows; the published tables now hold 17 on FL1
> and 22 on FL2, and `FW-144` **measured 72 bound paths** (FL1 17 · FL2 22 · FL3 33) on the
> deployed configuration. **Do not restate a count here** — `G33`, `phase-01b` L192 and `[TB §7]`
> all quote the old one, and re-baselining is the register's, not a leaf plan's. The risk is
> unchanged either way: it is **every** path, not a subset.

### 2.5 ⚠ The `OPCConnection` contract, measured 28 Aug 2026

Read this before writing the transport. **None of it is in any planning document**, and four of
the seven rows will cost a build cycle each if discovered by running the code.

| Fact | Consequence for this service |
|---|---|
| **`WriteTag` is already a batch endpoint.** `[HttpPost] api/v1/OPCConnection/WriteTag` takes an `OPCInfo` whose `Tags` is a `List<OPCTag>`; the handler loops the list server-side | **One POST per push, N tags in the body.** Never N POSTs. This is the whole of "batch write" (`P-103`) |
| **The batch is not atomic.** The handler writes tag-by-tag, so an early failure can leave the first tags landed | This is exactly the partial push `FR-074` compensates. **The partial boundary is per tag, inside one call** |
| ⛔ **A `200` is not evidence.** Both managers catch and log; `OPCUAManager.cs:362` compares two freshly-boxed `object`s with `==` — reference equality, so **false for every numeric tag** — then swallows its own *"Cannot write to tag"* at `LogInformation`. `OPCDAManager` verifies correctly but only logs a `Warning`. Neither sets `IsGood` | **Verify with one batched `ReadTag` and audit the read-back value** (`P-105`). Never audit `Succeeded` on the strength of a status code |
| ⛔ **`OPCInfo.IsReadonly = true` makes the controller echo the tags and write nothing — at `200`.** The flag comes from `CommonDB`, not from the caller | A **configuration-controlled silent no-op** indistinguishable from success. Check it on the resolved `OPCInfo` and **fail the push loudly** before writing (`P-104`) |
| **`GetOPCInfo` must run first.** `MachineId`, `OPCServers`, `ConnectionType` (which selects the DA or UA manager) and `IsReadonly` are read from `CommonDB` via `GetOPCServerAndTagDetails`. An `OPCInfo` cannot be hand-built | Resolve, then write. `GetConfigurationsQuery` is `{ OPCModuleId, MachineIds }` — **`MachineIds` is a list, so all three lines warm in one call.** Cache per line, short TTL (`P-104`, licensed by `phase-01b` L97) |
| **Both routes are `[HttpPost]` behind the global `AuthorizeFilter`, and `WriteTagCommandValidator` requires a non-empty `AccessToken` and `OPC.MachineId > 0`** | Forward the caller's bearer token (`.WithOAuthBearerToken(...)`). ⛔ **A watchdog-driven `SetITInhibit` or hold/restore has no caller token** — **`G59`** |
| **`OPCTag.ValueDataType` must be `typeof(T).FullName`** — the controller does `Convert.ChangeType(Value.ToString(), Type.GetType(ValueDataType))` | `"System.Single"`, never `"float"`. A wrong name makes `Type.GetType` return `null` and throws **before any write**; a null `Value` throws on `.ToString()`. Send the value as a string, as `CoolingChamber` does |
| ⛔ **`ReadTag` swallows exactly like the write.** On a null read or an exception both managers **return the tag unchanged** and log at `LogInformation` (UA) / `Warning` (DA). `OPCDAManager.ReadTag` sets `Value`, `ValueDataType` **and `IsGood`** on success; **`OPCUAManager.ReadTag` never sets `IsGood`** on the single-tag path | **The confirm read must send `Value = null` and treat a null return as *unconfirmed*.** Pre-populating it with what was just written makes a failed read echo your own value back and the comparison **pass falsely** (`P-105`). ⚠ Safe only on the read path: the controller's `Convert.ChangeType` loop runs on **`WriteTag` only** |
| **`OPCTag` equality and `GetHashCode` are `TagName`-only, case-insensitive** | Build the batch as a plain `List<OPCTag>`. **A `HashSet<OPCTag>` or `Distinct()` silently collapses two different values for one path.** A dictionary keyed by `TagName` is the right shape for *matching* the confirm read back, not for building the batch |
| ⛔ **The project graph blocks the transport as specified.** `FlatWire.Infrastructure` references only `Microsoft.EntityFrameworkCore`, `Microsoft.Extensions.Configuration.Json`, `UA.Framework.Infrastructure`, `UAL.Constants` and `FlatWire.Domain` — **no `UA.Framework.RestClient`, no `UA.APIDTO`** — and nothing in FlatWire registers `RestClient` | Add both `<PackageReference>`s (centrally versioned, so no version attribute) and `services.AddScoped<RestClient>();`. **`P-108`** — and see why this is *not* the `P-101` indirection |
| ⛔ **Nothing registers flat wire with `OPCConnection`.** `OPCModules` has five members and no flat wire one, `GetConfigurationsQueryValidator` requires `OPCModuleId > 0`, and no script writes `OPCModules`/`OPCServers`/`OPCTags`/`OPCTagApplicationMapping` | **`GetOPCInfo` cannot succeed today.** Not a build blocker — simulate mode short-circuits before it — but a **commissioning** blocker that nothing owns: **`G60`** |

> ⚠ **`CoolingChamber`'s `OpcHelper` is the only existing consumer and it does not match this
> contract** — it calls `GetOPCInfo` with `GetAsync()` and query parameters against a
> `[HttpPost]` / `[FromBody]` route, and sends a module *name* where the query takes an
> `OPCModuleId` int. **Copy its shape** (resolve → set `Tags` → `WriteTag` with the token),
> **not its calls**, and read the controller for the contract. ⚠ **Do not copy its error
> handling either** — it catches, logs and returns `null`, which is the opposite of what
> `FW-082` `P-41` and `G29` require.

> ⚠ **`OI-A` lands here, and it is deferred rather than closed.** The ecosystem keeps tag paths
> in `CommonDB.OPCTags`, so `GetOPCInfo` returns a *registered* tag set — while `FR-022` puts
> our map in `appsettings`. **This service builds its `Tags` from `ITagPathResolver` and
> overwrites whatever `GetOPCInfo` returned**, which is also what `OpcHelper` does. That keeps
> `FW-144`'s seam intact and needs no `OPCTags` seeding; if the `CommonDB` registration later
> wins, it is one implementation of `ITagPathResolver` and no change here.

**`ITagPathResolver.Resolve` throws `KeyNotFoundException` for an unconfigured path, deliberately.**
Let it propagate. **Do not `TryResolve`-and-skip** — `G29` is the live case (edge type is in the
push payload and no edger tag path exists on any line) and `FW-082` `P-41` requires that push to
fail loudly rather than ship a machine configured without it.

## 3. Build order

0. ⛔ **Two `<PackageReference>` lines and one DI line, first — nothing below compiles without
   them** (`P-108`). `Infrastructure.csproj` gains `UA.Framework.RestClient` and `UA.APIDTO`
   (both centrally versioned in `API/Directory.Packages.props`, so **no `Version` attribute**),
   and `AddPersistence` gains `services.AddScoped<RestClient>();`. **No `AddHttpClient`
   prerequisite** — neither sibling has one.
1. `FlatWire.Infrastructure/Services/PLCTagService.cs` behind an interface in
   `FlatWire.Domain/Services/` — beside `IAuditLog` and `ITagPathResolver`, and for the same
   reason. **The five operations of §1.1**, each carrying operator and run context (`P-106`) and
   each returning a per-tag result the caller can stamp (§2.2). **Paths from
   `ITagPathResolver`, never from configuration directly and never from code.**
2. One private transport: **resolve `OPCInfo` (cached) → build `Tags` as a plain `List<OPCTag>`
   → one `WriteTag` POST** (§2.5). Reach `OPCConnection` through `RestClient` with the caller's
   bearer token; `InternalServices.OPCConnectionService` is bound in `Program.cs` already.
   ⚠ **`OPCManagerHub.cs` is not a template** (`D-05`), and neither is `OpcHelper` (§2.5).
3. `SimulatePLCTagPush` branch **before the resolve, not merely before the write** — log the write
   that would have been made, make no call at all, return (§2.3). ⛔ **This is what makes the
   story buildable today**: `GetOPCInfo` cannot succeed until flat wire is registered in
   `CommonDB` (`G60`), and the flag is `true` in every environment until commissioning.
   ⚠ **The branch returns after step 4, not before it.** `[PLC §11.1]` audits every write *"no
   exceptions, including simulated writes, which log the write they would have made"* — so a
   simulated push still writes its `Attempted` and `Succeeded` records, with
   `AuditEntry.Simulated = true`. Ordering the branch ahead of the audit would drop the trail in
   the one mode that is on in **every** environment, which is the whole reason the audit path is
   exercisable before `C1`.
4. Audit **before** the push, as `Attempted` pairs, per §2.2 — on **both** branches.
5. Polly around the real outbound call only — transport faults and timeout, never a status code
   (§2.4).
6. **The confirm read** — one batched `ReadTag` on the paths just written, **with `Value = null`
   as the sentinel**; a null return is *unconfirmed*, a disagreeing value is a **failure**. Audit
   the read-back value, not the HTTP status (`P-105`). **Excludes `ITInhibit`, which is
   write-only.** Skipped entirely in simulate mode.
7. The compensation path and the boundary comment — **the three steps in §2.1**, and the sentence
   that says where this service's compensation stops and `FR-526`'s single transaction begins
   (AC 4).
8. Expose `SetITInhibit` for [`FW-205`](FW-205.md), keyed under
   `Lines.FL{n}.Tags` and never at the root (`[PLCC §1.6]`).

## 4. Decisions this plan makes

> `P-##` is continuous across this folder; new decisions mint at **`P-113`+**.

### `P-27` — build the write surface now — **RESTATED 28 Aug 2026: the compensation shape is no longer blocked**

The **write surface** was never blocked. `[PLCC §4]` says build in Phase 1, exercise in Phase 4,
and every later phase assumes the operations exist. Build all of them.

~~What is blocked is the compensation design — `G2`/`OI-39` has not decided between a saga/outbox
and an `INFLAT` mirror.~~ **Both halves of that sentence have since been overtaken:**

- **`D-32` (18 Aug 2026)** removed the `INFLAT`-mirror *option* by removing the shared status it
  was an option about. `INFLAT` is a `FlatWireDB`-local `Rod.Status` value, so the mirror is not
  an alternative — it is simply where the marker lives.
- **`[ARC §10]` / `FR-526` (19 Aug 2026, `FW-220`)** removed the cross-database half. The two
  databases are co-located and commit together, so **there is nothing to compensate between
  them**, and the recovery that remains is the three steps in §2.1.

So: **implement the three-step compensation, and document the boundary as `FR-526`'s single
transaction on one side and the PLC push on the other.** Do not implement a cross-database saga
— there is nothing for it to span. The **24–64 h Phase-4 reserve** stands until `OI-39` closes
formally, but `[ARC §10]` already asks for it to be **re-derived before S2 planning**: its
cross-database portion is spent and its PLC portion is not.

`G30` still bears on this, and now it is the *only* thing that does: it decides whether FM2 on
FL3 is one failure domain or two, which changes **how many controllers a compensating clear must
reach** — not what the clear does.

### `P-103` — five operations, one transport, one mode

`phase-01b` L108 counts six, `[PLC §7.1]` and `[PLCC §1]` count five, and the two fives are not
the same five. Build **five real operations** (§1.1). **"Batch write" is the transport** — one
`WriteTag` POST carrying `OPCInfo.Tags`, used by all five — and **"simulated push" is a mode**,
one branch inside that transport. Building either as its own method creates a second write path,
and the second path is where the audit, the token, the `IsReadonly` check and the confirm read
get forgotten. ⚠ **`SetITInhibit` is the operation both five-row tables omit** and `[PLC §8]`
requires; the tables are short by one, not this plan.

### `P-104` — resolve `OPCInfo` first, cache it per line, and treat `IsReadonly` as a failure

An `OPCInfo` cannot be constructed by the caller: `MachineId`, `OPCServers`, `ConnectionType` and
`IsReadonly` are `CommonDB` state that `GetOPCInfo` returns, `WriteTagCommandValidator` rejects
`MachineId <= 0`, and `ConnectionType` is what selects the DA or UA manager. So every write is
**resolve, then write**.

**Cache it.** The resolved `OPCInfo` is effectively static — machine, servers, connection type —
and `phase-01b` L97 already licenses *"short-lived memory cache for lookup tables."* Uncached,
every operator action costs an extra HTTP hop **and** a `CommonDB` stored-procedure round trip on
a shared instance. `MachineIds` is a list, so **one call warms all three lines**; a short TTL is
enough, because a change there is a commissioning-window event, not a runtime one.

⛔ **And `IsReadonly = true` is a hard failure, not a skip.** The controller returns the tags
unchanged at `200` and writes nothing — a configuration-controlled silent no-op that looks
exactly like a successful push. Check it on the resolved `OPCInfo`, audit `Failed` with the
reason, and raise `PLC_PUSH_FAILED`. Left unchecked it is the one silent failure in this story
that has nothing to do with commissioning.

> ⛔ **Added on re-review: this decision has an unbuilt precondition, and it is a *commissioning*
> blocker rather than a build one — `G60`.** `OPCModules` has five members (`None`,
> `HoleDetection`, `CoilReceiving`, `HandheldService`, `FurnaceScheduling`) and **no flat wire
> one**, while `GetConfigurationsQueryValidator` requires `OPCModuleId > 0`; and **none of the
> eight files in `Database/Scripts/` touches `OPCModules`, `OPCServers`, `OPCTags` or
> `OPCTagApplicationMapping`** — `10_CommonDB_Insert_WIPStations_FlatWire.sql` registers WIP
> stations and machines only. So `GetOPCInfo` returns an empty list and `WriteTag` cannot be
> called at all. **The build proceeds anyway** because `SimulatePLCTagPush` is `true` in every
> environment until commissioning and step 3's branch sits **before** the resolve — but the
> resolve path is then **unexercised until the 40 h Phase-14 window**, which is the worst
> compression in the schedule. Raise `G60` now, not at `C1`.

### `P-105` — a `200` is not evidence: confirm with one batched `ReadTag` and audit the read-back

⛔ **Forced by the code, not chosen.** `FR-074` requires an exception when *any individual tag
write fails*, and the response cannot support it:

- `OPCConnectionController.WriteTag` returns `200` with the tag list whatever happened.
- `OPCUAManager.WriteTag` catches **every** exception — including its own *"Cannot write to
  tag"* — and logs it at **`LogInformation`**. Worse, its verification at line 362 compares
  `Convert.ChangeType(...) == Convert.ChangeType(...)`, two freshly-boxed `object`s, which is
  **reference equality and false for every numeric tag**: the write is issued, the check always
  says failure, and the failure is swallowed.
- `OPCDAManager.WriteTag` verifies correctly (`.Equals`) but only logs a `Warning`, and returns
  the read-back tag rather than a status — so **the two managers disagree about what the response
  means**, and `ConnectionType` decides which one you get.
- `OPCTag.IsGood` is set by neither write path. It comes back `null`.

**So: after a real push, issue one batched `ReadTag` on the paths just written, compare, and put
the read-back value in the audit record.** One extra round trip per operator action — check-in,
roll adjust, checkout, pause — all of which are human-paced; **this is not the 10 Hz path and
must never be put on it** (that is `FW-N05`'s subscription). Skipped entirely in simulate mode.

> ### ⛔ Restated on re-review — two things without which this mechanism confirms nothing
>
> **1. `Value = null` is the sentinel, and it is load-bearing.** `ReadTag` swallows exactly like
> the write: on a null read or an exception **both managers return the tag unchanged**. So a
> confirm read sent tags pre-populated with the values just written **echoes your own value back
> on failure and the comparison passes falsely** — the mechanism would look implemented, run on
> every push, and report success unconditionally. **Send `Value = null`. A null return is
> *unconfirmed*; a value that disagrees is a *failure*.** ⚠ This is safe on the read path and
> only there: the controller's `Convert.ChangeType(Value.ToString(), …)` loop runs on
> **`WriteTag`**, so a null `Value` throws on a write and is harmless on a read.
> ⚠ **`IsGood` cannot be the primary test** — `OPCDAManager.ReadTag` sets it from
> `tagValue.Quality.IsGood`, `OPCUAManager.ReadTag` **never sets it** on the single-tag path
> (only the subscription path does), so it is a bonus signal on DA and always `null` on UA.
> ⚠ **Compare the value converted to the type that was written**, not the `ValueDataType`
> strings — the read returns the *server's* type name, which need not match what was sent.
>
> **2. `ITInhibit` is write-only, so `SetITInhibit` is excluded by construction.**
> `phase-01b` L112 and `[PLC §8.1]`: one tag per line, **written, never read**. Everything else in
> the write surface is a setpoint that reads back. Do not build a general "confirm every write"
> loop that then needs a special case — exclude the interlock where the operation is defined.
> ⚠ **`G29`'s edge type needs no exclusion**: there is no path at all, so `ITagPathResolver`
> throws before anything is written.

⚠ **This does not close `G33`.** A wrong path can read back consistently wrong, and
`[PLC §10.3]` is explicit that *"a tag push actually configures the machine"* cannot be proven
before commissioning. It closes the narrower and far more common case: a write the controller
refused. **The better fix is per-tag status from `OPCConnection`** — that is another service's
change and is raised as **`G58`**.

⚠ **Do not "fix" `OPCUAManager` from this story.** It is a shared service on four other
consumers' paths; raise it, do not edit it.

### `P-106` — the operations carry operator and run context

`[PLCC §1]`'s signatures are `PushPassSchedule(scheduleId, lineId, payoffPosition)` and
`ClearPayoffTags(lineId, payoffPosition)`. **`AuditEntry` requires `OperatorId` and queries on
`RunAlpha`** — `FW-143` AC 3's two keys — and `FR-075` requires the operator on every write. So
as written the signatures **cannot produce a compliant audit record**, and an audit trail whose
records are unattributable has no compliance value.

Add the context; do not thread it through a static or an `IHttpContextAccessor` reach-around,
because operations 4 and 5 are raised from a hosted service where there is no HTTP context to
reach (see `G59`). **Keep `scheduleId` / `lineId` / `payoffPosition` exactly as `[PLCC §1]` names
them** — those are cited by `phase-04`, `FW-082` and `FW-157`.

### `P-107` — the `rollback` check is scoped to this service's PLC path

AC 3's *"the word rollback does not appear"* is a design rule about **machine** writes, and a
solution-wide `grep` refutes it for the wrong reasons: `FlatWireDbContext.RollbackTransaction()`
is a **correct** database rollback on a genuinely transactional resource; `IAuditLog`'s own
remarks use the word in order to forbid it; `[PLC §10.4]` uses it for **configuration** rollback.
**Scope the check to `PLCTagService.cs`, its interface, and the strings it logs or audits.** An
unscoped grep gets dismissed as noise the first time it is run — or, worse, gets someone to
rename a correct EF Core API.

### `P-108` — add the two package references and register `RestClient`; do **not** reach for `P-101`'s indirection

⛔ **Found by re-reading the project graph before execution, and it stops the build on day one.**
`FlatWire.Infrastructure` — where AC 1 puts `PLCTagService.cs` — references only
`Microsoft.EntityFrameworkCore`, `Microsoft.Extensions.Configuration.Json`,
`UA.Framework.Infrastructure`, `UAL.Constants` and `FlatWire.Domain`. It can name **neither
`RestClient` nor `OPCInfo`/`OPCTag`**. And **nothing in FlatWire registers `RestClient`**:
`FW-140 §2.1`'s *"`AddPersistence` … registers `RestClient` — the hook FlatWire uses to reach
`API.OPCConnection`"* is a true statement about **`CoilCheckin`'s** copy
(`services.AddScoped<RestClient, RestClient>()`), and the built FlatWire `AddPersistence`
registers `IContextRepository`, `IAuditLog`, seven repositories and twelve service pairs and no
HTTP client at all. `FW-148` never tripped over it because `OpcHealthCheck` deliberately used a
named `IHttpClientFactory` client instead.

**Three lines:** `<PackageReference Include="UA.Framework.RestClient" />` and
`<PackageReference Include="UA.APIDTO" />` in `Infrastructure.csproj` — **no `Version`
attribute**, both are `PackageVersion`-pinned at 1.0.0 in `API/Directory.Packages.props` — and
`services.AddScoped<RestClient>();` in `AddPersistence`. **No `AddHttpClient` prerequisite**;
`CoolingChamber` and `CoilCheckin` both register the bare type.

⚠ **This is deliberately not the `P-101` treatment, and the distinction matters because the two
cases look identical.** `P-101` had to mint a Domain-side abstraction because `IHubContext<>`
lives in the **ASP.NET Core shared framework**, which a `Microsoft.NET.Sdk` class library cannot
reference *at all* — no `PackageReference` fixes it. `RestClient` and `UA.APIDTO` are ordinary

reference is the correct answer and an extra interface would be indirection bought for nothing.
⚠ **`P-02` is not weakened** — the added references are packages, not a project reference, so
`Infrastructure → Domain` still holds.


### `P-109` — the Polly retry is on the RESULT, not on an exception

⛔ **Forced by `RestClient`, and found on execution.** Its `SendAsync` catches **every** exception
and returns `Result.Fail`, so `OpcHealthCheck`'s `Policy.Handle<HttpRequestException>()
.Or<TaskCanceledException>()` — the precedent §2.4 told the developer to match — **would never have
fired through `RestClient`**. Every retry would have been silently dead while the code looked
correct.

The policy is `Policy.HandleResult<Result<HttpResponseMessage>>(r => r.IsFailure)`, and the split
falls out exactly as `phase-01b` L97 wants it: **`Result.IsFailure` means the call never
completed** (a dropped packet — retry once), while **a non-2xx arrives as `IsSuccess` with a status
code** (a rejected write — never retried, or it is the same write twice). ⚠ Any future outbound call
from this service inherits the trap; the exception-based shape belongs to raw `HttpClient` only.

### `P-110` — the compensating re-clear writes FLAGS false, leaves analogues alone, and says it is a compensation

Three parts, and the first is a machine-safety call.

⛔ **`[PLC §7.1]` says a clear "resets to idle and bypass defaults" and `[PLC]` publishes no default
table.** Guessing `0` for an analogue is not neutral: **writing `0` to a roll gap is a physical
command to close the rolls** on a mill that may still be threaded. So the re-clear writes the
**component active/bypass flags `false`** — a bypassed stand's gap is irrelevant — and **touches no
setpoint**. The missing default table is raised rather than guessed (§7).

**It re-clears everything that was sent, not "the tags that landed"**, because `G58` means
`OPCConnection` does not say which landed. Re-clearing a tag that never took the value is harmless;
leaving one set is a half-configured mill.

**And it carries its own audit label** — `Compensate:{group}` on the `PlcTagsCleared` sink — because
`[PLC §11.3]` expects a reviewer to establish *whether* tags were cleared and after what; a
compensation indistinguishable from an operator's checkout clear defeats that. ⚠ It is therefore
**not** routed through `ClearPayoffTagsAsync`, which would also have needed a payoff position this
failure does not have.

### `P-111` — resolve every path BEFORE writing anything, and convert the resolver's throw

Two halves, both about not making a bad situation worse.

**Resolve-all-first** means an unconfigured path fails the push with **zero tags written** — so
there is no partial push and nothing to compensate. The alternative resolves lazily and discovers
the gap after N tags have landed. `G29` is the live case, and there is no gauge-target, width-target
or drive-enable key on **any** line, so this path is reachable today.

**The `KeyNotFoundException` is converted to a named failure result, not propagated.** `ITagPathResolver`
throws by design and §2.5 says to let it fail loudly — but propagating reaches `FW-146`'s `default`
arm as `500 INTERNAL_ERROR`, **indistinguishable from a null-reference bug**, which is exactly the
`P-89` problem. The push still fails; the caller gets a reason naming the logical name and the
configuration location, and raises `PLC_PUSH_FAILED` itself. ⚠ This is not `TryResolve`-and-skip:
nothing is dropped and no push proceeds partially configured.

### `P-112` — the payload is the CALLER's, and an unverified value says so in the trail

**`PushPassSchedule` cannot read a schedule.** MVP-1 never authors one and has no
`PassScheduleRepository` (`P-12`, `P-13`), so `[PLCC §1]`'s `scheduleId` can only be **audit
identity**: `FW-082` resolves `[PLC §7.2]`'s six value groups and passes them in. The three cited
parameter names are kept and a `Values` list added beside them.

**And the trail marks what it does not know.** The harness caught the first build auditing an
`Unconfirmed` tag as `Succeeded value=0.0325` — the *"a green trail is not proof"* problem written
into the trail itself. An unverified value is now recorded `0.0325 (unconfirmed)`. ⚠ The marker
rides on the value **string** because `AuditEntry` is `FW-143`'s type and has no confirmation field;
that costs nothing, because the trail's query keys are `RunAlpha` and `OperatorId`.
