### 1.1a ⛔ Three defects in the built code, and this story is what fixes them

Not a criticism of `FW-203` — each is a consequence of a *synthetic feed* standing in for a *model*,
which is precisely the gap this story closes. Each is also a way to build this story wrong.

**1 · Gauge is published where the roll gap belongs.** `BuildComponents` computes
`gauge = NominalFor(line).GaugeIn + sim.GaugeOffsetIn` (`:458`) and writes it into
`CurrentValue` on `FM1` (`:478`) and `FM2_S3` (`:469`). But `Reading.cs:141` defines that field as
**the roll gap** for a mill stand. Gap-equals-gauge is the no-mill-spring case, so **AC 6's sign
error is currently shipped** — and `D-26` with `[PSG §3.3.11]` additionally make `FM2_S3` a **skim**
stand rather than the gauge stand.

**2 · `lbPerFt` is a compiled literal.** `BuildPayoffs` is `sim.FootageFt * 0.0075m` (`:413`).
Two standing rules break at once, and both are stated in that same codebase:
`AlloyProperty.LbPerFtFactor` is **"Do not populate … a scalar lb/ft is the wrong shape"**
(`MasterSpecification.md:1364`), and *"Do not compile a default"* is asserted twice citing that very
column (`SpcService.cs:61`, `IContextRepository.cs:88`). `P-271` settles it.

**3 · FL3 is not a third model — it falls through to FL1's.** `BuildComponents` special-cases only
FL2 (`if (line == LineId.FL2)`, `:460`), so **FL3 publishes `DB1`/`DB2`/`FM1` and no FM2 stand at
all**, while `Nominal[FL3]` (`:98`) is FL2's *output* gauge — reported on `FM1`. FL3 is FL1 feeding
FL2 with no intermediate anneal: the whole chain, and speeds coupled through it (`[SIM §4.3]`,
`[SIM §5.6]` A10). ⚠ This is the clearest available demonstration of what AC 2's *"three distinct
models, not three instances of one"* is protecting against — **a parameterised model already
produced it**.

⚠ **A fourth, and it is `[SIM §3.2]`'s, not the code's.** The sketched interface has **no member
that `steer` maps onto**. `[SIM §8.1]` specifies `POST /sim/{lineId}/steer` as *"change speed
setpoint, targets or drift mid-run"*, `FW-218` already ships `Steer(line, gaugeOffsetIn,
driftPerTickIn)`, and `ApplyConfiguration`/`ApplyScenario`/`InjectFault`/`SetRunState` cannot
express any of it. `P-269` closes the hole.

## 2. What makes them three models rather than one

The card asserts it; this section is why it is structural rather than stylistic. **Each line differs
in what instruments it has, not in a parameter value** — which is what makes a shared parameterised
model produce §1.1a defect 3 on its own.

### 2.1 The three chains

| | Chain | Components published | Live gauge |
|---|---|---|---|
| **FL1** | rod → `DB1` → `DB2` → `FM1` → intermediate spool | `DB1` `DB2` `FM1`. ⚠ **No edger** — FL1 has none | Real-time |
| **FL2** | pre-flattened spool → `FM2_S1` → `FM2_S2` → `FM2_S3` → coreless coil | `FM2_S1` `FM2_S2` `FM2_S3` `EdgeSet`. Edgers at S2/S3 only; **S3 is final and non-bypassable** | ⛔ **None — no instrument** |
| **FL3** | FL1 feeding FL2 continuously, **no intermediate anneal** | **The whole chain**: `DB1` `DB2` `FM1` `FM2_S1` `FM2_S2` `FM2_S3` `EdgeSet` | Real-time |

**FL3 is one run**, one `FlatWireRun` row with `RouteMode='Hybrid'`
(`CK_FlatWireRun_RouteMode`, `FlatWire_DDL_03_Materials.sql:114`), and one batched PLC push on one
acknowledgement — **not two models chained.** Mass flow couples the speeds: `FM1`'s exit speed sets
`FM2_S1`'s entry speed and the rest derives from the reduction chain (`[SIM §5.6]` A10). ⚠ Whether
the push reaches one controller or two is `PLC-Q08`/`G30` and is **a configuration value in the
model, never a special case in code** — the same instruction `[PLCC §1.6]` gives for `ITInhibit`.

### 2.2 ⛔ FL2's gauge absence is structural, and that is what retires the last FL2 branch

This is the subtlest thing in the story and the card gets it half right.

`OpcFeedSimulator.cs:337` is `SuppressesGaugeAndWidth(line) => line == LineId.FL2`. That is an
`if (line == FL2)` **in a producer**, and three built sources call exactly that a defect:
`Reading.cs:50` — *"There is NO FL2 BRANCH on this type **or in its producer**, and adding one would
be a defect"*; `FW-N05 §2.5` — *"Never write `if (line == FL2)` anywhere in this service"*; and
`FW-181 §2.1`, re-reviewed against the built loop, with its own verification step being a `grep` for
it.

The reason it is a defect is that in the real system **the absence is not a rule, it is a missing
instrument**: `[PLC §5.2.2]` publishes no `AGC` row for FL2 at all (assumption A3), so no sample is
ever produced and `FW-150`'s *"no sample, no send"* **is** `[SIG §5.3]`'s suppression *"entirely"*.

**Three distinct models reproduce that structurally.** `Fl2LineModel` has no live gauge instrument,
so it emits none, and the branch disappears without a special case. **This is the single strongest
argument for AC 2**, and it is why `P-270` is worded as a deletion rather than a rewrite.

⛔ **What the card gets wrong is the destination of the internal gauge.** AC 3 ends *"Gauge is still
computed internally for the `RunReading` profile"*, inherited from `[SIM §4.2]:196`. It is real that
FL2's model must compute gauge internally — for the roll gap of §2.3, for the width target, and for
the weight fallback of `P-271`. But **not for that table**:

- `FW-181 §3` makes FL2's Profile **the incoming spool's FL1 history** on a footage x-axis, served
  by the REST `gaugetrace` read (`FW-164`) — **not the FL2 run's own rows**.
- A simulator that filled `RunReading.GaugeIn` on FL2 would produce data **the real feed
  structurally cannot**, breaking `P-37`'s *"`FW-150` and `FW-151` must not be able to tell whether
  the feed is real"* — the one rule the whole simulator exists to preserve.
- The built loop already handles the absence correctly and must stay untouched:
  `BroadcastLoopService.cs:789` returns `InSpec = true` when gauge is absent, *"a snapshot with no
  gauge is still in spec"*, so FL2 rows are written with `GaugeIn` and `WidthIn` **NULL** rather
  than skipped.

⚠ **`[SIM §4.2]`'s sentence is stale**, and §7 records the amendment as owed.

⚠ **AC 3's channel list is also one item too long.** It names `PayoffWeight` among what still flows
on FL2. `FW-181 §2` already corrected the identical clause in **its own** AC 1: `PercentRemaining`'s
denominator is the staged rod's net weight from `RodStaging`, which is **FL1/FL3 only** — FL2 feeds
from a spool. `FW-150` logs it once per bay and calls it *"a real gap rather than a bug here"*.
**Do not close it by inventing a denominator.** The honest reading of AC 3 is *the line keeps
ticking*, and speed, footage, component state and line status are what prove it.

### 2.3 Mill spring — the direction, and the requirement that actually says so

The set roll gap sits **below** the delivered gauge. The gaugemeter relation is
`h₁ = S₀ + F/K` (`[PSG §3.3.7]`): to deliver 0.110″ against a 0.004″ deflection the gap is set to
**0.106″**, and because `F/K` is **load-dependent** no fixed percentage can express it.

⛔ **AC 6 cites the wrong requirement.** `FR-386` (`MasterSpecification.md:1085`) is the
FM2-activation / route-mode rule — aspect ratio `> 5.5` or alloy `1350` → activate FM2 — and it
carries **no gauge multiplier at all**. The alloy springback multiplier is **`FR-385`** (FM1 gap
`= gauge × alloy springback factor`) and **`FR-387`** (FM2 `S1 × 1.06`, `S2 × 1.02`,
`S3 × springback`), and §10.5's arbitration row is `FR-385`/`FR-387`
(`MasterSpecification.md:3220`). ⚠ The error originates in `[SIM §5.5]:278` and is repeated in
`[TB §7]:1033` and on this card; `[SIM §5.6]` row A5 states the basis correctly and without an FR
id. §7 records the amendment as owed.

**Get the sign right** — springback-as-an-alloy-multiplier placing the gap *above* gauge is the
error §10.5 exists to correct, a machine stiffness misfiled as a material property. **A simple
load-proportional term; do not compute rolling force** (`[SIM §5.6]` A9).

   ⛔ **`CurrentValue` becomes the gap and stops being the gauge** on `FM1` and every `FM2_S*` —

   *appends* to collections, and a compiled default here is exactly what
   `MasterSpecification.md:1364` and `SpcService.cs:61` forbid.

6. **Swap `LineSim` out of `OpcFeedSimulator`, keeping the type name and both registrations**
   (`P-266`). `ExecuteAsync`, `ResolveLines`, the `PeriodicTimer` and the cadence all stay.
   `Compose`, `BuildPayoffs` and `BuildComponents` **collapse into `Tick`** — they are the
   kinematics, and they belong in the models. `PublishTick` keeps the drop-tick check and the
   `channel.TryWrite`. ⚠ **Both registrations survive** — concrete singleton *and* hosted service

## 4. Decisions this plan makes

`P-268`–`P-274` are minted here and defined **once**, in this section.
[`Orchestration.md`](Orchestration.md) §4a carries pointers only.

### `P-268` — `Tick` returns `Reading`; `LineModelSnapshot` is not minted, and `Line` is the enum

**Settled, and it is the same finding as `P-265` one interface over.** `[SIM §3.2]` sketches
`LineModelSnapshot Tick(TimeSpan elapsed)`. But `Reading` **is** that snapshot: `Reading.cs:14`
opens *"ONE RECORD PER LINE PER TICK — a SNAPSHOT, not a tag sample"*, it lives in
`FlatWire.Domain/Models/RealTime/`, and it depends on nothing but the enums — so returning it
violates AC 1's *"no infrastructure dependency"* not at all.

Minting `LineModelSnapshot` would create **a second contract for one fact** and a mapping layer
between them on the hot path, at the cadence, forever. `[SIM §2.1]` forbids the simulator adding a
type of its own in terms, and `Reading.cs:23` states the corollary from the other side: *"the
contract is frozen before its producer exists — if the simulator needs a change here, the contract
is wrong."* The right reading is that the contract does **not** need a change: it already has the
shape `Tick` wants.

**Declining it deletes a layer rather than adding one**, which is the whole reason this decision is
worth taking rather than following the sketch.

⚠ **And `Line` is `LineId`, not `string`.** `[SIM §3.2]` has `string LineId { get; }`, written before
`ual-api` existed; `LineId` is an enum everywhere in that codebase — `Reading.Line`,
`IReadingChannel`, `ITagPathResolver`, `SimLineState`, `CK_FlatWireRun_LineId`. A string would
reintroduce parsing at every call site and collide with the type name.

### `P-269` — `ILineModel` gains one steer member, because the sketched five cannot express `/steer`

**Settled.** `[SIM §8.1]` specifies `POST /sim/{lineId}/steer` as *"change speed setpoint, targets
or drift mid-run"*, and `FW-218` has **already shipped** `Steer(line, gaugeOffsetIn,
driftPerTickIn)` against a live control surface. `[SIM §3.2]`'s five mutators cannot carry it:
`ApplyConfiguration` takes a whole pass-schedule push, `ApplyScenario` selects a run shape,
`InjectFault` injects a fault and `SetRunState` moves the state machine. **A real hole in the
contract, not a preference.**

One member, one parameter object — speed setpoint, gauge and width target nudges, drift per tick,
each optional. ⚠ **`[SIM §2.1]` is not violated by this.** That rule forbids the simulator adding
an interface *to the contracts* — `IFlatWireClient`, the `[SIG §5.2]` event set, the shape of a
`Reading`. `ILineModel` is itself sanctioned by `[SIM §3.2]`, and a member on it changes nothing any
consumer sees.

⚠ **The adapter, not the model, owns the echo** (`P-267`). The model holds a target and an actual;
the commanded offset and drift are `OpcFeedSimulator`'s to retain and hand back through `Peek`.

### `P-270` — FL2's gauge absence is structural in the FL2 model, and the FL2 branch is deleted

**Settled.** `SuppressesGaugeAndWidth(line) => line == LineId.FL2` (`:337`) is the last surviving
`if (line == FL2)` in a producer, and `Reading.cs:50`, `FW-N05 §2.5` and `FW-181 §2.1` each call
that a defect. It exists only because a *synthetic feed* had to imitate an absence it could not
have structurally; a *model* can have it structurally, because `Fl2LineModel` simply has no live
gauge instrument (§2.2).

**So the branch is deleted, not relocated.** That is also the clearest single answer to *why three
models* — the alternative is a parameter that says "this line's gauge is off", which is the same
`if` wearing a different hat.

⛔ **And the internally computed gauge does not reach `RunReading`.** AC 3's last clause and
`[SIM §4.2]:196` both name that destination and both are wrong: FL2's Profile is the **inbound
spool's FL1 history** over REST (`FW-181 §3`, `FW-164`), and filling `RunReading.GaugeIn` on FL2
would put data on the wire that the real feed structurally cannot produce — `P-37`'s one rule.
The internal gauge serves the roll gap, the width target and `P-271`'s weight fallback. **Nothing
else.**

### `P-271` — `lbPerFt` is configuration with no code default; absent means a null weight

**Settled, and the card names the wrong home.** AC 5's *"read from configuration and never a
constant"* is right in direction and the built code breaks it — `sim.FootageFt * 0.0075m` (`:413`).
But two things have moved under the card:

- **A scalar lb/ft is the wrong shape.** `AlloyProperty.LbPerFtFactor` is seeded NULL and marked
  **"Do not populate … a scalar lb/ft is the wrong shape"** (`MasterSpecification.md:1364`), and
  *"Do not compile a default"* is asserted twice against that column (`SpcService.cs:61`,
  `IContextRepository.cs:88`).
- **`Q10` carries no recommendation, but the formula does not need one.** `FR-332` settles the
  calculation as `A(in²) × 12ρ` per foot with a round-edge correction and ρ =
  `united_db..alloys.alloy_density` (`MasterSpecification.md:1012`). `OI-45` records **the formula
  and the density source as settled**, with only the **dimensional basis** open — and integration
  over `RunReading` recommended (`:3261`, `:1422`).

**This model does not implement `FR-332`.** It reads one configured `lbPerFt` for **payoff-weight
telemetry**, with **no C# default**, and when it is absent it publishes `WeightLb = null` — which
the `Reading` contract already means *"not read"*, and which the panel renders honestly as no
reading. The trial's value is a **seeded, labelled assumption** — `[SIM §5.6]` row A2 — surfaced on
the console per `[SIM §9.2]`, and a values-only configuration edit when the basis lands.

⛔ **It is never the basis of a persisted completion weight.** That number is `FR-332`/`OI-45`'s and
belongs to [`FW-202`](FW-202.md); a telemetry estimate leaking into it is how one open question
would silently acquire two answers.

### `P-272` — the roll gap is published below gauge, and `CurrentValue` stops carrying gauge

**Settled.** One load-proportional mill-spring term, gap below gauge, per `[PSG §3.3.7]`'s
`h₁ = S₀ + F/K` and master spec §10.5 (§2.3). ⛔ **The requirement §10.5 arbitrates against is
`FR-385`/`FR-387`, not `FR-386`** — the card, `[TB §7]:1033` and `[SIM §5.5]:278` all carry the wrong
id, and §7 records the amendment.

The code change is the one in §1.1a defect 1: `FM1` and every `FM2_S*` publish the **gap** in
`CurrentValue`, not the gauge. Die blocks keep publishing die diameter there. ⚠ **No rolling force
is computed** (`[SIM §5.6]` A9, permanent), and `FM2_S3` is a **skim** stand
(`D-26`, `[PSG §3.3.11]`) — not the gauge stand `FR-387` treats it as.

### `P-273` — FL3 is a third model with the full chain and coupled speeds

**Settled, and it is a defect fix rather than a new feature.** FL3 today falls through to FL1's
component branch and publishes no FM2 stand at all, on FL2's nominal gauge (§1.1a defect 3).
`Fl3LineModel` publishes the whole chain — `DB1` `DB2` `FM1` `FM2_S1` `FM2_S2` `FM2_S3` `EdgeSet` —
as **one run** with `RouteMode='Hybrid'`, and derives stand speeds from the reduction chain rather
than driving each independently (`[SIM §4.3]`, `[SIM §5.6]` A10).

⚠ **FL3 is not suppressed.** The hybrid route is real-time and drives the same FM2, so suppressing
it by pattern-matching *"anything with FM2"* would silence the hybrid gauge — which is
`FW-181` AC 5's whole point, and the reason `RouteMode` rather than `lineId` is the discriminator
(`P-49`).

⚠ **The controller topology stays configuration.** `PLC-Q08`/`G30` is unresolved; whether the push
reaches one controller or two is a configured value in the model, **never a special case in code**.

### `P-274` — `SetRunState`'s four states project onto `SimLineState.Running` as `state == Running`

**Settled.** `[SIM §3.2]` gives `SetRunState` four values — `Idle|Running|Paused|Stopped` — while
`SimLineState.Running` is a **bool** that `FW-218` shipped and `FW-214` was designed against, and
`[SIM §9.2]` says **"do not widen `SimLineState`"**. So the projection is `Running` ⇔
`state == SimRunState.Running`, and `Idle`, `Paused` and `Stopped` all echo `false`.

⚠ **That is lossy on purpose.** The four-state machine is what the model needs to keep **run status
separate from line state** (`[SIM §4.4]`) — a mill can stop with the run still `Running`, which is
`FR-141`'s edge. The six-field record is a **command echo**, not a telemetry surface: run status,
line state and everything else reach the console as `[SIG §5.2]` events 1–7 over the hub. Widening
the record to carry the fourth state would be *"a second telemetry path competing with the hub"*.

### `P-275` — FL3's speeds couple on the GAUGE ratio only, never on gauge × width

**Settled, and the first implementation had it backwards.** Volume is conserved through the chain, so
the take-up runs faster than FM1's exit — but by the ratio of the **gauges**, not of the
cross-sections.

⛔ **`[SIM §5.6]` A8 is the reason, and it is a permanent simplification**: *"lateral spread is
ignored; width is targeted directly"*. Width in this model is a **setpoint**, not a rolling
consequence, so putting it into a conservation term treats a target as though it were measured
spread. A10's wording is *"the reduction chain"*, and the reduction is in gauge.

⚠ **The trial fixtures make the error concrete and it is worth recording.** 0.1100 × 0.5000 is
**0.05500 in²** and 0.1000 × 0.5600 is **0.05600 in²** — so a cross-section term has the area *grow*
through the finishing mill, and the take-up came out **slower than its own entry**. That is not a
rounding artefact; it is what A8 exists to keep out of the model. Gauge-only gives 1320 fpm against
FL1's 1200 at the same setpoint, which is the observable the coupling exists to produce.

⚠ **A separate story should know those two areas differ**: `FR-332` derives weight from area, and
reconciling 0.05500 against 0.05600 needs the round-edge correction, which is part of what `OI-45`
has open. Nothing in this story depends on it — recorded in §7.

### `P-276` — `IsFaulted` is `false` on `FM1` alone and `null` everywhere else

**Settled, and it is a correction to built behaviour.** `FW-203` reported `IsFaulted = false` on
every component. But `Reading.cs` states the rule its own contract depends on — *"NULL MEANS ABSENT
EVERYWHERE ON THIS TYPE, AND 0 AND FALSE ARE CLAIMS"* — and a fault bit is on record for **`FM1`
only** (`PLC-Q02`, `[PLC §5.4]`). So `false` on a die block or an FM2 stand **asserts a healthy read
from an instrument that does not exist**, which is a different statement about the machine from *not
read*.

⚠ The consumer is `AlertRaised` rather than `ComponentStatus`, so nothing fails today. That is
exactly why it would have survived: a fabricated `false` is invisible until something starts
believing it.

### `P-277` — the speed setpoint is 1200 FPM, and the built 300 contradicted its own comment

**Settled.** `FW-203` carried `NominalSpeedFpm = 300m` under a comment reading *"inside every seeded
schedule's 800-1600 band"*. `PS-1100-FL1-001` seeds `LineSpeedMinFpm` **800** and `LineSpeedMaxFpm`
**1600**, so the value sat below the floor while asserting it did not.

⚠ **Nothing judged speed against the band, so it produced no failure** — it made every *duration* in
the trial roughly four times too long, which matters to `[SIM §7.1]`'s `ToTarget` scenario and to
`FW-202`'s spool completion, both of which are footage-and-time shaped. **Same family as `P-135`,
and found the same way: by running it.** 1200 is mid-band, and it is configuration.
