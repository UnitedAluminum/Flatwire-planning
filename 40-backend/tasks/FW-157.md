> **Why this document exists.** This is the largest backend story in the trial (36 h) and the
> one where the system's hardest architectural fact bites: **check-in reaches two databases and
> a controller, and the controller is not in the transaction.**
>
> ⚠ **The database half stopped being the problem on 19 Aug 2026.** `[ARC §10]` records it:
> `FlatWireDB` is co-located with `united_db` / `proddb` / `CommonDB` on **one SQL Server
> instance**, so one `SqlConnection` and one `SqlTransaction` span both halves under the local
> transaction manager — no MSDTC. **`FR-526` makes the database half one ACID transaction and it
> may be described as one.** The PLC half is still compensation. **There is exactly one seam:
> database ↔ PLC.**
>
> Two consequences shape every line of it. **Records are written *before* the PLC push**, not
> after — so a push that fails leaves evidence rather than a silent gap. And recovery is
> **compensating writes, never "atomic rollback"** — the word must not appear, because it
> describes a guarantee this operation cannot give (`G2`, `G16` closed 4 Aug 2026).
>
> ⚠ **The trial runs a reduced version of this story.** `[TRP §4]` marks Phase 4's write path
> *"**no `RodStaging`**"* — so the staged-row consumption in AC 5 is **out of trial scope**
> while remaining an MVP-1 obligation. §2.3.

## 2. The ordering, which is the design

### 2.1 Write, then push — `FR-072`

```
1. inspection result        ─┐
2. pre-run SPC pair          ├─ ONE RodCheckin row (run.RecordRodCheckin)
3. run record  (schedule id + version)   → FlatWireRun.Start raises RunStarted
4. acknowledgement audit entry — PassScheduleChangeLog, and it IS the snapshot (P-259)
   ══════════ commit (both databases, one SqlTransaction — FR-526) ══════════
5. PLCTagService.PushPassSchedule(scheduleId, lineId, payoffPosition)
   ══════════ second, small transaction: consume the bay, or abort the run ══════════
```

**The audit entry precedes the push** so a failed push leaves an **incomplete-push marker**
([`FW-151 §2.2`](FW-151.md)). Reversing 4 and 5 loses the only evidence that a
configuration was attempted.

⚠ **Steps 1 and 2 are COLUMNS ON ONE ROW, not two records** — the inspection columns plus
`SpcM1In` / `SpcM2In` on `RodCheckin`, whose DDL calls them *"pre-run SPC: primary rod diameter"*
and *"secondary diameter at 90 degrees"*. **Writing a separate `SpcCheckpoint` of type `PreRun`
would deadlock every check-in**: the band it must be judged against is
`AlloyProperty.RodDiameterTolerance*`, **seeded NULL** pending the client, so `P-43` would refuse
the checkpoint and take the check-in with it. `POST /spc` stays available for an explicit, judged
checkpoint once the band arrives.

⛔ **Step 5's built signature is not the card's, and the difference is load-bearing.** The
service exposes `PushPassScheduleAsync(PassSchedulePushRequest, ct)` where the request is
`Context(LineId, OperatorId, RunAlpha)` + `ScheduleId` + `PayoffPosition` + **`IReadOnlyList<PlcTagValue> Values`**.
`PushPassSchedule` **cannot read a schedule** — MVP-1 authors none and has no
`PassScheduleRepository` (`P-112`, `P-13`) — so `scheduleId` is **audit identity** and
[`FW-082`](FW-082.md) resolves `[PLC §7.2]`'s six groups into the
`Values` list. The operator and run context are **required** by the audit record (`P-106`), so
neither is optional here.

✅ **Step 3 raises `RunStarted`, and the aggregate does it.** [`FW-239`](FW-239.md) declares the
event and handles it; `FlatWireRun.Start` raises it (`FlatWireRun.cs:255`), so `FW-150`'s per-run
cache is invalidated at check-in and `P-141` is satisfied. **Raising it inside the aggregate
rather than in the service is the load-bearing choice** — a second caller of `Start` cannot forget
it. ⚠ It is raised **before** the PLC push, so a handler must not read it as *"the machine is
configured"*; it says a run record exists. `RunEnded` is `FW-219`'s.

### 2.2 Compensating writes — and the banned word

`phase-01b` L111 and `[TRP §6]` blocker 3: describe it as compensating writes, **never
"atomic rollback"** (`G16`). A partial push leaves the line partly configured; recovery
issues the clears for what did land — itself an action that can fail — and marks the run
accordingly.

⛔ **And it must NOT compensate across databases, because there is nothing between them to
compensate.** `FR-526` makes `FR-519`–`FR-525` and the flat wire check-in records **one
transaction**; `[ARC §10]` was corrected on 19 Aug 2026 to say so, and the clause *"and the two
databases are separate"* was the load-bearing half of the old claim and is **wrong in the deployed
topology**. The division of labour is fixed: `PLCTagService` issues the re-clear for the tags that
landed — only it knows which — and this service does the caller's half, **one small local
transaction** marking the run `Aborted` with `PlcTagsPushed = 0`, then `500 PLC_PUSH_FAILED`.

> **`G2`/`OI-39` is unresolved and this story is where it lands.** `[TRP §6]`: *"Phase 4 is
> provisional until it closes"*, needed **before T2**, and it carries the **24–64 h reserve**
> of `[TRP §2.3]`. `phase-01b`: **settle `G30` first** — whether FM2 on FL3 is one failure
> domain or two changes what a compensating clear must cover.

### 2.3 ⚠ The trial does not run the staging path

`[TRP §4]` prices Phase 4's write path as *"check-in write path + cross-DB `INFLAT`;
**no `RodStaging`**"*, because DB2A and pre-check-in left trial scope on 14 Aug.

| | MVP-1 | Trial |
|---|---|---|
| AC 5 — staged-row match + consumption | ✅ required | **out of scope** |
| Everything else | ✅ | ✅ |

**Build the staged-row path for MVP-1; expect it dark in the trial.** Do not delete it, and
do not let its absence turn into an assumption that check-in never has a predecessor row.

⚠ **`G21` resolved 15 Aug 2026 and it changes the match key.** The bay is the physical
**`Station`** (`FL1PO`, **shared by FL1 and FL3**), not `(LineId, PayoffPosition)` — so resolve
the bay by station and position, and consume through the built `RodStaging.ConsumeAtCheckIn`,
which raises `BayStateChanged`. ⚠ That event is also the eviction trigger
[`FW-239`](FW-239.md) needs for `FW-150`'s `stagedWeights` cache (**`G67`**) — consuming a staged
row without raising it leaves `PercentRemaining` computed against the previous rod.

#### ⛔ Two staged rows are in play and they are not the same row

This is the defect a live run against the seed found on 29 Aug 2026, and it is invisible in a
reading of the acceptance criterion.

| | Resolved by | What it is for |
|---|---|---|
| **the rod's own staged row** | **alpha** | AC 5's row. The payoff must match it, its blocked state refuses the check-in, its carry-forward evidence is the rod's, and **it is the row consumed** |
| **the bay occupant** | **station + position** | Answers only *"is a **different** rod physically on this bay"* → `409 BAY_OCCUPIED`. **Never consumed** |

Conflating them: checking in `R00048` at payoff 1 consumed the bay occupied by `R00047`, and
`R00047`'s blocked-bay rule then threw **after** the run had been created and the schedule pushed.

⚠ **And the blocked-bay test has to be asked early.** `BlockedBayCannotCheckInRule` lives inside
`ConsumeAtCheckIn` — correctly, since an aggregate must not be bypassable — but consumption
happens **after** the push, so relying on it alone creates a run, pushes the schedule, and only
then throws. Ask the aggregate the question before any of that (`staging.IsBlocked` →
`422 INSPECTION_FAILED` with the WIP-rejection route). It is not a second copy of the rule; it is
the same rule asked at the right time.

### 2.4 The snapshot rule survives `D-31`

`PassScheduleId` is a **real, enforced FK** since `D-31`, so an unavailable schedule is now a
`404`/FK failure rather than an unreachable service. **The snapshot rule is unchanged**:
MVP-1 persists its own copy of what it pushed — id, version, effective configuration —
because `[PLC §11.2]` and `Q64` need a certificate to stay reproducible **after the owning
system later edits the schedule**, which a local FK does nothing to prevent. The value object
is `PassScheduleSnapshot` ([`FW-207 §3`](FW-207.md)).

⚠ **Where it is PERSISTED is not a second store — `P-259`.** `PassScheduleSnapshot` is the in-memory
value object the aggregate acknowledges; the durable copy is the **acknowledgement audit entry itself**,
written to `PassScheduleChangeLog` as one header row (schedule and version) plus one row per effective
parameter. That table is purpose-built for it — its `ChangeType` `CHECK` admits `Acknowledgment`, its
`ParameterName` is documented *"NULL on an acknowledgment"*, and it carries `RunId`, which is what makes
the snapshot findable from the run. **Do not add a second snapshot table beside it.**

## 4. What was built, in order

1. ⛔ **There is NO MediatR command, and that is deliberate — `P-258`.** The 29 Aug text ordered a
   nested `CheckInRodCommand` handler in `FlatWire.Application/Commands/CheckIn/`
   ([`FW-139 §2.2`](FW-139.md)); **building one would undo the design.**
   `TransactionBehaviour` wraps a command in **one** transaction spanning the whole handler,
   which puts the PLC push **inside** it — so a failed push would roll back the very records
   `FR-072` exists to create. **The service owns its unit of work.** Shape validation is
   unaffected: `AddFluentValidationAutoValidation` runs every request validator at model binding,
   so the DTO gets its `400` either way. `P-65`'s seam is untouched — the controller still
   forwards to `ICheckInService` and the interface has not changed, and
   [`FW-139`](FW-139.md) itself is unaffected and still `done`: this endpoint simply does not
   route through the pipeline.
2. ✅ **Shape validation** in FluentValidation → `400`
   ([`FW-147`](FW-147.md)); **state rules in the
   aggregate** → `422` ([`FW-207`](FW-207.md)). The split is the point, and the four
   pass-schedule rules were **already written** (§1.2).
3. ✅ `CheckInService` orchestrating §2.1's steps in order. `RunStarted` is raised by
   `FlatWireRun.Start`, not by the service (§2.1).
4. ✅ **Folded into step 3, not a separate store — `P-259`.** The acknowledgement audit entry
   **is** the `PassScheduleSnapshot` persistence (§2.4): one `PassScheduleChangeLog` header row
   plus one row per effective parameter. Two stores would be two records of one fact.
5. ✅ Call [`FW-082`](FW-082.md)'s push **last**, supplying the
   `Values` list and the `PlcWriteContext` (§2.1).
6. ✅ Compensation path + the saga-boundary comment — the boundary itself is documented in
   `PLCTagService` ([`FW-151`](FW-151.md) AC 4). ⚠ It compensates **locally only** (§2.2).
7. ✅ Staged-row consumption (§2.3), behind MVP-1 scope — **after** the push, so a failed push
   leaves the bay `Staged` by not moving it.
8. ⛔ **`Operator+` policy — NOT DONE.** ([`FW-145`](FW-145.md).) The controller carries a bare
   class-level `[Authorize]`: authenticated, any role. See §8.

## 5. Decisions this plan makes

> `P-##` is continuous across the repository; `P-01`–`P-39` preceded `P-40` when it was minted on
> 15 Aug 2026. `P-254`–`P-257` were minted by the 29 Aug re-review of the Phase-4–8 plans, and
> **`P-258`–`P-261` are minted here by the de-stub**. **`P-40` still stands** — the re-review and
> the build changed its inputs, not its conclusion.

### `P-40` — build the ordered path now; leave the recovery *strategy* behind `G2`

The **write ordering** (§2.1), the **status codes** (§3) and the **snapshot** (§2.4) are all
specified and unblocked. What `G2`/`OI-39` has not decided is the **recovery strategy** —
saga/outbox versus an `INFLAT` mirror — and that choice changes what happens *after* a
partial failure, not what happens on the happy path.

**So: build the ordered writes and the compensating clears for the single-line PLC push, and
leave the cross-database recovery strategy as a documented seam.** Mark the run so a
half-configured line is detectable rather than silently `Running` — which is the story's own
"so that" clause and does not depend on the undecided part.

⚠ **Do not implement a two-phase commit or anything named for one.** The operation spans two
databases and a controller; the specification's answer is compensation, and `G16` was closed
on exactly this wording.

### `P-258` — no MediatR command; the service owns its unit of work

§4 step 1. `TransactionBehaviour` would put the PLC push inside the record transaction, so a
failed push would roll back the evidence `FR-072` exists to create. The controller→interface seam
of `P-65` is unchanged, and shape validation still runs at model binding.

**Fallback:** a command whose handler commits before the push and re-opens after it. Rejected —
it is this design with a pipeline attached, and the pipeline's whole value is the transaction it
would then have to be told to skip.

### `P-259` — the acknowledgement audit entry and the MVP-1 snapshot are ONE artifact

§2.4, §4 step 4. `PassScheduleChangeLog` is purpose-built for it: its `ChangeType` `CHECK` admits
`Acknowledgment`, its `ParameterName` column is documented *"NULL on an acknowledgment"*, and it
carries `RunId`. **One header row** (schedule and version) **plus one row per effective
parameter** is what makes a certificate reproducible after the owning system edits the schedule.

**Fallback:** a second snapshot store beside it. Rejected — two records of one fact, and they
drift.

### `P-260` — the push carries only components the line can address

FL2's tag map has no `Db1Active` / `Db2Active` / `Fm1Active` entry, so those components are not
addressable there and are omitted **by name in the log** rather than by a rule in the service.
This is not `P-41` undone: nothing is silently dropped and no path is invented.

### `P-261` — the schedule states a speed WINDOW; the push writes the bottom of it

`LineSpeedMinFpm`..`LineSpeedMaxFpm`, and the push needs one setpoint. Nothing specifies which.
The bottom is the only end that cannot exceed the schedule's own limit, and threading a line up
slowly is the conventional start. ⚠ **Recorded rather than left implicit because a start speed is
a physical command** — raise it with the controls engineer.

⚠ **These four ids were minted in code before this register recorded them, and `P-258`–`P-260`
briefly collided with [`FW-152`](../../30-database/tasks/FW-152.md)'s.** That file's mints moved
to `P-262`–`P-264`; these are the definitions of record.
