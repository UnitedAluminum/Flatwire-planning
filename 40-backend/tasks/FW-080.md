## 3. The design

### 3.1 Transport and protocol — `[SIG §4.1]`

- **WebSockets-first** with `SkipNegotiation` where topology allows; SSE and long-poll only
  as a last resort. **IIS WebSockets must be enabled on the target** — `[DEP §4.4]`, gap
  `G10`.
- **MessagePack** on both ends — `AddSignalR().AddMessagePackProtocol()` server-side,
  `@microsoft/signalr-protocol-msgpack` client-side.
- **Strongly-typed** `FlatWireHub : Hub<IFlatWireClient>` — a compile-time contract, **no
  magic-string method names**.

> ⚠ `[SIG]` treats MessagePack as **measure-first** — *"batching and decimation are the real
> win"* — and the protocol package is new on **both** ends. `P-21`.

### 3.2 The broadcast loop — `[SIG §4.2]`

A bounded channel decouples the poll rate from fan-out. The loop drains on a **fixed ~100 ms
/ 10 Hz cadence** (`FlatWireSignalROptions.DrainCadenceMs`), sending **batched arrays per
line group**, with decimation.

| Traffic | Treatment |
|---|---|
| Gauge, width, speed, payoff weight, footage | **Batched** arrays at ~100 ms |
| `ComponentStatus`, `LineStatus` | **On-change only** |
| Rare domain events (weld, die change, pause, SPC, alert, checkout) | **Immediate, unbatched** |
| **`PayoffStateChanged`** | ⚠ **Never enters the ~100 ms batch** |
| **The four prompt events — 11, 12, 13, 14** | **Immediate, unbatched.** They sit on `[SIG §4.2]`'s rare-event node; they are not telemetry and never batch |
| FL2 standalone | **Suppresses batched gauge and width** — FL2 broadcasts `null` live gauge/width. Speed, footage, component and line status **still flow** |

The loop itself is [`FW-150`](FW-150.md); this story provides the hub and the
groups it sends through.

### 3.3 ⚠ Two events are durable — and they are the only two

`[SIG §5.2]`: *"`SpoolCompletionPromptDue` and `OrderAllocationReached` are the only events in
this contract that are not fire-and-forget."* Every other event may be missed by a
disconnected client and recovered from the next snapshot; these may not. **Both are
server-owned persisted state, re-delivered on group re-join (`TC-173`), and both carry a
latched weight the client must render rather than replace with a fresher `PayoffWeight` tick.**

| | **Event 11 · `SpoolCompletionPromptDue`** | **Event 13 · `OrderAllocationReached`** |
|---|---|---|
| Raised on | the **`RUNNING → STOPPED` edge**, exactly once per stop | the **footage crossing**, server-side, once per pairing |
| Weight latched at | the **PLC stop timestamp** | the **crossing instant** |
| Persisted to | **`FlatWireRun`**'s five prompt columns — `PromptDueAt`, `PromptPlcStopTs`, `PromptLatchedWeightLb`, `PromptResolvedAt`, `PromptAnswer` + its `CHECK` (`G38`, schema half closed) | **`RodOrderConsumption`** — `State = 'ThresholdReached'`, `ThresholdReachedAt`, `LatchedWeightAtThresholdLb`, `NotificationRaisedAt`; closed by `AcknowledgedAt` / `AcknowledgedBy` / `WeightAtAcknowledgementLb` |
| Outstanding when | `PromptDueAt IS NOT NULL AND PromptResolvedAt IS NULL` | `State = 'ThresholdReached' AND AcknowledgedAt IS NULL` |
| Closed by | event 12, `SpoolCompletionPromptResolved` | event 14, `OrderAllocationResolved` |
| Raised by | `FW-202` | `FW-227` |

**Persist to the columns; never hold a prompt in memory.** A per-connection cache survives
neither a browser refresh nor an app-pool recycle, and both are specified to. Re-delivery is
`P-100`. Duplicate delivery is **specified behaviour, not a fault** — each is raised once per
edge, so the client half must be idempotent.

⚠ **`OrderAllocationResolved` does something event 12 does not:** it **reveals the next
order** on the same rod. The line is **still running**, the rod is not dismounted and nothing
is scanned, so this event is the only signal DB3 gets that a boundary was crossed — and the
material produced between the crossing and the acknowledgement is the **overrun**, recorded
and reportable.

> ⚠ **`enum LineState` has no `Stopped` member.** Resolve the edge through the configurable
> **`LineStateMap`** (`[PLC §6]`), **never by adding an enum value** — the absence is
> deliberate (`PLC-Q01`), the map is **empty until commissioning test `C2`**, and `Program.cs`
> already asserts at boot that an unmapped raw value resolves to nothing.

### 3.4 Groups and reconnect — `[SIG §4.3]`

Groups `FL1Data` / `FL2Data` / `FL3Data`; `JoinLineGroup` / `LeaveLineGroup`; tuned
`KeepAliveInterval` and `ClientTimeoutInterval` (from `FlatWireSignalROptions`); `[Authorize]`
on hub methods; JWT via `?access_token=`.

> **Reconnect is a deliverable, not just a test** (`phase-01b` L103): automatic reconnect
> with exponential backoff **plus line-group re-join**, so a client renders cached
> last-known state behind a *"Reconnecting…"* banner and **never a blank screen**. The
> server half is the re-join and the durable re-delivery; the client half is 1A's
> (`FW-135` / `FW-137`).

**The client subscribes before it joins** (`[SIG §5.6]`, `FW-135` step 5), because an
outstanding prompt arrives **on join** rather than on the original edge. That is a contract on
both ends: the server must send on join, and it must be safe to send twice.

**Stateless hub.** A Redis or Azure SignalR backplane is a **config-only** path if
`FlatWire.API` goes multi-instance — no code change. Single instance is fine for the trial.
`P-100`'s query-on-join is what keeps that true of the durable prompts.

> ⚠ **Always send to the group; never loop over connections.** `Clients.Group(name)`
> serializes the payload **once per protocol** and reuses that buffer for every connection in
> the group. A hand-rolled `foreach (connection) Clients.Client(id)…` serializes **once per
> connection** — at 10 Hz × 3 lines that is the difference between 30 serializations a second
> and 30 × N. **This is the reason the groups exist**, not just a tidier API, and it is the
> one place a plausible-looking implementation costs real throughput.

### 3.5 The interface — fourteen events and six markers

**This is the list to build.** `[TB §7]`'s `FW-136` card enumerates nine, its `FW-149` card
ten-plus-five, and `phase-01b` criterion 4 twelve; all predate events 11–14 and the
`AlertEvent` marker. `[SIG §5.2]` and `[SIG §5.4]` are the authority (§8).

```csharp
// FlatWire.Domain — [SVC §3.2]'s layer table, and FW-208's P-35 depends on it being here.
public interface IFlatWireClient
{
    // 1–2 · batched arrays at the cadence
    Task GaugeReading(GaugeReadingEvent[] readings);
    Task WidthReading(WidthReadingEvent[] readings);

    // 3–5 · batched / decimated
    Task SpeedFPM(SpeedFpmEvent reading);
    Task PayoffWeight(PayoffWeightEvent reading);
    Task FootageCounter(FootageCounterEvent reading);

    // 6–7 · on change only
    Task ComponentStatus(ComponentStatusEvent status);
    Task LineStatus(LineStatusEvent status);          // rename pending → LineStateChanged

    // 8–10 · immediate, unbatched
    Task AlertRaised(AlertRaisedEvent alert);
    Task AlertCleared(AlertClearedEvent alert);
    Task PayoffStateChanged(PayoffStateChangedEvent change);   // ⚠ never in the batch

    // 11–14 · immediate, unbatched. 11 and 13 are DURABLE (§3.3)
    Task SpoolCompletionPromptDue(SpoolCompletionPromptDueEvent prompt);
    Task SpoolCompletionPromptResolved(SpoolCompletionPromptResolvedEvent resolution);
    Task OrderAllocationReached(OrderAllocationReachedEvent prompt);
    Task OrderAllocationResolved(OrderAllocationResolvedEvent resolution);

    // The six run-event markers — [SIG §5.4], consumed by DB3 traces
    Task WeldJoinEvent(WeldJoinMarker marker);
    Task DieChangeEvent(DieChangeMarker marker);
    Task PauseEvent(PauseMarker marker);
    Task SPCCheckpoint(SpcCheckpointMarker marker);
    Task AlertEvent(AlertMarker marker);
    Task RodCheckoutEvent(RodCheckoutMarker marker);
}
```

**And one type more — the abstraction that lets anything outside `FlatWire.API` broadcast**
(`P-101`). `IFlatWireClient` describes what a *client* receives; it is not something a handler
can inject. What a handler injects is this:

```csharp
// FlatWire.Domain/Services/ — beside IAuditLog and ITagPathResolver, and for the same reason.
public interface IFlatWireBroadcaster
{
    IFlatWireClient Line(LineId line);   // → the FL1Data / FL2Data / FL3Data group
}
```

Implemented in `FlatWire.API` over `IHubContext<FlatWireHub, IFlatWireClient>` — the only
project that can name either type. **No SignalR type crosses into `Domain`, `Application` or
`Infrastructure`**, which is what `[SVC §3.2c]` requires anyway.

⚠ **One member, and `P-100` does not need a second.** Inside a `Hub<IFlatWireClient>`,
**`Clients.Caller` is already typed as `IFlatWireClient`** — so the re-delivery on join is
`await Clients.Caller.SpoolCompletionPromptDue(…)`, with no broadcaster involved at all. The
broadcaster exists **only for callers outside the hub**, and those only ever address a line
group. If a later story needs a connection- or user-targeted send from outside, it adds the
member then; do not add it speculatively now.

Three things about the interface list are easy to get wrong:

- **`AlertEvent` is a marker, not a third alert event.** `AlertRaised` / `AlertCleared` drive
  DB1's alert bar; `AlertEvent` annotates a DB3 trace. Both exist, and `FW-149`'s card omits
  the marker.
- **Payload type names are `[SIG §5.6]`'s, suffixed `Event`.** `FW-149`'s card writes
  `GaugeReading(GaugeReading[])`, which makes the method and its payload share a name — legal
  C#, needlessly confusing, and not what the client mirrors. **`FW-149` owns the payload
  shapes; this story owns only that there are twenty members and what they are called.**
- **The pending renames are not this story's to apply.** `LineState` → `LineOperatingState`
  and `LineStatus` → `LineStateChanged` are `[PLCC §6.3]`'s, to be done in one pass across all
  three layers. **Build to `[API]` / `[SIG]` as published.**

## 4. Build order

1. ✅ **`FW-145`'s `?access_token=` handler — built here, as the plan directed.** It did not
   exist and nothing else supplied it, so its §3.5 `PostConfigure` was taken as this story's
   prerequisite rather than worked around with an anonymous hub. Without it every hub
   connection is a `401` and steps 4–8 cannot be demonstrated.
2. **Add `Microsoft.AspNetCore.SignalR.Protocols.MessagePack` in *two* places** — `P-21`.
   `ManagePackageVersionsCentrally` is `true`, so it takes a `<PackageVersion …
   Version="8.0.30" />` in `API/Directory.Packages.props` **and** a version-less
   `<PackageReference Include="…" />` in `FlatWire.API/Api.csproj`. ⚠ **A `PackageVersion`
   entry is not a reference** — with only the first, nothing compiles differently and the
   omission is silent. **No package is needed for SignalR itself.**
3. **`IFlatWireClient` in `FlatWire.Domain`** — §3.5's full list. `FW-149`'s deliverable by
   the card, this story's by `P-22`.
   **3a. `IFlatWireBroadcaster` in `FlatWire.Domain/Services/`** and its `FlatWire.API`
   implementation over `IHubContext<FlatWireHub, IFlatWireClient>` — `P-101`. **`FW-208`'s
   eight handlers unblock on 3 and 3a together**; without 3a the interface compiles and the
   handlers still cannot be written.
4. **`FlatWire.API/Hubs/FlatWireHub.cs`** — `Hub<IFlatWireClient>`, `[Authorize]`,
   `JoinLineGroup` / `LeaveLineGroup`. ⚠ **`JoinLineGroup` takes `LineId`, not a string, and
   maps to `$"{lineId}Data"` itself.** Passing a caller-supplied name to
   `Groups.AddToGroupAsync` lets a client join any group it can spell; an unmapped value is a
   refusal. `LeaveLineGroup` is for **screen teardown** — SignalR removes a dropped
   connection from its groups on its own, so it is not the cleanup path.
5. **`AddSignalR(…).AddMessagePackProtocol()`** and
   **`app.MapHub<FlatWireHub>("/hubs/flatwire")` after `app.UseAuthorization()`** — `P-99`.
   ⚠ **Mapping it there does *not* put hub method calls inside the middleware stack** — only
   the handshake. Two traps in that one line:
   - ⚠ **`EnableDetailedErrors` must be Development-only.** It sends a failing hub method's
     exception **message to the client**, which is what `FW-146` §3 step 9 forbids on the REST
     side — *"its stack goes to the log, never to the response."* Gate it on
     `builder.Environment.IsDevelopment()`.
     ⚠ **And `ExceptionHandlingMiddleware` will not save you here.** An exception thrown
     *inside a hub method* is caught by **SignalR's own dispatcher** and written into the
     completion message returned to the caller — it never becomes an unhandled exception, so
     the middleware never sees it. **That holds on every transport**, including a long-poll
     fallback whose requests do pass through the stack. `EnableDetailedErrors` is the only
     thing deciding whether that completion carries the real message. **The hub is the one
     surface in this service `FW-146` does not cover.**
   - ⚠ **`HubOptions` cannot read `FlatWireSignalROptions` from inside `AddSignalR`'s

## 5. Decisions this plan makes

> `P-##` is continuous across this folder; `P-01`–`P-98` precede these. New decisions
> elsewhere mint at `P-103`+.

### `P-21` — add `Microsoft.AspNetCore.SignalR.Protocols.MessagePack`, and measure before committing

**The package is named in no specification.** `[SIG §4.1]` prescribes
`AddSignalR().AddMessagePackProtocol()` without naming what supplies it, and it is **not** in
`API/Directory.Packages.props`. **Pin it on the `8.0.x` line. Never 9.x or 10.x** — a newer
protocol package against a `net8.0` service is a runtime mismatch waiting to happen. It brings the
`MessagePack` serializer transitively — one new dependency, not none. Central package management
means the version goes in the props file and the reference in the `.csproj` (build step 2).

⛔ **Built at `8.0.30`, and NOT at `8.0.8` — do not "align" it down to match `JwtBearer`.**
`8.0.8` was the obvious pick, being the patch the sibling `Microsoft.AspNetCore.Authentication.JwtBearer`
sits on. It carries a **known high-severity advisory** — `NU1903`, `GHSA-f8h2-vmm9-qhj6` — which
the build reports as a **warning, not an error**, so matching the sibling would have shipped it
quietly. `8.0.30` is the latest `8.0.x` and is clean.

**Nothing is needed for SignalR itself** — the server-side hub types are in the ASP.NET Core
shared framework, which is why no sibling service in `ual-api` references a SignalR package
either.

**And treat it as measure-first, per `[SIG §4.1]` and `G10`.** `@microsoft/signalr` **9.0.6 is
already a dependency** of `ual-angular` and `@microsoft/signalr-protocol-msgpack` is
**absent**, so the transport is available today and only the protocol is new, on both ends.
`[SIG]`'s own judgement is that *"batching and decimation are the real win."* **Build the
batching and decimation first; enable MessagePack behind
`FlatWireSignalROptions.EnableMessagePack` and measure.** If it does not pay, the switch turns
it off **without a rebuild — but not without a restart**: protocol registration is a
`builder.Services` call that runs before `Build()`, so the flag is read from
`builder.Configuration` at startup and `ValidateOnStart` has not run when it is. Say "restart"
rather than "reload" to anyone operating it.

### `P-22` — `IFlatWireClient` lands with this story even though it is `FW-149`'s

**Sequencing, not scope.** `Hub<IFlatWireClient>` does not compile without the interface,
and `FW-149` lists `FW-080` as *its* dependency — so taken literally neither can start.

**Resolution:** define `IFlatWireClient` in `FlatWire.Domain` with the **full** published set
as part of this story's first commit — **`[SIG §5.2]`'s fourteen events plus `[SIG §5.4]`'s
six run-event markers, enumerated at §3.5** — and let `FW-149` own the payload types, the
shape review and the match against `FW-136`'s client-side set. The interface is a compile-time
contract on both ends; a partial one built here and widened there would be a breaking change
by `[API §8]`.

⚠ **"The full published set" is fourteen, and every card that enumerates it says otherwise.**
**Build §3.5, not a card** — a hub built from `FW-149`'s card publishes 10 of 14 events and
5 of 6 markers, and the four it drops are the two prompt pairs, the only signals DB3 gets that
a spool or an order boundary needs an operator.

⚠ **It is not only `FW-149` that waits.** `FW-208`'s dispatcher is built with **eight
broadcast handlers unbuilt**, blocked on this type. `P-35` puts them in
`FlatWire.Infrastructure`, which is possible **only** because the interface is in `Domain` —
so the placement in this decision is a constraint on a built story, not a preference. **And it
is only half of what those handlers need**; the other half is `P-101`.

**Naming, and it is deliberate:** the aggregate, table, endpoint and story all say
**`WeldEvent`**; **`WeldJoinEvent` survives only as the SignalR method name** and is
documented as such (`[SIG §5.4]`).

### `P-99` — map the hub after `UseAuthorization()`, and do not rely on the MVC filter

⚠ **`AddCustomMvc`'s global `AuthorizeFilter` is an MVC filter and binds MVC actions only.**
It does not touch a hub. A hub is protected by `[Authorize]` on the hub class or method, and
under **endpoint routing** ASP.NET Core requires the authorization **middleware** to run
between `UseRouting()` and the endpoint or the request fails with *"contains authorization
metadata, but a middleware was not found that supports authorization"* — a `500`, not the
`401` the contract requires.

That middleware is already there: **`P-55` added `app.UseAuthorization()`** after measuring
22 of 22 endpoints returning `500` without it. **`MapHub` goes after it**, beside
`MapControllers()`. The physical line position does not by itself set middleware order —
`MapX` only registers endpoints — but keeping the two `Map` calls together and below
`UseAuthorization()` is what makes the ordering readable, and it puts the hub's **handshake**
inside `CorrelationIdMiddleware`, `UseSerilogRequestLogging` and `ExceptionHandlingMiddleware`.
⚠ **The handshake only.** Over WebSockets a hub *method* invocation arrives on an established
connection and never re-enters the middleware stack at all; under a **long-poll fallback** the
poll *is* an HTTP request and does traverse it — but either way **SignalR's own dispatcher
catches the hub method's exception** and writes it into the completion message, so it never
surfaces as an unhandled exception and `FW-146`'s mapper never sees it (§4 step 5). The
conclusion does not depend on the transport, which matters because `G10` is precisely the risk
of falling back to one.

**The corollary is the trap:** the hub inherits **no** authorization from the MVC pipeline, so
an `[Authorize]`-less hub is **anonymous** and looks entirely healthy in Development. The only
anonymous endpoint in this service is `/health`, deliberately and explicitly (`P-85`).

### `P-100` — re-deliver the durable prompts by **query on join**, not from a per-connection cache

`[SIG §5.2]` requires an outstanding prompt to reach a client **on group re-join**; §3.4
requires the hub to stay **stateless** so a backplane is config-only. Both hold only if the
re-delivery reads the database.

**Both prompts hang off the line's active run, so it is one query, not two.** On
`JoinLineGroup(lineId)`, after `AddToGroupAsync`, send **one** `IMediator` query that:

1. seeks the line's active run — `WHERE LineId = @line AND Status IN ('Running','Paused')`;
2. reads its five prompt columns → `SpoolCompletionPromptDue` if
   `PromptDueAt IS NOT NULL AND PromptResolvedAt IS NULL`;
3. joins `RodOrderConsumption` **on `RunId`**, filtered to
   `State = 'ThresholdReached' AND AcknowledgedAt IS NULL` → `OrderAllocationReached`.

**No active run on the line means no prompt — return immediately.** That is the common case
for an idle line and it costs one seek.

⚠ **This needs no new index, and the access path is about as cheap as a read gets.** Step 1
seeks **`UX_FlatWireRun_ActiveLine`** — a *unique filtered* index on `LineId` where
`Status IN ('Running','Paused')`, so it holds **at most one row per line, three in the whole
database** and returns at most one. Step 3 seeks `IX_RodOrderConsumption_RunId`, and live
pairings are bounded by `UX_RodOrderConsumption_Station` at one per station. **Do not add a
filtered index for the prompt columns** — reaching them through the active run is both the
real relationship and the faster path.

⚠ **Join on `RunId`, not on `RodOrderConsumption.LineId`.** That column is documented
*"projection and reporting only"* (`G21`) and is **not in the filtered index**, so keying the
lookup off it would miss every index this design relies on.

⚠ **Through `IMediator`, not a repository or `FlatWireDbContext`.** `[SVC §3.2]` lists
`Hubs/FlatWireHub.cs` on the same line as *"controllers (thin)"* and says **"all logic routes
through MediatR"** — a hub that opens its own reads is the one place in the API project doing
data access, and it would be exempt from `ValidatorBehavior`, `LoggingBehavior` and the
correlation id at the same time. **Inject `IMediator` and send the query**, exactly as the
fifteen controllers do.

⚠ **A query handler is not an endpoint, so `OI-32` is untouched.** `[SIG §5.5]` closes the
prompt half deliberately — *"the prompt is raised by the server on the `RUNNING → STOPPED`
edge and answered over the hub, so there is nothing for a client to poll."* **Do not add a
`GET` for this.** The handler is reachable from the hub and from nowhere else.

**To the caller, never to the group** — a re-join must not re-prompt the screens that never
disconnected. Inside `Hub<IFlatWireClient>` that is `Clients.Caller`, already typed. Send the
**latched** weights from the row (`PromptLatchedWeightLb`, `LatchedWeightAtThresholdLb`),
never a current `PayoffWeight`. **Query after `AddToGroupAsync`, not before**, so a prompt
raised while the read is in flight reaches the caller as a normal broadcast rather than
falling between the two.

**Why not a cache.** An in-memory pending-prompt dictionary passes the reconnect test and
fails everything else: an app-pool recycle loses it, a second instance never had it, and a
browser refresh — which `FR-144` names explicitly — arrives as a *new* connection with no
history. It also silently ties the hub to one instance, contradicting the config-only
backplane promise. The database is already the store of record for both prompts (§3.3).

**The cost is one seek per join** — a screen-open and reconnect path, never the cadence path.
Even a reconnect storm is N seeks into a three-row index.

### `P-101` — mint a broadcast abstraction in `Domain`, or `FW-208`'s handlers cannot be written

⛔ **Forced by the project graph, not chosen for tidiness.** `FW-208`'s `P-35` puts its eight
broadcast handlers in `FlatWire.Infrastructure` and says DI will supply *"the API-side
`IHubContext<FlatWireHub, IFlatWireClient>`"*. **A handler there cannot name that type**, for
two independent reasons:

- **`FlatWireHub` is `FlatWire.API`'s**, and `FlatWire.API` → `FlatWire.Infrastructure`. The
  reference does not run the other way and must not — reversing it would make the composition
  root a dependency of the data layer.
- **`IHubContext<>` is in the ASP.NET Core shared framework**, which `FlatWire.Infrastructure`
  does not carry: it is `Microsoft.NET.Sdk`, not `Microsoft.NET.Sdk.Web`. Adding a
  `FrameworkReference` would fix the second problem and leave the first untouched.

`FW-208`'s warning — *"if `FW-080` lands the interface in the API project instead, `P-35`
becomes unbuildable"* — is **necessary and not sufficient**. Landing `IFlatWireClient` in
`Domain` is required, and on its own it still leaves the handler with nothing to inject.

**Resolution: this story also mints `IFlatWireBroadcaster` in `FlatWire.Domain/Services/`**
(§3.5), implemented in `FlatWire.API` over the real `IHubContext`. **The shape already exists
in this service** — `IAuditLog` is a `Domain/Services/` interface implemented by
`SerilogAuditLog` in Infrastructure, and `ITagPathResolver` by `ConfigurationTagPathResolver`;
`P-62` put the twelve service interfaces there for exactly this reason, *"so both Application
and Infrastructure can see them without either referencing the other."* This is that pattern
pointed the other way, which is the only novelty.

**And it makes a rule mechanical.** `[SVC §3.2c]`'s *"SignalR stays out of
`FlatWire.Application`"* stops being a convention anyone can breach by accident — it becomes a
**project-reference impossibility**, the standard `P-34` set.

⚠ **One member — `Line(LineId)` — and that is the whole interface.** `P-100`'s caller-only
re-delivery does **not** need a second: inside a `Hub<IFlatWireClient>`, `Clients.Caller` is
already typed as `IFlatWireClient`, so the hub sends to its own caller directly. The
broadcaster is for callers **outside** the hub, and those only ever address a line group.

✅ **Verified 28 Aug 2026.** A stand-in broadcast handler was compiled inside
`FlatWire.Infrastructure` against `IFlatWireBroadcaster` — no reference to `FlatWire.API`, no
SignalR type — and then deleted. `FW-208`'s eight handlers have what they need.

⚠ **Scope note: one interface with one method, and a forwarding implementation.** It holds no
state, no retry and no fan-out logic — it returns `Clients.Group($"{line}Data")` and nothing
else. Anything more belongs to `FW-150`. **It adds no call on the cadence path**: the
broadcast loop is inside the API project and uses the hub context directly.

**The cheaper alternative, and why it loses.** `FW-208`'s eight broadcast handlers could
simply live in `FlatWire.API`, which needs **no new type at all** — only the API assembly
added to the MediatR scan. It loses because the in-transaction handlers need
`IRodStagingRepository` and must stay in Infrastructure, so one story's handler set would
straddle two projects, and the composition root would gain runtime behaviour. **One interface
with one method is the smaller price.**

### `P-102` — align the JSON protocol on **string** enums, or `P-21`'s switch is a trap

⛔ **Found by running the hub, not by reading it.** `JoinLineGroup(LineId)` accepted a *different
argument type on each protocol*:

| Argument | MessagePack | JSON *(before this decision)* |
|---|---|---|
| `0` (int) | **rejected** | accepted |
| `"FL1"` (string) | **accepted** | **rejected** |

SignalR's MessagePack resolver chain leads with `DynamicEnumAsStringResolver`, so enums cross as
**strings**. SignalR's JSON protocol has its **own** `PayloadSerializerOptions` — the
`JsonStringEnumConverter` `Program.cs` registers is on `Mvc.JsonOptions` and never reaches it — so
it expected the **integer**.

**That makes `P-21`'s central promise false as built.** *"Turn MessagePack off behind the switch
and measure"* would change the client's argument type, and every caller written against MessagePack
would break on the flip — a failure that appears only when someone takes the measurement the plan
asks for.

**Resolution: `AddJsonProtocol` with `JsonStringEnumConverter`**, so both protocols carry enums as
strings. **Aligning JSON on strings rather than MessagePack on ints is `P-58`'s call already** —
*"the fourteen canonical enums go onto the wire as STRINGS"*, so the C# enum, the TypeScript union
and the DB `CHECK` read alike. The hub now matches the REST surface instead of contradicting it.
Re-measured: `"FL1"` is accepted on **both**.

⚠ **Payload enums ride on this too** — `PayoffPosition`, `AlertSeverity`, `CheckpointType`,
`ComponentName`, `LineState`, `CheckoutMode` all appear in `[SIG §5.2]` payloads and had the same
split. **One open question for `FW-149`, not settled here:** `PayoffPosition` carries explicit
numeric values and `[API §4.5]` contracts `"payoffPosition": 2` as an **int** on REST, so the hub
now sends `"Payoff2"` where REST sends `2`. That is consistent within each surface and worth a
deliberate answer when the payload shapes are reviewed.
