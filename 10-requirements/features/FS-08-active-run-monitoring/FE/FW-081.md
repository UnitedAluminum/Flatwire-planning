### 2.1 ⛔ `isLive` must switch after mount — and **both** of the card's reasons are retired

The card is unusually explicit: *"a runtime-switchable input, not mount-time … Phase 8 needs
exactly this for FL2's Live/Profile control, and a hybrid FL3 run has both."*

⛔ **Both halves of that sentence are now false, and the requirement is unchanged.** This is the
single most important thing in this revision, because the natural reaction to *"the reasons went
away"* is to build the cheap mount-time flag.

| The card's reason | What happened to it |
|---|---|
| *"Phase 8 needs this for FL2's Live/Profile control"* | ⛔ **Gone.** `FR-120` is superseded and `D-55` made the trace treatment uniform, so [`FW-181`](../../FS-11-spool-lifecycle-fl2/RT/FW-181.md) has **no per-line control left to bind** |
| *"a hybrid FL3 run has both"* | ⛔ **Gone, and it was never right.** [`FW-192`](../../FS-13-fl3-hybrid-route/RT/FW-192.md) requires *"continuous `GaugeReading`/`WidthReading` end to end — **no FL2 historical switch mid-run**"*: an FL3 run is **one live series across both mills**. ⚠ That incoherence — the same FM2 real-time on FL3 and blind on FL2 — is what retired `A3` (`G120`) |

**Three reasons replace them, and each is concrete:**

1. ⭐ **`isLive` is not only a source selector — it is the chart's update path, and that is
   measured.** `TracePanelComponent.isLive` and `ChartCanvasComponent.isLive` gate
   `chart.update('none')` against `releaseChart()` + `new Chart(...)` — `chart-canvas.component.ts`
   line 64. [`FW-N33`](../../FS-11-spool-lifecycle-fl2/FE/FW-N33.md) found the input **unbound**,
   so the live path had never been taken: both panels destroyed and reconstructed ~20 times a
   second. ⛔ **So *"switches without remounting"* is not an abstraction — it is the difference
   between an in-place data update and a Chart.js teardown**, and it is falsifiable in a profiler.
   ✅ **Both panels now bind a signal** — the dashboard's own, and the popup's through the payload
   (§2.5) — so the teardown is gone **and** the input has a second value to take. ⚠ **What is still
   missing is the consumer**: nothing sets it false until [`FW-164`](../BE/FW-164.md)'s stored
   series lands, and the code carries a `TODO:` saying exactly that. ⛔ **Do not read a bound signal
   as a delivered toggle either** — the contract is proven by a teardown spy, not by a screen.
2. **Profile is a REVIEW mode, and it survives the reversal intact.** The same panel renders a
   finished run's stored series from `GET /run/{runId}/gaugetrace` ([`FW-164`](../BE/FW-164.md),
   [`FW-165`](../DB/FW-165.md)) for the Gauge-Trace, CPK and Cut-Traceability reports (`FR-120`'s
   surviving clause, `G3`, `D-12`). An operator moving a mounted panel from *now* to *that* is the
   same runtime flip, for a reason that has nothing to do with which line it is.
3. ⚠ **The incoming spool's profile is a DIFFERENT artefact, and conflating the two is part of what
   let `A3` survive** — `G120`'s sweep had to be classified rather than run for exactly this reason.
   At FL2 **check-in** the operator reviews the recorded profile of the
   **FL1 pass that produced the spool**, weld points marked — REST, static, unchanged
   ([`ActiveRunMonitor.md §3.2`](../../../screens/ActiveRunMonitor.md),
   [`[PLC §2]`](../../../../20-architecture/PLCTagSpecification.md)).
   ⛔ **That is not FL2's own trace and never was.** Both phrases are *"historical profile"*; only
   the first one moved.

⛔ **A mount-time flag forces a remount**, which loses the ring buffer, re-subscribes the hub, and
re-triggers the replay-on-join — visible as a flicker and a gap in the trace at exactly the
moment an operator is watching for drift.

### 2.3 The window is a distance, not a duration — ⚠ and **five** cadences are in play

AC 3 asks for *"a fixed ~500-point window"*. ⚠ **`FR-018` gates the `RunReading` write on
footage — 4 ft per data point — not on a millisecond tick.**

So the row rate is **speed-dependent**: `(FPM ÷ 60) ÷ spacing_ft`. A 500-point window is
**2,000 ft** at 4 ft spacing, and its wall-clock duration changes as the line speeds up or slows.

⚠ **That is correct for a gauge trace** — an operator reasons about drift **over material**, not
over time — but it means the x-axis is footage and a time-based buffer eviction would be wrong.

⛔ **There are FIVE cadences, not four, and the plan had two of them conflated.** ⚠ **The ~100 ms
figure is the SEND drain, not the ingest** — `appsettings.json` names all three of its own in one
comment, and the tag read is **1 s**, ten times slower than the drain that forwards it:

| Cadence | Value | Where it is set |
|---|---|---|
| **The tag read (ingest)** | **1 s** — ⛔ **and 1 s is the FASTEST permitted**: `NFR005`'s allowed set is `{1000, 5000, 10000, 30000}` ms, validated as a set, not a range | `FlatWireOpc:PublishIntervalMs` |
| **The hub send (drain)** | **~100 ms** — this is the figure the plan used to call the ingest tick | `FlatWireSignalR:DrainCadenceMs` |
| The footage gate | **4 ft** — ⚠ **`IntermediateSpacingFt` (20 ft) is bound and validated but NEVER SELECTED**: choosing it needs the run's route, which is `FW-N11`'s half of `FR-018`, so the gate uses the finer figure always | `FlatWireRecording:FinishedSpacingFt`; `FR-018` |
| **The machine's own publish rate** | **FL2 4 s** *(confirmed)* · **FL1/FL3 ~10 Hz** *(⚠ **ours**, `PLC-Q11`, confirmed or corrected by commissioning `C8`)* | `[PLC §5.2]` — the machine, not us |
| The render frame | `requestAnimationFrame` | this story |

⚠ **Why gauge and width are ARRAYS and the other four channels are not** (`P-124`, §2.2) **is this
table.** A 1 s read against a ~10 Hz instrument would drop nine samples in ten if it carried one
value; the array is how a single poll delivers the whole burst the PLC buffered. ⛔ **So do not
"simplify" the two array channels to scalars** — that is the mechanism that makes a 4 ft gate
reachable at line speed at all.

⛔ **A point count is therefore not a window — and *"point"* itself means two things, which is
where the arithmetic looks wrong until you separate them.** A **broadcast sample** is one arrival
off the hub; a **persisted row** is one `RunReading`, gated at 4 ft. So:

| 500 of them | On FL1 | On FL2 |
|---|---|---|
| **broadcast samples** | ≈**50 s** at ~10 Hz | ≈**33 min** at 4 s — a **~40× spread from one constant** |
| **persisted rows** | 2,000 ft | 2,000 ft *if the 4 ft gate is actually met* — ⛔ **on FL2 it cannot be, see below** |

⚠ **That is still the case for footage** — feet mean the same thing on both lines and a point count
does not. **Express the window in feet and let the point count fall out of it** (`P-219`, extended
by `P-344`), or an operator comparing FL1 with FL2 is reading two different pictures on one axis
label.

⛔ **But the second row of that table does NOT come out even, and this is the sharpest thing in the
section.** `FR-018` says **"FL2 always 4 ft"** ([`[REQ]`](../../../BusinessRequirements.md) `FR-018`)
while `[PLC §5.2.2]` gives FL2 a **4 s** instrument. Those two are a speed multiplication apart:

> At the simulator's **1200 FPM** setpoint (`P-277`; FL3 1320, and a board mockup shows 1,620) a line
> moves **20 ft/s**. A 4 s instrument therefore produces **one genuine reading every 80 ft** — so
> between two real FL2 readings sit **nineteen** empty 4 ft slots.

⛔ **`P-124` and `P-344` decide what goes in those slots, and the answer is nothing.** They must be
**gaps**, not the previous value carried forward and not an interpolation — so a 4 ft FL2 series is
**~95 % empty by construction**, and that is the honest rendering, not a bug.
⚠ **Say the number out loud before building the empty state**: `FW-N31` owns *"honest gaps and
visible freshness at 4 s"*, and it is drawing a trace that is mostly gap. ⛔ **A renderer that hides
sparsity to look tidy reintroduces exactly the false in-spec reading `[TRP §7]` warns about.**

⚠ **Open, and above this story:** whether `FR-018`'s *"FL2 always 4 ft"* is meant to survive contact
with a 4 s instrument, or whether FL2's recording spacing should follow its instrument. **Neither
`FR-018` nor `[PLC §5.2.2]` mentions the other**, and both post-date `G120` only on one side. Raised
in §7; ⛔ **do not resolve it by changing the gate.**

⛔ **And on a hybrid FL3 run the two cadences are in ONE series.** `[PLC §5.2.3]` re-points FL3's
finishing-end gauge at `FL2.PLC.AGC.*` (4 s) while the FM1 end reads `FL1.PLC.AGC.*` (~10 Hz), and
[`FW-192`](../../FS-13-fl3-hybrid-route/RT/FW-192.md) requires *one continuous series across both
mills*. ⚠ **A buffer that assumes a uniform inter-sample step cannot hold that** — which is the
second reason `P-344` stores the footage stamp rather than inferring position from an index.

⛔ **The built `TracePanel` contract could express none of this, and fixing it was the first thing
this story did.** `projects/shared/src/lib/shared.interface.ts` used to declare:

```ts
points: number[];          // bare readings, position implied by array index
timeLabels: string[];      // parallel array of STRINGS - actually holds footage (see below)
```

⚠ **The field name was wrong, and that was the least of it.** `pushReadings()` in
`active-run.component.ts` set `label: String(event.footagePosition)` — so `timeLabels` carried
**footage**, stringified, under a name that says time. The footage stamp therefore reached the panel
and was not thrown away, which was better than it looked.

⛔ **But a stringified label is not a position.** You cannot evict by distance from it, compute a
gap width with it, or hold a `null` in the numeric series beside it. **`points: number[]` implied
position by index**, so a missed sample silently shifted every later point.

✅ **BUILT 9 Sep 2026 — `points: (number | null)[]` and `footages: number[]`, both REQUIRED**, with
`timeLabels` kept for the axis. ⭐ **The 23-dependent warning turned out not to apply to this type**:
`TracePanel` is consumed only by `flat-wire` and by `shared`'s own `trace-panel` / `trace-chart`, and
`lib-chart-canvas` only by `trace-panel` — measured across `projects/` and `src/`, so there was one
construction site to update and optional fields would have bought nothing but a permanent `?`.
⛔ **The warning still holds for `NavRailItem`**, which slitter consumes; it was never a rule about
`shared` as a whole. ⛔ **Do not "fix" the shape further by making `points` a tuple array.**

### 2.4 A `null` renders **no measurement** — on any line — and this is still the known trap

⛔ **9 Sep 2026: every line broadcasts a live trace, so this section is no longer about FL2 at
all.** ~~FL2 broadcasts **`null`** gauge and width.~~ ✅ **The rule survives the reversal and gets
stronger**, because it stops being an FL2 variant and becomes a rule on the *one* shared trace
path — which is where [`FW-181`](../../FS-11-spool-lifecycle-fl2/RT/FW-181.md) says it always
belonged. `P-124`'s server rule is unchanged and now applies to every line: **null means no
sample — skip the channel, never send `0`.**

⛔ **So the chart must distinguish "no data" from "zero", and must never draw a flat line at
target.** A chart handed a null that draws a line at target shows an operator **a perfectly
in-spec measurement of nothing** — `[TRP §7]` still calls this *"the single most likely thing to
ship wrong"*, and it is now reachable on **all three lines** rather than being FL2's normal state.

**What a null means now**, in the order you will meet it:

| Cause | Line | Response |
|---|---|---|
| **A real footage gap between samples** | ⚠ **FL2, constantly** — 4 s of wire between points | **Render the gap as a gap.** ⛔ Never interpolate: a straight line through unmeasured wire *is* a false in-spec reading. `FW-N31` owns the rendering; `P-344` is what makes it possible |
| **A dropped feed** | any | No measurement + a **visible staleness** indication. ⚠ At 4 s a stalled FL2 feed and a healthy one look alike for seconds, so *last updated* is **load-bearing**, not decorative (`ActiveRunMonitor.md §3.2`) |
| **A paused or threading line** | any | No measurement — ⛔ **not** a fault. `SpeedFPM`, `FootageCounter`, `ComponentStatus` and `LineStatus` keep flowing, so **an absent reading is not an absent line** (`FW-181`) |

⛔ **The retired FL2 empty-state TEXT must not ship.** *"No live gauge on FL2 · see Profile"* went
with `FR-120` (`[TB §7]`, `FW-181`). The empty state now says *no measurement*, and says nothing
about which line it is on.

⚠ **Route mode still exists and is still published** — `ActiveRunResponse.RouteMode` is built and
carries the rule in its own doc comment (`P-49`) — ⛔ **but the trace no longer binds it.** That is

### 2.6 ✅ AC 3 was built to the retired contract — **CORRECTED 9 Sep 2026**

⚠ **The plan read as a greenfield build until 9 Sep 2026, and it never was one.**
`trace-window.model.ts` already implemented the sliding window, and `active-run.component.ts`
already drove it under `auditTime(0, animationFrameScheduler)` — AC 3's rAF loop. ⛔ **What was

⭐ **This was the third stale-contract residual in the code, and the only one that was not a

### 2.7 ⛔ The live update path carried DATA and not OPTIONS — found and fixed 10 Sep 2026

⚠ **This is the finding this revision adds, and it is the same class of failure as §2.5 and §2.6:
correct-looking output that is quietly not a measurement.**

A trace draws its **target line and tolerance band** from Chart.js `options` (the annotation plugin,
`buildTraceConfig`) and its **green/red point colours** from `data` — `pointBackgroundColor` is a
per-point array on the dataset (§4a, AC 1). ⛔ **`chart-canvas.component.ts`'s live branch assigned
`chart.data` and called `update('none')` without ever assigning `chart.options`.** So on any chart
that was not rebuilt, the band and target line **stayed as they were at construction** while the
colours kept moving with every frame.

**What that produces on a screen:** a point rendered **red** sitting **inside** the drawn band, or
green outside it. ⛔ **Nothing structural catches it** — the chart renders, the trace advances, the
statistics are right, and the two halves of the same judgement simply disagree.

**It is reachable by two routes, and one of them is this story's own AC:**

| Route | When |
|---|---|
| ⛔ **An `isLive` flip from a stored series to the live one** | AC 5's whole point. The mounted chart keeps the stored series' target and tolerance, because a flip must *not* rebuild (§2.1) — so the band is the old run's while the points are this one's |
| **A target or tolerance change on a mounted panel** | A pass-schedule change mid-run, or the panel being re-pointed at different material |

✅ **Fixed by assigning `chart.options` beside `chart.data` on the live path.** ⭐ **And it is free,
which is worth stating because the first draft of this fix guarded it:** Chart.js `update()` opens
with `config.update()`, which clears the resolver cache and re-reads options **on every call
whether or not the assignment happens** (`chart.js` 4.5.1, measured in its own source). ⛔ **So do
not add a change-guard, a fingerprint, or a memoised options object** — a guard would protect a
cache that is rebuilt every frame regardless, and cost a comparison per frame to do it.

⚠ **A configuration carrying no `options` at all is left to the library**, which substitutes an
empty set on the same update — guarding that in the component only adds a branch nothing reaches.

## 4. Decisions this plan makes

> `P-##` is continuous across the repository; `P-01`–`P-217` precede this story, the three minted on
> 9 Sep 2026 take the next free numbers — **`P-343`–`P-345`**, not `P-221` — and **`P-346`** is
> minted 10 Sep, verified free across the repository before it was taken.

### `P-218` — Live-versus-Profile is decided by route mode, never by data arriving

> ⛔ **SUPERSEDED IN PART, 9 Sep 2026 — see `P-343`.** Its **route-mode** half is gone: with
> `FR-120` superseded there is no per-line Live/Profile distinction for route mode to decide.
> ✅ **Its second half survives and is now the more important of the two** — *never* infer the
> display mode from whether data is arriving. **The recorded text is kept intact**, per the
> register convention.

§2.4, applying `P-49`. A chart that infers "profile" from the absence of readings shows **Live
with no data** during a pause, a thread, or a transient dropout — and shows **Profile** on a
healthy FL1 line whose first reading has not landed yet.

⛔ **Route mode is a fact about the run; data arrival is a symptom.**

### `P-219` — the window is footage-based, and eviction is by distance

§2.3. `FR-018` samples on footage, so a time-based ring buffer holds a varying amount of material
and the x-axis stops being comparable between runs.

⚠ **`FW-N11` owns `FR-018`'s number and route rule**; `FW-150` owns only the gate. **This story
owns neither** — it consumes the series as delivered. ⛔ **`FW-N11` is UNCOSTED and has no story
file** — it lives only in [`FS-20`](../../FS-20-unscheduled-unhosted.md) as the operator-session
remainder, cited against Phase 6 and never scheduled. **Do not go looking for the file**, and do not
assume the number will be configurable by the time this story ships.

### `P-220` — the two producer-less markers are recorded, not stubbed

§2.2. A stubbed marker stream that silently emits nothing is indistinguishable from a working one
with no events, and the trial would demo a trace with no weld markers **looking correct**.

**Fallback:** if a demo needs them before `FW-166`/`FW-174`, drive them from
[`FW-203`](../../FS-04-realtime-plc-backbone/RT/FW-203.md)'s simulator — **visibly synthetic**, not a silent stub.

### `P-343` — `isLive` selects the **series source and the update path**, never the line

§2.1, §2.4. Replaces `P-218`'s route-mode half. There are exactly three inputs to the flip, and the
line is not one of them:

| `isLive` | Means | Chart.js |
|---|---|---|
| **`true`** | the run happening now, from the hub — ⭐ **on FL1, FL2 and FL3 alike** | `chart.update('none')` in place |
| **`false`** | a **stored** series: a finished run's `gaugetrace`, or a spool's incoming FL1 profile at check-in | rebuild is acceptable — nothing is streaming |

⛔ **Three things must not decide it:** the **line** (`D-55` — one treatment, three lines), the
**route mode** (`P-218` superseded), and **whether data happens to be arriving** (`P-218`'s
surviving half — that is a null, and a null is `P-124`'s no-measurement state, not a mode change).

⚠ **It is not a cosmetic flag.** `ChartCanvasComponent` gates the whole Chart.js lifetime on it, so
getting it wrong costs a teardown per frame rather than a wrong label ([`FW-N33`](../../FS-11-spool-lifecycle-fl2/FE/FW-N33.md)).

### `P-344` — every buffered point carries its own footage stamp, and a gap stays a gap

§2.3, extending `P-219`. The window is footage; the **buffer** must be too. A ring buffer that
treats its array index as position, or that back-fills to keep a uniform step, **destroys the
information `FW-N31` exists to render** — and it destroys it *upstream of the renderer*, where no
frontend fix can recover it.

⛔ **This is the one place the FL2 change reaches into this story's 24 h.** At ~10 Hz on FL1 a
missed sample is invisible; at 4 s on FL2 the gaps **are the data's shape**, and on a hybrid FL3 run
both step sizes occur in **one series** (`[PLC §5.2.3]`, `FW-192`).

⚠ **Interpolating across a gap is not a display bug — it is a false in-spec reading** over wire
nobody measured.

### `P-345` — the expected cadence is per-line DATA, and the render loop is decoupled from it

§2.3. FL2 is 4 s and FL1/FL3 are ~10 Hz, so **no constant in the client may stand for "how often a
reading arrives"** — ⛔ and that includes any staleness threshold, any decimation window and,
above all, the *N-consecutive-out-of-spec* count, which [`FW-N32`](../../FS-11-spool-lifecycle-fl2/FE/FW-N32.md)
makes per line.

✅ **Half of this is already built, and the built half is the pattern to copy.**
`FlatWireOutOfSpec:ConsecutiveReadings` **defaults to 3**, is read through `IOptionsMonitor` so an
`appsettings` edit takes effect on the next request, and is **surfaced to the client on
`GET /run/active`** (`FW-164` AC 4). ⛔ **So the client already receives this number rather than
holding it** — `P-345` is satisfied for this one value and must not be re-solved.

⛔ **What is wrong is that it is ONE number for three lines.** At the built default of **3**, and at
1200 FPM: **≈0.3 s of production on FL1** against **12 s and 240 ft on FL2**. ⚠ **The config's own
comment concedes the figure is undefendable** — *"a STARTING POINT for commissioning to move, not a
derived figure: `G9`/`OI-34` leave the AGC sample rate and the latency budget undefined, so nobody
can state what three readings is in seconds"*. **On FL2 we now can state it, and it is 12 seconds.**
⚠ **The expected arrival rate has no surface at all yet** — that one is still to build.

✅ **`requestAnimationFrame` already decouples the render from the arrival rate**, which is why the
same loop serves both without a branch — the buffer fills at whatever rate the line publishes and
the frame draws whatever is in it.

⚠ **FL1/FL3's ~10 Hz is OUR figure, not the client's** (`PLC-Q11`); commissioning `C8` confirms or
corrects it. **Read it from configuration, not from this document.**

### `P-346` — whatever the panel DRAWS travels with the update that skips the teardown

§2.7. An update path that exists to avoid rebuilding the chart must carry **everything the reader
judges the trace by**, not only the series. Points are `data`; the target line and tolerance band are
`options`. ⛔ **Carrying one and not the other produces a chart whose two halves disagree** — a red
point inside the band — and it is invisible to every structural check, because the chart renders and
the trace advances.

⚠ **The general form, which is why this is a decision and not a bug note:** the *reason* for the
fast path is performance, and the temptation is always to move less. **Move everything the operator
reads.** If a future fast path skips something else the panel draws — an axis range, a threshold
line, a legend keyed to spec — the same failure returns wearing different clothes.

⛔ **Do not guard the assignment.** Chart.js re-reads and re-resolves options on **every** update
(`config.update()` → `clearCache()`, measured in `chart.js` 4.5.1's source), so a change-guard
protects a cache that is rebuilt regardless and costs a comparison per frame to do it.
