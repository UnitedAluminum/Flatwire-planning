## 2. Immediate, unbatched — and how a handler reaches the hub

`[SIG §4.2]` and [`FW-150 §2`](../../FS-04-realtime-plc-backbone/RT/FW-150.md): rare domain events are sent
**immediately and unbatched**; only gauge, width, speed, payoff weight and footage are
batched at ~100 ms, with `ComponentStatus`/`LineStatus` **on change only**.

> ⚠ **`[SIG §5.3]` is withdrawn (9 Sep 2026) and it touches only the verification method here.**
> FL2 publishes gauge and width at **4 s**, and `[SIG §5.3]` says **do not batch that stream** —
> at one sample every 4 s there is nothing to coalesce. So on FL2 there is no ~100 ms batch for a
> marker to be late behind, and the *"immediate"* check distinguishes nothing. **Run it on FL1 or
> FL3** (§5).

> ⚠ `PayoffStateChanged` must never enter the batch either — but that is
> [`FW-150`](../../FS-04-realtime-plc-backbone/RT/FW-150.md)'s, not this story's.

**The route from a command handler to the hub is a domain event**, because `[SVC §3.2]` bars
SignalR types from `FlatWire.Application`:

```
aggregate raises  →  FlatWireDbContext dispatches AFTER commit  →  handler in
(AddDomainEvent)     (PostCommit<T> lane)                          Infrastructure →
                                                                    IFlatWireClient
```

**Dispatch after commit, never before** — dispatching first broadcasts a marker for a row the
database may still reject, which is the disagreement in the story's "so that".
[`FW-208`](../../FS-02-backend-service-foundation/BE/FW-208.md) owns that plumbing and expresses
the two lanes as **types** (`InTransaction<T>` / `PostCommit<T>`, `P-97`), so a handler on the wrong
lane is a compile error rather than a review note. Every handler in this story is `PostCommit<T>`.

### 2.0 ✅ The three events this story mints — all built

`RunEvents.cs` holds **thirteen** records. ⛔ **The 29 Aug reading of *seven*, and its conclusion
that two of the four markers had nothing to translate, are both superseded** — anything still saying
`SpcCheckpointRecorded` or `DieChangeRecorded` does not exist is stale.

They follow the `P-141` precedent — **the story that broadcasts an event declares it, the story that
writes the row raises it**:

| Event | Declared | Raised by | Live? |
|---|---|---|---|
| `SpcCheckpointRecorded` | **this story** | [`FW-168`](../BE/FW-168.md) — `FlatWireRun.AnnounceSpcCheckpoint` | ✅ |
| `DieChangeRecorded` | **this story** | [`FW-167`](../BE/FW-167.md) — `FlatWireRun.RecordDieChange` | ⛔ inert |
| **`RollOverrideRecorded`** | **this story** | [`FW-169`](../BE/FW-169.md) — `FlatWireRun.RecordRollOverride` | ⛔ inert |

⭐ **`RollOverrideRecorded` is the third, and this plan never listed it.** It is not incidental: it
is the *only* thing that makes AC 3's `ComponentStatus` re-broadcast possible (§2.1), and a developer
working from the old two-row table would have built the re-broadcast with no event to hang it on.

⚠ **Every one carries `MachineName`, and it is not decoration.** `IFlatWireBroadcaster.Line(MachineName)`
is the only way to address a line group (`P-139`), so an event that cannot name its line **cannot be
broadcast at all** — this is what `FW-208` had to fix on `WeldRecorded` after the fact.

⛔ **Do not raise any of them from a broadcast handler** to make a marker appear; a marker without
its row is the disagreement this story exists to prevent.

### 2.1 The two re-broadcasts — one built, one refused

| Trigger | Re-broadcast | State |
|---|---|---|
| A roll override | **`ComponentStatus`** | ✅ **Built** — `RollOverrideComponentStatusHandler` |
| A weld | **`PayoffWeight`** | ⛔ **Refused on correctness grounds** — below |

They exist because [`FW-150`](../../FS-04-realtime-plc-backbone/RT/FW-150.md) sends `ComponentStatus`
**on change only** and derives *"change"* from a **tag read** — so a component changed through a
**command** is invisible to the loop until the next tag moves. The re-broadcast is an ordinary event
being re-sent, not a new one. ⚠ An override **adjusts an engaged component**; it does not engage or
disengage one, so the handler sends `IsActive = true`. Bypassing a stand is a pass-schedule change,
not a roll adjust.

⛔ **The weld half is not built, and that is this story's conclusion rather than an omission.**
`FW-150`'s `stagedWeights` cache — `PercentRemaining`'s denominator — **has never had an eviction
path** (`G67`), and *the weld is the payoff handover*. Re-broadcasting `PayoffWeight` after a weld
against a stale denominator publishes a **confident percentage of the previous rod**, which is worse
than the ~100 ms of staleness it removes: a stale-denominator fault reads as a plausible number, not
an error.

⚠ **And there is nothing left for it to buy.** `PayoffWeight` **already flows on the batched channel
every tick**, so the *value* is re-established within one tick regardless. Only the denominator is
wrong, and **no handler in this story can fix that** — the eviction is
[`FW-239`](../../FS-04-realtime-plc-backbone/RT/FW-239.md) AC 2's, and `[GAP]` calls it a **bug fix,
not a wiring job**. ✅ **Revisit this half when `FW-239` lands, and not before.**

⚠ **FL2 has no `Payoff{n}Weight` tag key at all** (`G71` — its load cell reports `TraversingTakeup`
and the tag surface carries only `Payoff1Weight`/`Payoff2Weight`), so an absent payload there is
expected, not a fault.

### 2.2 `LineStatus` — built from the pause/resume events, and narrowed

`RUNNING ↔ PAUSED`, reaching Dashboard 1. ✅ Built as `RunPausedLineStatusHandler` and
`RunResumedLineStatusHandler`, exactly as `P-256` specified.

⛔ **A second handler on `RunPaused`, and it must not become a second `PauseEvent`.**
`RunPausedBroadcastHandler` already sends the `PauseEvent` **marker**; these send `LineStatus`, a
**different message**. MediatR invokes *every* handler registered for a notification type, so both
run — and the check to make in review is that no `PauseMarker` goes out twice.

⚠ **`P-347` — `ContinuePause` must not announce `Running`.** The four resume outcomes are
`ResumeRun`, `LogWipRejection`, `ContinuePause` and `CheckOutRod`; **`ContinuePause` closes the pause
dialog without resuming production** — the operator looked at it and chose to keep standing. A
handler built literally from AC 2 announces `Running` on every `RunResumed` and puts a **running
line on Dashboard 1 that is standing still**. The built handler returns early and logs. ⚠ Rod
Checkout is the **fourth outcome**, not a pause reason (`OI-14`, superseding `FR-262`), and its idle
transition comes from `FW-177`'s `RodCheckedOutBroadcastHandler`.

⛔ **And the telemetry loop could not have served AC 2.** `FW-150`'s `LineStatus` channel calls
`ITagPathResolver.TryMapLineState`, which **returns `false` while `LineStateMap` is empty — i.e.
until commissioning test `C2`** — so nothing is sent, correctly and silently. That is `P-256`.

⚠ **`enum LineState` has no `Stopped` member**, deliberately. Resolve any stop edge through
the configurable `LineStateMap` (`[PLC §6]`), **never by adding an enum value** (`PLC-Q01`). The
built enum is `Running · Idle · Setup · Paused · Fault · Offline`.

⚠ **`[PLCC §6.3]` records `LineStatus` → `LineStateChanged` and `LineState` →
`LineOperatingState`.** **Not applied.** `[API §2]` and `[SIG §5.2]` are the contracts of
record and still publish the old names. **Build to `[API]`/`[SIG]`; apply the rename in one
pass across all three when arbitrated.**

### 2.3 ⚠ `P-255` — the SPC event is raised after the SAVE, not at the record

This is the sharpest trap in the story and it is not the same point as *dispatch after commit*.

`SpcMeasurement.InSpec` is a **`PERSISTED` computed column**
(`AS (CASE WHEN ABS(Actual - Target) <= Tolerance …)`), so at the moment a checkpoint is added
**every `InSpec` is still `null` in memory** and `AllInSpec` with it. An event raised in
`RecordSpcCheckpoint` would therefore carry `false` — *"out of spec"* — for a checkpoint the database
is about to judge **in spec**.

So the aggregate splits the two: `RecordSpcCheckpoint` adds the row and raises nothing;
`SpcService` saves, which loads the computed columns back; then `AnnounceSpcCheckpoint` raises
`SpcCheckpointRecorded`. **Both happen inside one transaction**, so the row and its marker still
commit together — and the *dispatch* is still `PostCommit<T>`.

⚠ **An unjudged checkpoint must never reach the handler.** `AllInSpec` is `bool?`; the marker's
`InSpec` is a plain `bool`, so a null would serialise as `false` — the one meaning the aggregate
refuses to give it. `SpcService` refuses such a request with a clear reason (`P-43`); the coalesce
in the aggregate is the backstop, not the gate.

⚠ **The marker cannot say *which* die change or roll adjust it verifies** — `OI-18`: there is no
`DieChangeId`/`OverrideId` FK, only the free-text `TriggerDescription`. The auto-link is the
requirement; the mechanism is an open item, and inventing a field on the marker would decide it.

### `P-256` — `LineStatus` RUNNING ↔ PAUSED is sent from the pause/resume events, not from the loop

✅ **Built as specified.** AC 2 requires the transition to reach Dashboard 1, and **the telemetry
loop cannot deliver it**: `LineStatus` there is derived from a PLC tag through `LineStateMap`, and
`TryMapLineState` returns `false` until commissioning `C2` (§2.2). Wiring AC 2 to that channel ships
a story that is dark in every environment, including the trial, and looks correct in code review.

**So: `LineStatus{Running}` / `LineStatus{Paused}` are emitted from the `RunResumed` / `RunPaused`
post-commit handlers**, where the state is **application-known** and needs no tag vocabulary. It
is on-change by construction — the events fire only on the edge.

⛔ **This does not make the loop's channel redundant and must not replace it.** The loop reports
what the *machine* says (`Fault`, `Offline`, `Setup`); this reports what the *system did*. When
`C2` lands, both are live and they agree on the two states they share — a disagreement is a real
signal, not a duplicate. ⛔ **And do not add an enum value to bridge them** (`PLC-Q01`).

⚠ **The same reasoning gives [`FW-177`](../../FS-10-exceptions-off-ramps/RT/FW-177.md)'s `LineStatus → IDLE` its
source** — `LineState.Idle` exists; the checkout path, not the tag map, knows the line went idle.
✅ Built there, and correctly narrowed: **only a checkout that ended the run idles the line** — a
Mode P pre-check-out takes a staged rod off a bay while the line keeps running the previous one.

### `P-347` — `ContinuePause` closes a pause without resuming, so it announces no `LineStatus`

**New, 10 Sep 2026.** AC 2 reads `RUNNING ↔ PAUSED`, which taken literally makes every `RunResumed`
announce `Running`. **One of the four resume outcomes does not resume production.**

**Resolution:** `RunResumedLineStatusHandler` announces `LineStatus{Running}` for `ResumeRun` and
`LogWipRejection`, **returns early and logs for `ContinuePause`**, and leaves `CheckOutRod`'s idle
transition to `FW-177`'s handler.

Rationale: `ContinuePause` exists so an operator can open the resume dialog, read it, and **choose to
keep standing** — the pause record closes, the line does not move. Announcing `Running` there paints a
producing line on Dashboard 1 that is stopped, and it is **invisible to any test that checks a
message was sent rather than which one**. ⚠ **This narrows an acceptance criterion**, so it belongs
on the card as much as here; the card is `[TB §7]`'s to amend.
