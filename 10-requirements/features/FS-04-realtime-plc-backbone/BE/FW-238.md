## 2. Context you need

### 2.1 Five tables, four of them written, and the order between them is the whole design

`11_` touches five `CommonDB` tables in dependency order, because each one is keyed by something the
previous one produces. ⚠ **Only four are written** — `OPCServers` is a **lookup** and is read
(`D-48`, §2.1a). The counts below are the script's, and `11_`'s §5 verification block asserts every
one of them.

| # | Table | Rows this story writes | Keyed by |
|---|---|---|---|
| 1 | `OPCModules` | **1** — `OPCModulesIdx` **6**, `ModuleName` `FlatWire` | Nothing. The id is *forced*, not allocated (§2.4) |
| 2 | `OPCServers` | **0 — READ ONLY.** Two existing endpoints are read, never written | ✅ `OPCServersIdx` **1 and 2** — `G97`, answered by `D-49` |
| 3 | `OPCServerApplicationMapping` | **4** — each line onto **both** endpoints, `ConnectionSequence` 1 and 2 (§2.1b) | the module, the two servers, and `machines` 125 / 126 |
| 4 | `OPCTags` | **41** — 39 data + **2 system-error** | `TagName`, unique because every path begins `FL1.PLC.` or `FL2.PLC.` |
| 5 | `OPCTagApplicationMapping` | **41** — **18** on machine 125, **23** on 126 | tag × machine × module |

⛔ **The order was enforced by the script and by nothing else — and as of `09_` that is no longer
true.** As written, `OPCTagsIdx` carried **no foreign key anywhere in source control**, `OPCTags` had
no primary key and no unique index, and `OPCServersIdx` had no foreign key either — so idempotency
here was `11_`'s own guards, not the schema's. That is also why `16_` deletes mappings **before** the
rows they point at: reversed, the mapping rows are orphaned with no error, the natural key `11_`
matches on stops resolving, and the next run **inserts duplicates instead of skipping**. It is why
`11_`'s §5 fault queries gained a **dangling-endpoint** check: nothing in the schema would notice a
mapping pointing at an endpoint that is not there.

✅ **[`09_`](../../../../30-database/scripts/09_CommonDB_OPCTables_Constraints.sql) closes that hole, and
it is ordered before `11_` for exactly this reason** — §2.1c. ⚠ **Read the paragraph above as the
*pre-`09_`* state**, which is still the state of every environment where `09_` has not been run. The
guards in `11_` are **not** removed by it: they stay as the belt to `09_`'s braces, and they are what
makes `11_` re-runnable on an instance that is still unconstrained.

### 2.1a ⛔ `OPCServers` is a lookup — the endpoint is chosen, not created (`D-48`)

The endpoints are **site infrastructure shared by every module that connects**, not per-module data.
`CommonDB.dbo.OPCServers` already holds `UAOPC1`–`UAOPC4`, all of class `SWToolbox.TOPServer.V6`,
and flat wire becomes **one more consumer of two of them** (§2.1b) rather than the author of a
fifth row. Four things follow, and the fourth is the one worth reading twice:

1. **`11_` performs no `INSERT` and no `UPDATE` against `OPCServers`.** §4b reads the rows and
   prints them, so the run records which endpoints it used.
2. **`11_` carries no `@OPCServerName` and no `@OPCServerClass`.** Nothing it does needs either,
   and a variable for either one invites exactly the insert this decision forbids. It addresses
   endpoints by id instead — §2.1b (a) is the second, sharper reason for that.
3. **Guards replace them**, outside the transaction: the endpoints must already exist (the abort
   **prints the ones that do**, so the reader gets the answer with the error).
4. ⛔ **`16_`'s old *"delete the endpoint if no module still maps it"* step was WRONG, not merely
   unnecessary.** An endpoint nothing currently maps is still infrastructure; deleting it on the
   strength of *our* rollback would have removed somebody else's lookup row. That step is gone.

⚠ **This does not by itself say *which* endpoint** — only that the answer has to be a row that
already exists. §2.1b is the answer, and what it turned out to mean.

### 2.1b ✅ `G97` answered — and neither half of the answer was the shape of the question (`D-49`)

**The lines use the OPC UA endpoint pair at `OPCServersIdx` 1 and 2, and both lines map to both.**
Client direction. Two things about that sentence were checked against the instance before anything
was written, and **both checks changed the script**.

**(a) The ids do not match the names — so the endpoint is addressed by id.**

| `OPCServersIdx` | Name | | `OPCServersIdx` | Name |
|---|---|---|---|---|
| **1** | **`UAOPC3`** | | 3 | `UAOPC1` |
| **2** | **`UAOPC4`** | | 4 | `UAOPC2` |

⛔ *"`OPCServersIdx` 1 and 2"* is therefore the **`UAOPC3`/`UAOPC4`** pair — **not** `UAOPC1`/
`UAOPC2`, which is what the names invite you to assume and which is **a different pair, serving
`CoilReceiving`, `Handheld Service` and `Furnace Scheduling`**. ⛔ **A name-based selector gets this wrong silently**: with an
`@OPCServerName`, *"1 and 2"* is transcribed as `UAOPC1`/`UAOPC2` and the lines are pointed at the
wrong endpoints **with no error at any layer** — the guard passes, the mapping writes, `GetOPCInfo`
answers. `11_` §1 therefore carries **ids**, because ids are what the instruction gives *and* what
`OPCServerApplicationMapping` stores; §4b prints the names so a reader can still see which rows
they are. ⚠ **Re-check per environment** (`G96`'s rule, applied to a second column): the
numbering is an artefact of insertion order, so the right numbers elsewhere may be the wrong pair.

**(b) It is a primary/failover pair, not a per-line split — so §4c writes four rows, not two.**

`11_` `D9` asked whether FL1 and FL2 sat behind *one* endpoint or *two*. That framing has no
correct answer, and the table says why:

| Measured on `DEV00164-001`, 5 Sep 2026 | |
|---|---|
| `(module, machine)` pairs in `OPCServerApplicationMapping` | **37** |
| …carrying **exactly two** endpoint rows, `ConnectionSequence` 1 and 2 | **37 — all of them** |
| …carrying one | **none** |
| `GetOPCServerAndTagDetails` result set 2 | `ORDER BY MachineId, ConnectionSequence` |

So the sequence is **consumed, not decorative**: the procedure hands the client an *ordered* server
list per machine — primary first, failover second. ⛔ **A one-row-per-line mapping would have made
flat wire the only machine in `CommonDB` with no failover, and would have looked like a working
registration right up until the primary endpoint dropped.** §4c is now a `CROSS JOIN` of the two
lines with the two endpoints, and two fault queries were added: a line without a full pair, and a
duplicated `ConnectionSequence`.

⚠ **One thing measurement could not settle, and it is left as a named assumption.** `11_` makes id
**1** the primary, taking *"1 and 2"* in the order it was given. **The precedent points the other
way**: `Hole Detection` — the only other module on this same pair — uses id **2** as its primary on
all three of its machines. Flipping the two `DECLARE`s in `11_` §1 is the entire change if that is
what is wanted; nothing else depends on which is which.

### 2.1c ✅ `09_` — the five tables are heaps, and every guard in `11_` exists because of it

**All five `CommonDB` OPC tables have no primary key, no unique constraint, no foreign key, no check
constraint and no index of any kind.** Measured on `DEV00164-001`, 5 Sep 2026:

| Table | Rows | Pages | PK | Unique | FK | Index |
|---|---|---|---|---|---|---|
| `OPCModules` | 4 | 1 | none | none | none | none |
| `OPCServers` | 4 | 1 | none | none | none | none |
| `OPCTags` | 496 | 4 | none | none | none | none |
| `OPCServerApplicationMapping` | 74 | 1 | none | none | none | none |
| `OPCTagApplicationMapping` | 882 | 5 | none | none | none | none |

⛔ **This is a migration defect, not a design choice.** The legacy `united_db` predecessors —
`OPC_Tags`, `OPC_Servers`, `OPC_Tag_Application_Mapping`, `OPC_Server_Application_Mapping` — **do**
carry primary keys and two foreign keys, under `Databases\united_db\Tables\OPC_*\Constraints\`. The
constraints were dropped when the tables were migrated into `CommonDB` and never re-created; git
history shows no key ever existed on the `CommonDB` copies.

**Read `11_`'s own header against that table and the connection is exact** — every hand-written
guard in it is standing in for a missing constraint:

| `11_` guard, in its own words | What `09_` replaces it with |
|---|---|
| *"`OPCTags`: No primary key and no unique index of any kind exists on this table in source control. Idempotency is therefore enforced by this script's own guards, not by the schema"* | `PK_OPCTags` · `UQ_OPCTags_TagName` |
| *"Guard: `ModuleName` has no unique index, so a duplicate would make the id lookup ambiguous"* | `UQ_OPCModules_ModuleName` |
| *"A duplicate (machine, module, tag) mapping. The table has no unique index to prevent it"* (fault query) | `UQ_OPCTagApplicationMapping_Module_Machine_Tag` |
| *"A duplicated `ConnectionSequence` on one line … No unique index prevents it"* (fault query 8) | `UQ_OPCServerApplicationMapping_Module_Machine_Seq` |
| *"A server mapping pointing at an endpoint that does not exist … `OPCServersIdx` carries no foreign key"* (fault query 6) | `FK_OPCServerApplicationMapping_OPCServers` |

`09_` adds **5 clustered primary keys, 6 unique constraints, 4 foreign keys, 1 check constraint and
2 indexes**. It **writes no row and alters no column** — it only `ALTER`s five tables.

⚠ **It is an integrity fix, not a performance one — and measurement after the run proved that
harder than intended.** `SET STATISTICS IO` for `GetOPCServerAndTagDetails`, same 11 machines and
module 4, across all five tables:

| | Logical reads |
|---|---|
| Before `09_` (all heaps) | **21** |
| After `09_` | **269** |

⛔ **The plan predicted "at or below 21" and was wrong — reads went up ~12×.** The cause is not a
missing index: `GetOPCServerAndTagDetails` builds `@machines` as a **table variable**, which the
optimiser estimates at **1 row**. With only heaps it had to hash-join over one scan of each tiny
table; with seekable indexes available it switches to **nested loops and repeats a seek per
machine**, and on 1–5 page tables repeated seeks cost more than a single scan.
`OPCServerApplicationMapping` went 1 → 70 reads and `OPCServers` 1 → 68.

⚠ **This does not argue for reverting anything, and no covering index would fix it** — the problem
is cardinality estimation, not access paths. In absolute terms 269 logical reads against five
fully-cached 1–5 page tables is sub-millisecond, and **the results are unchanged and still correctly
ordered** (result set 2 by `MachineId, ConnectionSequence` — verified after the run). If it is ever
worth removing, the lever is `OPTION (RECOMPILE)` on the procedure's statements, **not** an index —
and that is a change to a shared procedure, outside this story.

⛔ **No foreign key on `Machineidx`, and it is not an omission.** The `dbo.machines` both mapping
tables join is a **`CommonDB` VIEW** over `united_db..machines` (§5.2 finding 7). SQL Server supports
neither cross-database foreign keys nor foreign keys to a view. All 74 + 882 values were verified
valid against `united_db.dbo.machines` — **0 orphans** — but the rule is not expressible. This
matches `LabelButtonMachineMapping` and `OptionButtonMachineMapping`, structurally identical mapping
tables that likewise carry no FK on their machine column.

⚠ **The mapping-table natural keys lead with `OPCModuleId`, not `Machineidx`.** Column order does not
change what a unique constraint *enforces*, but it decides whether it is usable as an index —
and `OPCModuleId` alone is the predicate in all three result sets of `GetOPCServerAndTagDetails`
**and** in both `DELETE` statements of `16_`.

Verified independently after the run: **0 heaps · 5 PKs · 6 uniques · 4 FKs · 1 check · 2 indexes ·
0 untrusted FKs**, and row counts **unchanged** at 4 / 4 / 496 / 74 / 882, which is the proof it
wrote no data. Its pre-flight passed **16 checks, 0 conflicts**, so every object was created with no

### `P-318` — the story has an **authored** half and an **activated** half, and only the second closes `G60`

The DB 8 h bought a script; a script that has never run registers nothing. But holding the card open

**So the card is worked as two halves with different exit conditions.** *Authored* — `11_`, `16_`,

*Activated* — steps 5–9 — is a **commissioning-window event** gated on three outside answers, and it

scheduled rather than assumed.

### `P-319` — the activation order is fixed, and each step's tripwire is named

Steps 5–9 of §3 in that order, because **three of the four possible mis-orderings fail silently**:

| Wrong order | What you see | What is actually true |
|---|---|---|
| Run `11_` before the `machines` rows exist | ⛔ **Nothing — it aborts loudly.** The one safe mis-ordering | The guard did its job |

**Only the first of those four is self-reporting.** That asymmetry — one guard, three silent
failures — is why the order is written down as a decision rather than left to the runbook.

### `P-321` — the `UAL.Constants` enum change is proposed as documentation, and never becomes a dependency

`G60`'s original text named a missing `OPCModules` member as half the gap. Measured 5 Sep 2026, it
is not: **no line in the FlatWire codebase evaluates the enum** — every occurrence is a comment or a
log string — `ResolveOpcInfoAsync` sends `options.OpcModuleId`, a plain config int, and

**Adding `Slitter = 5` and `FlatWire = 6` is still worth doing**, because an enum that omits a

### `P-322` — a shared **lookup** is joined, never seeded, and the guard that enforces it hands back the answer

`D-48` settles that `CommonDB.dbo.OPCServers` takes no `INSERT` and no `UPDATE` from flat wire
(§2.1a). Recorded as a decision here for two reasons that outlive the edit.

**First, it is the same call as `D-32`, one table down.** `D-32` bound the `coils` / scheduling
schema as *read and written as it stands and never altered*; `D-48` says the OPC endpoint register
is read as it stands too. The test that separates the two halves of the registration is **who owns
the row**: `OPCModules` id 6, the two mapping tables and the 41 tag rows are **ours** — nothing else
in the ecosystem refers to them, which is exactly why `16_` can reverse them on a DEV instance.
The endpoint is **not ours** under any reading, and the giveaway was already in `G97`'s own
measurement: four endpoints existed and were serving other modules before flat wire was designed.

**Second, the abort is a better instrument than the variable it replaced.** An `@OPCServerClass`
looks like a field to fill and is really a field to *not fill*, so it makes a wrong action available
at the exact moment someone is under commissioning-window pressure. What replaces it is a guard that
**prints the endpoints and stops** — the failure hands the reader the list rather than an empty
column to guess at. ⚠ **The rule that guard protects:** an endpoint that is not there is a request
to whoever owns `CommonDB`'s OPC estate. It is never a reason to add an `INSERT` back to `11_`.

### `P-323` — a two-number answer that had two wrong readings, and measurement caught both

`G97` was answered as *"`OPCServersIdx` 1 and 2 will be used for OPCUA"* (`D-49`). Eleven words,
and **both of the obvious readings of them were wrong** (§2.1b). Recorded because the near-miss is
the reusable part, not the ids.

**The name/id reading is silently wrong.** A name is legible and an id is not, so selecting the
endpoint by `@OPCServerName` reads like the better design. But ids 1 and 2 are `UAOPC3`/`UAOPC4`,
so under a name selector *"1 and 2"* is transcribed as `UAOPC1`/`UAOPC2` — **ids 3 and 4, the pair
three other modules use** — and nothing raises an error anywhere: guard passes, mapping writes,
`GetOPCInfo` answers, lines point at the wrong server. ⚠ **The lesson is narrower than "prefer
ids"**: when an instruction arrives in a particular key, resolve it in that key. Translating ids
into names on the way in adds a step whose only possible contribution is an error.

**The one-or-two reading is wrong later, which is worse.** The lines do not split across two
endpoints; they **share a primary/failover pair**, which is what all 37 existing `(module, machine)`
mappings do and what `GetOPCServerAndTagDetails`' `ORDER BY … ConnectionSequence` exists to serve.
⛔ Two rows instead of four **registers successfully, verifies successfully, and works** — until the
primary endpoint drops, at which point flat wire is the only machine in `CommonDB` with nowhere to
fail over to.

**What both have in common** is that the answer was checked against the table before being typed
into the script, at a cost of two queries. ⚠ **It is the same move that found `G100`**, and the same
move behind `D4`'s *"single words"* correction. **Three for three on this story: every claim about
`CommonDB` that was reasoned rather than measured has turned out wrong.**

⚠ **The residue.** One assumption is left and it is not measurable: which of the pair is the
primary. `11_` takes the order given (1, then 2); `Hole Detection` does the reverse on the same
pair. Named in §2.1b, in `11_` `D14`, and in §7 — flipping two `DECLARE`s is the whole change.

### `P-331` — the merge gate is verified by **ancestry**, and "built and green" is not a state of it

`FW-236` moved three times in one day — `not-started` → built and green in a working tree →

### `P-332` — a text-matching conformance check over these scripts must strip comments first

**Every prohibition in `08_`, `09_`, `11_` and `16_` is documented *inside the script*, in the words
of the thing it forbids.** So a grep for the forbidden string finds it — in the sentence saying not
to write it. The execution pass's first conformance sweep produced **seven** failures and **all
seven were this**: `ns=` in a header note and inside fault query 2's own `LIKE 'ns=%'`;

`DELETE <alias> FROM` form that a `DELETE FROM <table>` pattern does not match.

⛔ **The scripts are not going to stop doing this, and they should not** — the comment is what makes
the prohibition survive an edit. **The checker is what has to change:** strip comments first, match
second, and distinguish a table variable from a table. ⚠ **The failure direction is the expensive
one** — seven false alarms in a check that is meant to be cheap is how the check stops being run.

### `P-333` — a gate must name the branch that carries the module, not the branch that sounds important

⛔ **Step 6 blocked this story for three passes on a merge into `release/mvp-3.x`, and
`release/mvp-3.x` does not contain `API/Domain/FlatWire`.** The gate was real, the diagnosis behind
it (`G94`) was correct and remains correct, and the branch it named was the wrong one — flat wire

✅ **The method was never the problem.** `P-331` said *verify by ancestry, not by "built and
green"*, and that was right and stays. What `P-331` did not say is **ancestry of what**, and the
answer is not a fixed branch name — it is *the branch this environment's `OPCConnection` is
built from*, which differs by environment and will differ again at staging and production.

⚠ **The check that would have caught it is one line, and it is cheap enough to keep:**

```bash
git ls-tree -d --name-only origin/<branch> API/Domain/ | grep -q FlatWire \
  || echo "this branch does not carry FlatWire - is it really the gate?"
```

⛔ **The generalisation worth keeping:** a gate expressed as *"wait for X to reach branch B"*
carries a hidden claim — that B is where the thing being protected runs. **Write that claim down
and measure it**, because when it is wrong the gate does not fail loudly; it simply never opens.
`D-51`.
