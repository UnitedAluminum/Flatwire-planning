## 2. The details that decide it

### 2.1 The rule leads and the index backstops — AC 3 is inverted

AC 3's **intent** is right and is the point of the story: no read-then-write check may *decide*
whether a second rod lands on an occupied bay, because that has a race window and two rods on one
physical bay is what `G21` recorded.

⛔ **But its letter — *"not from application-level checking"* — was superseded by `G21`'s fix,
which is three layers, not one.** The built domain states the order in its own comment:

> *"⚠ THIS RULE IS THE DESIGNED DEFENCE AND THE INDEX IS BELT-AND-BRACES — not the other way
> round. `UX_RodStaging_Bay` … is verified on a live deploy; this rule must hold WITH THAT INDEX
> ABSENT."*

So the handler **must** read the bay: `BayAlreadyOccupiedRule` takes `occupyingRod` as a
constructor argument, and its own remark says *"the caller reads this; the rule does not, because
a rule performs no I/O (`P-93`). **Pass `null` only when a query has actually shown the bay
empty.**"*

**Both layers answer the same `409`,** which is why having both costs the client nothing:
`MapUniquenessViolation` matches the index name and returns `409 BAY_OCCUPIED`; the rule arm takes
the status off `RuleViolationKind` as data (`P-89`, `P-90`) and returns `409` with the same
`[API §1.8]` code. `[API §4.5]`'s *"`409` from the index, not a read-then-write race"* is satisfied
either way.

⛔ **`FW-264` committed the test that pins this** —
`An_occupied_bay_is_refused_by_the_domain_with_no_database_present()`, which is the evidence
`G21`'s register row had been owed since 15 Aug 2026 and got on **10 Sep 2026**. Removing the
pre-read deletes the only thing that makes that test meaningful.

⛔ **`G21`'s shape still matters.** FL1 and FL3 **share one physical payoff** —
`STATION_BY_LINE = {FL1:"FL1PO", FL3:"FL1PO"}` — so both the index and the rule are keyed on the
**station**, never on `MachineName`. **A handler that scopes the read by `MachineName` re-opens the
gap with the index still in place and satisfied** (`P-183`).

⚠ **Two indexes, two rules, two client actions — do not collapse them.**

| Invariant | Index | Rule | `409` code | Client action |
|---|---|---|---|---|
| One rod per bay | `UX_RodStaging_Bay` (`Station`, `PayoffPosition`) | `BayAlreadyOccupiedRule` | `BAY_OCCUPIED` | Re-read the **bay** |
| One bay per rod | `UX_RodStaging_RodActive` (`RodAlpha`) | `RodAlreadyStagedRule` | `ROD_ALREADY_STAGED` | Re-read the **rod** |

Neither implies the other, `RodStaging.Stage` checks both, and the middleware's own remark says
*"collapsing these to one generic `409` loses the client's branch."* The handler therefore performs
**two** reads — the occupant of this bay, and this rod's existing bay — and passes both in. That is
two indexed single-row lookups on the write path; the cost is negligible and it is what buys the
readable refusal message the operator acts on.

### 2.2 `Blocked` is derived, and a `Fail` returns `201`

The rule changed on 31 Jul 2026 and the old behaviour is the intuitive one, which is why it
needs stating: an inspection `Fail` **commits the staging row** and returns **`201`** with
`state: "Blocked"` and the WIP-rejection route. **No override** (`CHK010`).

The reason is physical: **the failed bundle is on the bay.** Writing nothing would leave the
system believing a bay is free while a rod sits on it.

⛔ **`Blocked` is `Status='Staged'` + any inspection column `='Fail'`.** It is **never a fourth
`Status` value**, and `IsWelded` is a **flag on a `Staged` row**, not a status either. So any
handler branching on *"staged"* also matches welded and blocked rods **unless it says
otherwise** — and that is the single most likely bug in this story (`P-184`).

✅ **The aggregate already exposes both predicates** — `IsBlocked` and `OccupiesBay`, the latter
carrying *"⚠ Matches welded and blocked rods too … this is the predicate `UX_RodStaging_Bay`'s
`WHERE Status='Staged'` filter mirrors."* **Use them; do not re-derive either in a handler.**

⚠ **`FW-146` must not re-map the `Fail` response** — the controller's own remark says so, and
`[API §1.8]`'s `INSPECTION_FAILED` row was qualified for exactly this reason.

### 2.4 The inspection is three items

`G14`: `RodStaging` and DB2A deliberately use **3 inspection items** and `R#####` alphas, and
**do not inherit a 4th item**. ⛔ **Do not add a connector-tag item** — the connector tag belongs
to check-in (`[API §4.6]`), and the built validator says so.

⚠ **`G14`'s check-in half is a different matter**: the DDL builds four inspection columns
`NOT NULL` plus `SpcM1In`/`SpcM2In`, and `POST /checkin/rod` supplies none, so **every check-in
insert fails as specified** (`REVIEW.md` Tier 1 #5). **That is [`FW-157`](FW-157.md)'s problem, not
this story's** — but the two must not disagree about how many items there are.

### 2.5 The state change is raised, not broadcast

`FW-160` owns `PayoffStateChanged`. This story **raises `BayStateChanged`** as a domain event
(`FW-208`'s lane) so the broadcast happens without a handler here touching SignalR (`P-35`,
`P-101`). ✅ **The aggregate already raises it** on `Stage`, `MarkWelded`, `ConsumeAtCheckIn` and
`Unstage` — the handler adds nothing.

⚠ **A failed weld changes no bay state and broadcasts nothing** (`FW-160` AC 2) — which the
aggregate honours by only reaching `MarkWelded` on a **passing** weld.

⚠ **Dispatch order is load-bearing and already correct** — `SaveEntitiesAsync` dispatches
**before** the save, deliberately (`FW-208`). ⛔ **Do not reorder it.**

### 2.7 Unstage is more than a Mode P row

The card says only *"writes `RodCheckout` with `Mode='ModeP'`"*. `[API §4.5a]` and the built rules
require the whole shape, and the welded half is client-decided (`Q69`/`Q72`, 30 Jul 2026):

| Rod state | Approval | `RodCheckout.NewRodStatus` | Enforced by |
|---|---|---|---|
| **Not welded** | None — operator-only, reason captured | `RECEIVED` | — |
| **Welded** (`IsWelded = 1`) | **Supervisor override** — badge/ID + PIN + reason | **`HOLD`** | `CK_RodCheckout_ModePWelded` · `WeldedRodRemovalIsPreRunOnlyRule` |

- `RodStaging.Status → 'Unstaged'`, `UnstageKind = 'PreCheckOut'` — the aggregate's `Unstage` does this.

## 4. Decisions this plan makes

> `P-##` is continuous across the repository; `P-01`–`P-353` precede this story's new entries.

### `P-183` — the bay conflict is never scoped by line *(unchanged)*

§2.1. `G21`'s fix is that FL1 and FL3 **share** `FL1PO`, and both `UX_RodStaging_Bay` and
`BayAlreadyOccupiedRule` are keyed on the station. A handler that filters by `MachineName` before
writing would find the bay free for FL3 while a FL1 rod occupies it — **the exact defect, with the
index still in place and satisfied.**

### `P-184` — no branch says "staged" without saying what it means about welded and blocked *(unchanged)*

§2.2. `Blocked` is derived from `Status='Staged'` plus a `Fail`, and `IsWelded` is a flag on a
`Staged` row. **Every predicate over `Status='Staged'` must state explicitly whether it includes
welded and blocked rows.** `BayStateChanged` already carries all three separately (`P-139`); the
handlers must preserve that. *(Applied by `FW-N06`'s `P-189` and `FW-166 §2.3`.)*

### `P-185` — ✅ **RESOLVED: `MarkStagedRodWeldedCommand` is not built**

§2.3. The question was whether the command survives its endpoint's retirement.
[`FW-166 §2.4`](../../FS-09-in-run-production-events/BE/FW-166.md) took the resolution, as the
surviving write path, and answered it: **there is one weld write and it is `POST /weldevent`.**
`RodStaging.MarkWelded()` already exists and is called from there. **`FW-158`'s AC 2 is struck on
this item** — building the command would be the third silent no-op of the class `FW-208` found.

### `P-354` — the domain rule leads; the pre-read is required, not a defect

§2.1. AC 3 forbids *relying* on an application-level check, and `G21` was fixed in **three**
layers with the register recording the index as *"belt-and-braces, not the sole defence"*.
`BayAlreadyOccupiedRule` and `RodAlreadyStagedRule` take their occupancy facts as **arguments**
(`P-93`), so the handler performs two indexed single-row reads and passes both in. ⛔ **A future
reviewer "simplifying" this by deleting the reads breaks `FW-264`'s
`An_occupied_bay_is_refused_by_the_domain_with_no_database_present()`** and removes the readable
refusal message — while the outcome stays `409` either way, because both middleware arms agree.

### `P-355` — this surface writes only `FlatWireDB`, and builds no compensation

§2.6. `Q68` moved the queue insert, the requirements summary and the `wip_coil_orders` insert to
check-in. Pre-check-in therefore has **no effect outside the flat wire system**, and pre-check-out
has **nothing to undo**. ⛔ **Do not build a compensating write, a cross-database reversal, or an
ordering guard on either path** — `FW-N24` owns the move and `FW-220`/`FW-221` own the procedures.
⚠ **`[API §4.5]`/`[API §4.5a]`'s *"still the open half of that question"* is stale prose**; build
the local shape, and do not restore compensation because a contract note implies it.
