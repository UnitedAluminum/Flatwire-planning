# FW-181 · The shared trace path — the no-measurement state

> ### ⭐ Re-pointed 7 September 2026 by `D-55`, and re-planned 9 September 2026 by `G120`
>
> **The Live/Profile binding is gone** — the trace treatment is uniform across FL1, FL2 and FL3, so
> there is no per-line control to bind. ✅ **The null rule survives and gets stronger:** it is now a
> rule on the *one* shared trace path rather than an FL2 variant, which is where it always belonged.
>
> ⛔ **And as of 9 Sep 2026 the FL2 premise underneath this story is retired too.** `A3` is retired
> and **`FR-120` is superseded**: FL2 broadcasts **live** gauge and width at **4 s**, from the
> gauging stands downstream of FM2-S3. So there is **no suppression to verify**, **no
> *"No live gauge on FL2 · see Profile"* text**, and **no Profile-as-default**. `G120`.
>
> ⛔ **The rule, unchanged and still the whole point of this story:** a `null` gauge or width reading
> renders as **no measurement**, never as a value at target. A chart handed a null that draws a flat
> line at target shows an operator *a perfectly in-spec measurement of nothing* — and `[TRP §7]`
> still calls this **the single most likely thing to ship wrong**.
>
> ⭐ **What the reversal changed is the rule's REACH, and it got wider.** It used to describe FL2's
> permanent state; it now describes **a real event on any of the three lines** — a footage gap, a
> dropped feed, a paused or threading line. ⚠ **On FL2 at 4 s a gap between samples is the *normal*
> case**, so this is no longer a rare path exercised only on one line.
>
> ⚠ **An absent reading is still not an absent line.** `SpeedFPM`, `FootageCounter`,
> `ComponentStatus` and `LineStatus` keep flowing. ⛔ Treating the absence of `GaugeReading` as a
> fault is a defect — that half never depended on `FR-120`.

> **Why this document exists.** Four hours, and `[TRP §7]` singles it out: ***"This is the
> single most likely thing to ship wrong."***
>
> The failure is specific and it looks like success. **A chart handed a `null` that draws a flat
> line at target shows an operator a perfectly in-spec measurement of nothing.** ⛔ It is not a
> blank panel and not an error — it is a *plausible* reading, which is why nobody catches it.
> **The mockup animates a simulated trace** — because a static prototype has no hub — **and the
> built screen must not.**
>
> ⚠ **The old framing made this an FL2 story. It never was one.** Until 9 Sep 2026 the null was
> FL2's permanent state, so the rule looked like an FL2 variant and was verifiable only there.
> With `FR-120` superseded it is a rule on **the one shared trace path**, and the null is an
> **event** — which means it is now reachable on FL1 and FL3 as well, where nobody was looking
> for it.
>
> Two more, each easy to get backwards: **`null` is not silence** — speed, footage, component and
> line status keep flowing, so an absent reading is not an absent line. And **a stored profile is
> static** — it must not be re-sampled by the live tick.

## 2. The contract — ⛔ every line sends live gauge and width

**Reversed 9 Sep 2026.** ~~`FR-120` and `[SIG §5.3]`~~ — `FR-120` is superseded and `[SIG §5.3]`
is withdrawn. FL2 falls under **`FR-101`** like every other line.

| Channel | FL2 | FL1 / FL3 |
|---|---|---|
| Live **gauge** | ➕ **Sent** — `FL2.PLC.AGC.Gauge`, `REAL`, inches, **4 s**, **unbatched** | Sent, ~10 Hz, batched |
| Live **width** | ➕ **Sent** — `FL2.PLC.AGC.Width`, same | Sent, same |
| `SpeedFPM` · `LineStatus` · `FootageCounter` · `ComponentStatus` | ✅ emitted | ✅ emitted |
| `PayoffWeight` | ⚠ **Not sent on FL2** — `RodStaging` is FL1/FL3 only, and FL2 feeds from a spool. **Expected, not a fault** | ✅ emitted |

⭐ **`PayoffWeight` is now the ONLY FL2 asymmetry on this hub, and it is the one that is
independently confirmed** rather than assumed: `Q30` — *"there are no available loadcells installed
on the take-ups or payoffs"* — the same mail that **falsified `A2`**, the assumption sitting
directly above the retired `A3` in the same table.

⛔ **AC 1 lists `PayoffWeight` among the channels that flow on FL2, and the built loop cannot send
it** — its denominator is the staged rod's net weight from `RodStaging`, which is **FL1/FL3 only**;
FL2 feeds from a spool, whose weight lives on `SpoolCheckin` / `SpoolProcessing`. `FW-150` records
this as *"a real gap rather than a bug here"* and logs it once per bay. **Do not close it by
inventing a denominator.**

⚠ **What the old §2 asserted, and why it is worth keeping visible:** that FL2 sent no gauge or width
at all, conditioned on **standalone** mode. ⭐ **That condition was the tell.** `G40` recorded it
without drawing the conclusion — `FR-120` denied the reading to FL2 *in standalone*, never to FL2 as
a line, which is only coherent if the same instrument on the same mill switches off when the
upstream feed changes. It does not. `G120`.

### 2.1 ⛔ Still no `if (line == FL2)` anywhere — and the reason is now stronger

**The instruction is unchanged; its justification is replaced, and this matters because the old one
would have re-created the branch.**

| | Argument for "no FL2 branch" |
|---|---|
| ~~Until 9 Sep 2026~~ | ~~FL2 has no `AGC` row, so no sample is produced and *"no sample, no send"* is the suppression, reached without an `if`~~ ⛔ **Conditional on the equipment** — it justified the absence of a branch by the absence of an instrument, so **the day FL2 gained one, the branch would be back** |
| ✅ **Now** | **Every line is read identically.** There is nothing line-specific to express, in the loop or in the client — ⭐ **and no equipment change can undo that**, which is exactly what just happened |

⚠ **This is the same repair `FW-210`'s `P-270` made to the deleted `SuppressesGaugeAndWidth`
branch.** Read them together: two places justified the *right* design with a fact that then turned
out to be false.

✅ **What survives from the old §2.1 verbatim, and is still the operative server rule:**
*"a null is skipped, never sent as `0` or `false`"* (`P-124`). ⛔ **So the client's field is still
`null` by absence** — the difference is that on a healthy line it is now absent only *between*
samples, not always.

> ✅ **Built 29 Aug 2026.** `ActiveRunResponse.RouteMode` exists, is nullable, and its own doc

>
> ⛔ **MOOT FOR THE TRACE as of 9 Sep 2026** — `FW-081`'s `P-343` supersedes the route-mode half.
> `RouteMode` is still published and still needed, for the material panel and the FL3 identity;
> **the trace binds nothing.**

~~AC 5 requires toggle availability to bind to **line mode**, not `machineName`. FL2 *standalone* has
no live gauge; **FL2 running as part of an FL3 hybrid does.** A client keying on
`machineName === 'FL2'` is wrong on FL3 and will look right for the whole trial, because the trial
is Standalone throughout.~~

⭐ **THIS PARAGRAPH IS THE INTERNAL DISPROOF OF `A3`, AND IT SAT HERE FOR ELEVEN DAYS.** It recorded
that FL2 has live gauge when running as part of an FL3 hybrid but not standalone. **That distinction
was never physical**: FL3 is FL1 feeding FL2 on the **same FM2**, through the same gauging stands,
so the instrument cannot appear and disappear with the upstream feed. `A3` is retired, `FR-120`
superseded — see `G120`. FL2 has live gauge in **both** modes, so there is no
mode-versus-`machineName` trap left to avoid here: a client may key on neither, because every line
behaves the same way.

⚠ **Worth keeping as a method, not just a history:** the contradiction was **inside our own
documents**, in a story's own decision text, and no client input was needed to find it. `G120` was
filed as needing a client answer and did not.

**The server still publishes the run's route mode where the client can see it** — on the
active-run DTO ([`FW-164`](../../FS-08-active-run-monitoring/BE/FW-164.md)) and on the
`LineStatus` payload — rather than leaving the client to infer it.

⚠ **`RouteMode` is not among `[API §2]`'s fourteen canonical enums** as a client-facing field
on this path. Publishing it is a **contract addition** — non-breaking under `[API §8]` (adding
a response field), but it must be mirrored in the TypeScript union
([`FW-147 §3`](../../FS-02-backend-service-foundation/BE/FW-147.md)) and named in
[`FW-149`](../../FS-04-realtime-plc-backbone/RT/FW-149.md)'s payload if it rides the hub. **Do not let the client
derive it from `machineName`.**
