01Scope

What this covers, and what it deliberately leaves alone.

Flat wire orders are planned onto a rod or wire coil. Each order gets its own draft plan; orders travelling on the same physical coil are then merged into one plan, dividing the coil wherever the orders stop being able to share an operation. This specification covers generating, merging, saving and reversing those plans.

The mill and slitter planning path is untouched. Nothing in it was extended, reused or refactored — flat wire sits alongside it, reusing only shared framework pieces (the EF repositories, the MediatR pipeline, the plan identifier function, the coil alpha issuer) and the existing planning tables where the columns already fit.

It also covers how much of an order a coil should carry. Allocating by weight alone produces material that cannot be shipped: a 4,000 lb rod winding two 1,800 lb spools leaves a 400 lb tail, and if the customer's lightest coil is 800 lb that tail makes no shippable coil at all. Section 6 specifies the arithmetic that answers the question before any row is written.

The rules implemented here are specified in tables.md (plan types, SMP collapsing, line assignment, back to stock) and merging-logic.md (the merge rule, split points, coil numbering, the extra as-is flatten). The worked examples in merging-logic-sample-data.json are used directly as a test fixture, and the cascade strategy has its own generated fixture in balance-to-piece-sample-data.json — those two files are the acceptance spec for section 9.

Two ways of laying orders out on a coil are specified, and the planner picks. The sample data the client supplied for the merge shows two orders sharing one spool; a later review comment from the same client says a spool must never hold two orders. Rather than choose for them, both are built — see section 7. The merging one remains the default, so nothing already agreed changes without someone asking for it.

03How a plan is built

Two stages, in this order. The second reads what the first saved, so it cannot run earlier.

Stage 1 · per order

Initial plan

The item's SMP route is trimmed to what the coil has not yet been through, collapsed into at most three operations, and assigned to flat lines. Nothing is read from the database — the coil arrives on the request.

  • TempRoutings
  • TempFlatLineProcessing
  • TempMfgSalesOrderRef
  • TempOrderRemainingOperations
Stage 2 · per coil

Final plan

The saved drafts are regrouped by coil order plan and merged. The coil is walked one sequence no at a time; where the orders can no longer share an operation, it divides.

  • PlanningRoutings
  • PlanningFlatLineProcessing
  • PlanningMfgSalesOrderRef
  • OrderRemainingOperations
Both stages

Saving

A save replaces all of that plan's rows with the document's rows and records a snapshot. Because saving is a replacement, undo and redo only have to write an earlier document back.

  • FlatWirePlanAction
  • OrdersPlannedSequence
  • RoutingsLevelIdMaps

Every order planned on a coil shares one PlanId. Generating the first plan on a blank coil mints one; every later plan on that coil joins the identifier already saved. This drives the replacement scope in FR-2 and FR-4 — deleting an order's rows by plan identifier would take the other orders on the coil with them.

04Functional requirements

Eight endpoints. No generate endpoint persists anything, and neither does the solution — the caller decides whether to keep what comes back.

FR-1

Generate one order's plan

Given a coil and an order, produce the operations that order needs: routing rows, flat line rows, an order reference and a remaining operations row. The plan is returned, not saved.

A caller may supply an SMP route on the request, which takes precedence over the item's own — so a proposed route can be planned without writing it to the item first. A supplied route goes through the same progress resolution, collapsing and line assignment; there is one path, not two.

FR-2

Save one order's plan

Allocate the plan identifier, create the coil order plan, mint any stock order no, stamp all of it onto the rows, and replace that order's rows in the temp tables.

Replacement is scoped to each CoilOrderPlanId in the document, never the plan identifier. Three things can only happen here: a stock order carries a dummy order no until the plan is actually being kept, the coil order plan's identity only exists once its row has gone in, and the order's position on the coil is recorded once and never renumbered.

FR-3

Generate the coil's merged plan

Read the saved temp rows for the plan, regroup them into the per order plans they came from, and merge them into one plan for the coil. Returned, not saved.

Root operations are separated out first and copied through rather than merged — they belong to the whole coil, not to any order.

FR-4

Save the merged plan

Replace the plan's rows in the planning tables, and replace its links back to the temp operations behind them. Replacement is scoped to the plan identifier, because the merged plan covers the whole coil.

FR-5

Plan a coil in one call

Generate and save each supplied order in turn, then generate and save the coil's merged plan — one request, one transaction.

The plan identifier allocated by the first order saved is threaded into every later order in the run. Each save is journalled under its own stage, so undo steps back through a run one stage at a time rather than treating it as a single opaque action.

FR-6

Undo and redo

Step a plan back to the state before its last action, or forward again. Recording a new action prunes the forward branch, so acting after an undo abandons what was undone.

No inverse logic exists per action type. Undo writes the previous snapshot through exactly the path a save takes, so any future edit becomes undoable with no work.

FR-7

Plan onto a coil that carries root operations

When operations have already been planned on the whole coil, an order's own operations start after them — taking the next sequence no and hanging from the last root level. Any number of root operations is supported.

FR-8

Remove a plan or its orders

Deleting a plan, or removing all assigned orders, takes the flat line processing rows with it — from both the per order and the merged tables — under the same sub plan and sequence filter the routings use.

FR-9

Plan several coils in one call

A run takes a list of coils and a list of orders. Each coil carries at most its own weight, so an order too heavy for the coil it starts on continues onto the next; each coil is planned and merged under its own plan identifier.

What will not fit is reported rather than forced: weight left unplanned comes back in the run result, and weight left free on a coil is left free. An order placed on two coils becomes two coil order plans, one per coil, each carrying the weight that coil took.

FR-10

Choose how orders are laid out on the coil

Each coil in a run names the strategy its merged plan is built with: MergeOrders or BalanceToPiece. Omitted, it is MergeOrders, which is what the merge has always done.

The two strategies produce different plans from identical input, which is the point — see section 7. Both go through the same save, journal and undo path, so choosing one costs nothing downstream.

FR-11

Advise how much of an order to plan

Given a coil, what is free on it, an order and the route, answer how much to plan so that everything produced can be shipped — and what that weight produces: the spools it is wound on, the finished coils cut from it, whatever is left over, and what to do about that.

It advises rather than decides. Supply a weight and that weight is evaluated instead of one being chosen, with the weight that WOULD have been advised returned beside it so an override can be recorded against it. Nothing is written.

05Business rules

The rules the generated rows must satisfy. Where a rule exists to make a physical constraint hold, that constraint is named.

BR-1

A route collapses into at most three operations

Draws and flattens before the anneal become one flatten; the anneal stands alone; flattens and edges after it become one more. Sequence nos run 0, 10, 20.

A group takes its input side from its first step and its output side from its last, which is what makes the fold lossless.

BR-2

Flat line assignment follows the anneal

The anneal runs at the furnace and carries no machine. A route with no anneal runs entirely on FL3. Otherwise operations before the anneal are FL1 and those after it FL2.

BR-3

Each operation's input is the previous output

The first operation receives the coil; every later one receives what the operation before it produced. That single rule keeps a route consistent and is what a future edit will use to recalculate everything downstream of a change.

BR-4

Two orders may share an operation only if all merge rules hold

Same operation, same output, same next operation. A new condition is a new rule class and nothing else changes.

BR-5

A coil can only be divided at a flatten

The furnace output cannot be split, so a division owed at the anneal waits for the next flatten. Any order with no operation there is given an extra as-is flatten so it can still take a coil of its own.

BR-6

Every order must end with its own output coil

A coil still carrying more than one order at its last flatten divides there even when the operations match perfectly.

BR-5 and BR-6 are the only division rules coded. The four split points the analysis lists all follow from them; none is written as a case.

BR-7

A new coil no is issued only at a division

Everywhere else the coil no carries through, including across the anneal. There is one routing row per sequence no per coil; the per output detail is on the flat line rows.

BR-8

Weight enters as the coil weight and divides with the coil

Each output then carries the weight of the orders travelling on it. Nothing is lost per operation, so weight off equals weight on. Required in weight is a different question — what the orders on the row actually need — and stays the sum of their planned weights.

BR-9

Rows hang in a plan tree

A per order route is a chain, so its levels run from one, each hanging from the one before. A division branches it: the operation the coil divided at is the parent, and the operations that follow on each new coil are siblings under it. Levels are unique across a plan.

BR-10

A routing row's remaining operations exclude its own

The column names what is still to be done once the operation is finished, so it always begins with the next operation and is empty on the last. The order level row is different — it names the order's whole planned route.

For FAF the three routing rows read AF, F, empty — while the order's own row reads FAF.

BR-11

The manufacturing order no is zero until export

It is assigned when a plan is exported, so every row a plan generates carries zero rather than nothing — including the home order no on the flat line rows.

BR-12

Back to stock sits on the row that produced the coil

A stock order ending at a flatten carries the flag on its flat line row; one ending at the anneal carries it on the routing row. Where the merge creates an as-is flatten, the flag moves off the anneal onto the new flat line row.

BR-13

Unused mill and slitter measures are written, not left unknown

A quantity or flag that flat wire does not use is zero or false. Row references — coil, core, plastic, arbor, output item, machine and setup identifiers — stay unset, because a zero there would read as a reference to a row that does not exist.

BR-14

A finished coil is never planned above the order's maximum

Where a weight will not divide into equal coils inside the customer's range, the heaviest legal coils are cut and the remainder is reported. It is never rounded up into the next coil.

The client's ruling: cut at the maximum and keep the remainder, because shipping the overage would force a WIP reject. Over shipping the ORDER within its tolerance is a different matter and is allowed — see BR-15.

BR-15

An order may be over planned within its shipping tolerance

The ceiling is (order_tot_qty_tol_plus / 100 + 1) × current_order_total_qty, less what is already planned and shipped. Raising a final spool rather than leaving an unshippable tail is the intended use of that headroom.

The same formula the edit order details query uses, computed in the service rather than in SQL so it has one home and can be tested without a database. A test pins it to the query's own numbers.

BR-16

Welding is rod to rod, before the first flat line

A tail can only be carried forward while it is still rod. Once flattened, material cannot be welded — the mill has no capability for it — so a short spool or material left at FL2 is a WIP reject or a concession, never a weld.

The order permits welding or does not; a step of the route may forbid it. A step that says nothing leaves the order's answer standing, which is why the flag on a step is nullable: null is no opinion, not no.

BR-17

Coils ship two to a skid, and an even count is preferred

An odd number of finished coils ships a skid with one coil on it. That is allowed — the client does it when it completes an order — but it is reported, because they would rather plan even.

A preference, never a constraint: shipped weight is never traded for it.

06Output solution

How much of an order to put on a coil, and what that weight makes. Pure arithmetic — it reads nothing and writes nothing, so the same code answers the first plan and every later correction.

Allocating by weight alone strands material. The worked example the analysis opens with is a 4,000 lb rod that winds two 1,800 lb spools and a 400 lb tail: with an 800 lb minimum coil the tail makes nothing, so 4,000 lb is consumed and 3,600 lb ships. The fix is a planning decision, not a mill one — the same rods, welds and spools with 400 lb less allocated leave 12 lb at risk instead of 900.

The shape of a plan that strands nothing

For one order on one coil, the planned weight is a whole number of finished coils, each inside the customer's range, nested onto spools that the flat line can actually wind:

QuantityConstraintWhose
Bbundle weight, between the order's minimum and maximum, never above itthe order's
mbundle count — a weight divides evenly exactly when floor(W / Bmin) ≥ ceil(W / Bmax)derived
kbundles per spool — as many whole coils as fit under the spool's maximumthe spool's
Wweight to plan — at most what is free on the coil, and at most the order's headroomthe answer

Among the candidates the solver ships the most weight; then, at equal weight, the fewest and so heaviest coils; then an even count. Where no equal split exists it still cuts the heaviest legal coils and reports the remainder rather than forcing a coil the customer will not take.

The objective inverts once the order is full. An order planned up to its ship ceiling wants the SMALLEST legal increment, not the largest — one spool's worth where the route winds spools, otherwise one coil, both at the lightest the customer accepts. The reason is returned with it, so the screen can explain the small number rather than look broken.

Only the spool band is read; everything else arrives on the request. That is deliberate — the planner is looking at an order on a screen, and an answer they can argue with is worth more than one that needed a round trip. Where the route reaches a spool and no band can be found, the call FAILS rather than answering: with no band the route would look like one with no spool stage, and the answer would be wrong rather than missing.

07Final plan strategies

Two ways of laying several orders out on one coil, both specified, the planner choosing per coil. The client's own material contains both answers, so neither is assumed.

SourceSays
merging-logic-sample-data.jsonOne flat line row at sequence 0 carrying 123456;123457 — two orders on one spool. Verified against the dev database.
The client's review comment"I do not believe that we want to have multiple orders on a spool. The process would become very complex and the room for error at coil generation and skidding would be substantial."

MergeOrders — the default

Orders travelling on one coil share operations, and the coil divides where they diverge. One routing row per sequence per coil carrying every order on it; the extra as-is flatten where one finishes at the anneal; coil nos issued at divisions. This is sections 5 and 9 as originally specified, unchanged.

BalanceToPiece — the client's ruling

An order boundary is a hard break: the rod is checked out and back in, and a new empty spool starts. So no spool spans two orders. Instead of grouping orders, each flatten peels one order's piece off and carries the balance forward as its own piece, which is flattened again for the next order.

RowOrderWeightNextLevel / parent
first flatten · pieceO11,000A2 / 1
first flatten · balanceO2, O32,000F3 / 1
second flatten · pieceO21,200A4 / 3
second flatten · balanceO3800F5 / 3

At most two rows per split — a piece and a balance — which makes it a cascade rather than an n-way division. The tree it needs already exists: LevelId and ParentLevelId chain each balance to the flatten it came from.

Flat line processing has no next-operation column, and needs none. That a balance is flattened again is expressed structurally: the coil no the balance leaves on is the incoming coil no of a routing whose operation letter is F. The topology is in the data already, so nothing was added to carry it.

What each costs

Both go through the same save, journal and undo path. Choosing one changes what is planned, not what happens to the plan afterwards.

08Coil numbering

Every division issues coil nos through the existing coil alpha generation, so flat wire numbers coils the way the rest of planning does. The shape of a coil no constrains how deep a plan can divide.

A coil no is a six character root plus up to three alphas, in nine characters total — JP6125, JM8603B, JZ5531BB, JM8804UCA. A division asks for children of the coil being divided, so a cascade nests:

DividesProducesWhy
FW7001FW7001A, FW7001BChildren of the rod
FW7001BFW7001BA, FW7001BBChildren of the balance
FW7001BBFW7001BBA, FW7001BBBThree alphas — the limit
FW7001BBBFW7001C, FW7001DNo room for a fourth, so generation returns to seven characters using the next free letter

Material going back to stock is numbered differently. It becomes a stock coil in its own right rather than a piece of the coil it came off, so its coil no is asked for as a warehouse alpha — generated from the rod rather than from its parent. A division that produces one of each therefore makes two calls; one that produces two of a kind makes one.

Under MergeOrders the back to stock output is the invented as-is flatten's coil, which the division assigns. Under BalanceToPiece it is the order's own last output. Either way the flag and the warehouse alpha land on the same row.

09Scenarios

The merge cases the analysis works through, each one a test. SC-1 to SC-5 are driven directly from merging-logic-sample-data.json — its temp block goes in, its planning block is the expected result.

SC-1

Identical routes divide at the last flatten

Two orders with identical routes on one coil. Every operation merges, and because the orders match all the way through, the division happens at the last flatten where each takes its own output coil.

123456 · 1000 lbFAF
123457 · 300 lbFAF

3 routing rows, all carrying 123456;123457. 3 flat line rows: one shared at sequence 0 for the full coil, then one per order at sequence 20 on new coils FW10002 and FW10003, carrying 1000 lb and 300 lb.

SC-2

Routes diverging after the first flatten divide there

One order runs the full route; the other finishes at the first flatten. The outputs match but the next operations differ, so the coil divides at the first flatten and only the longer order carries on.

123456 · 1000 lbFAF
123458 · 500 lbF

Two flat line rows at sequence 0 on new coils; the anneal and last flatten carry only the order that still has operations left.

SC-3

A customer order beside an as-is stock order

The remainder of the coil goes back to stock as an as-is order. Its input fields equal its output fields, its gauge band collapses to a single value, and the back to stock flag sits on its flat line row because it ends at a flatten.

123456 · customerFAF
stock · as-isF

Divides at the first flatten. The stock order's flat line row carries BackToStock; the customer order continues alone.

SC-4

An order finishing at the anneal gains an extra flatten

The stock order's last operation is the anneal, and a coil cannot be divided at the furnace. The merge creates an as-is flatten for it at the last flatten's sequence so it can be given a coil of its own — and the back to stock flag moves off the anneal row onto that new flat line row.

123456 · customerFAF
45232 · stockFA

The stock order's operations become FAF in the planning tables though its draft said FA. The extra flatten exists only in the merged plan.

SC-5

Different outputs on the first flatten divide immediately

Both orders run the full route, but the first flatten produces a different gauge for each. The outputs differ, so the coil divides at once and each order is walked on separately from there.

123456 → 0.1100 H18FAF
123459 → 0.0800 H18FAF

The shared first operation takes the minimum gauge of the two and the temper of the order needing further processing. After the division each branch carries only its own order — and only its own weight.

SC-6

Planning after a root operation

The coil already carries an operation planned on the whole coil, at sequence 0 and level 1 under a coil order plan with no order no.

An order planned afterwards runs sequences 10, 20, 30 at levels 2, 3, 4, its first operation hanging from the root. The merge copies the root row through and appends every merged order to its OrdersInput.

SC-7

Undo after a save, then a new save

A plan is saved twice, undone once, then saved again.

Undo restores the first snapshot through the same path a save takes. The new save prunes the forward branch, so the undone action is no longer reachable by redo.

SC-8

A second order added to a coil already planned

One order is already saved on the coil; a second is planned and saved.

The second joins the plan identifier already on the coil, takes the next position among the orders, and its save replaces only its own rows — the first order's rows are untouched.

SC-9

Three orders on one rod, laid out as a cascade

A 3,000 lb rod under BalanceToPiece: order one needs 1,000 lb, and two more share the rest. Each flatten peels one order off and hands the balance on.

123456 · 1000 lbFAF
123457 · 1200 lbFAF
123458 · 800 lbFAF

Nine routing rows, none naming more than one order. Each order's chain starts one operation later than the one before, because it begins with the flatten of the previous balance. Coil nos FW7001A and FW7001B at the first split, then FW7001BA and FW7001BB at the second. Weight enters at 3,000 and divides: the second flatten receives 2,000, the third 800.

SC-10

A cascade deep enough to run out of coil no

Five orders on one rod under BalanceToPiece, so the coil divides four times.

The fourth division has no room for a tenth character, so generation carries on from the letter after the first alpha and strips the rest — the children of FW7005BBB are FW7005C and FW7005D. This is the one case where a piece is not a descendant of the coil it came off, and the generator decides it, not the planner.

SC-11

A stock order finishing at the anneal, under each strategy

A customer order runs the full route beside a stock order that finishes at the anneal, and the stock order's material goes back to stock.

Under MergeOrders the merge invents an as-is flatten to carry the flag, and that row's coil is a warehouse alpha. Under BalanceToPiece no as-is flatten is invented — the order's own last output carries the flag, on a warehouse alpha of its own. Both produce exactly one back to stock row.

SC-12

A whole rod that strands nothing

A 4,400 lb rod against an order taking 800–900 lb coils, with plenty of order left to plan.

5 coils of 880 lb, no tail. On a 3,500 lb spool that is three coils to a spool: two spools, the second closing at 1,760. The count is odd, so a skid ships with one coil on it and OddBundleCountLeavesAPartSkid says so.

SC-13

A weight with no equal split

2,000 lb against an order taking 750–850 lb coils, on a route with no anneal and so no spool stage.

ceil(2000/850) = 3 exceeds floor(2000/750) = 2, so no equal split exists. Two coils of 850 are cut and 300 lb is reported rather than forced into a 666 lb coil that cannot ship. Given 250 lb more headroom the same order instead ships three coils of 750 and no tail — which is why the ship allowance is part of the solve rather than a check afterwards.

SC-14

A tail too short to ship

400 lb left on a rod, against an order whose lightest coil is 750 lb.

Where the rod cannot be welded: no output at all, and NoOutputPossibleFromRemainingWeight says so. Where it can: 400 lb carried forward, another rod required, and the planner told that 350 lb more completes a coil and 1,300 lb more completes a spool. On a route with no spool stage the spool figure stays at zero rather than quoting a target the route never reaches.

SC-15

An order with no room left

The order is planned right up to its ship ceiling and the planner asks for more.

The smallest legal increment is advised, not the largest — one spool's worth where the route winds spools, otherwise one coil, both at the customer's minimum — with OrderHeadroomExhausted so the screen can explain it. A larger weight typed by the planner is still evaluated as typed.

SC-16

An order too heavy for the coil it starts on

Two coils and two orders in one run, where the first order's weight exceeds the first coil.

The first coil takes what it can hold and the rest of that order continues onto the second, so the order becomes two coil order plans. Each coil is merged under its own plan identifier. Weight that fits nowhere is reported as unplanned; weight left free on a coil is left free.

The two generate requests are named that way deliberately — they are reads and should not open a transaction. Everything that writes must not contain it, which is why the one-call endpoint is a …Command: a run that saved some orders and then failed would otherwise leave the coil half planned. The solution is a …Query for the same reason in reverse — it works out an answer and writes nothing.

Planning a run

GenerateAndSaveFlatWirePlan takes a list of coils and a list of orders rather than one of each. Each coil carries its own coil details, its SMP, its plan identifier and the strategy its merged plan is built with; the orders are weighed out across the coils in order.

14Known gaps

Open before this can be trusted in production. The planning run and the solution both execute against the dev database; nothing has been exercised by a planner.

Decision

Re-planning the same order on the same coil adds a second slice

Posting the same run twice appends the same orders again rather than replacing them, so a coil tested repeatedly accumulates orders and every run does more work than the last — the whole of the performance problem in section 12. A planner who clicks twice gets two slices of the same order. Whether that should replace or append is a product decision, not a defect to be fixed blind.

Watch

A half-saved merged plan was seen once

A saved plan on dev once left 3 flat line rows with no routings, order references or remaining operations, with identity counters ahead by exactly 3, 2 and 2 — inserted and rolled back while the flat line rows committed. The insert path has since been rewritten to add all four tables and commit them in a single save, which should make the partial state impossible, but the original failure was never reproduced and so the fix is unproven. Worth watching rather than closing.

Open

Flat line rows are deleted without being archived

Every sibling table writes to its history table before deleting. The two flat line history tables exist but have no entity behind them, so removing a plan loses those rows with no audit trail.

Open

The stock order is not created in united_db

CreateFlatWireStockOrder mints the number and clears the recycled number's stale rows, but creating the sales order itself is marked TODO(DBA) — the column lists of the orders, order_parts and releases tables are not in the database repository.

Awaiting BA

Coil type has no single-letter mapping

Flat wire holds the coil type as Rod or Wire, but the routing column is char(1) and no mapping is stated anywhere. Left unset rather than invented; the flat line rows carry the type in full.

Awaiting BA

A second anneal per route

The three-operation collapse assumes at most one anneal. If a second is ever legitimate, the collapser generalises to alternating groups.

Stub

SMP routes and flat line machines

The SMP arrives from a stub until the external procedure exists — one dependency injection line to swap, with nothing above it changing. Only FL1 has a machine decided; FL2 and FL3 have none.

Planned

Editing operations

Adding, editing and removing a flatten or an anneal — including inserting an anneal into a flatten, which splits it in two. Each is a pure document transform, so every one is undoable through the journal with no work per edit type. Re-running line assignment after each structural edit is what promotes an FL3-only route to FL1 / Furnace / FL2 and collapses it back.

Awaiting client

The two client sources disagree about spools

The sample data supplied for the merge shows two orders on one spool; the review comment on How rods, orders, spools and coils fit together forbids it. Both are built and the planner chooses, so nothing is blocked — but the client should know their two documents disagree, and which one their planners will actually pick.

Awaiting client

Whether a skid weight caps two coils

order_max_skid_wgt exists and the slitter already folds it into its own ceiling. Whether it should also cap two flat wire coils on a skid is unanswered, so it is not applied. The skid policy is a single class and the solver already consults it, so the answer is a one class change.

Awaiting client

A maximum number of welds per coil

ASTM sets no limit, but the client notes a customer could have a specification for it and that nothing in quotes or orders captures one. Not built — there is no field to read. The weld policy is where it would go, as one more condition.

Provisional

The spool weights are fixture data

Every row in the spool table is annotated as a provisional fixture, and the numbers drive how many coils fit on a spool. They should be confirmed before anyone reads a spool count as a commitment.

Planned

Re-solving from what the mill actually produced

A spool planned at 1,800 lb and produced at 1,750 still cuts coils inside their range, so the band absorbs most drift. Only when a value falls outside its band do the spools after it need recomputing. Because the solver is a pure function of remaining weight, the same code serves the first plan and the correction — and rewriting a plan is what a save already does, so a correction is undoable like any other edit.

Planned

Allocating a run through the solver

The weight allocator still divides an order across coils by raw weight. Putting the solution in front of it — so a coil takes a shippable weight rather than whatever is left — is the point of the exercise, and it changes generated plans, so it is deliberately left until the arithmetic has been agreed.

Open

An index on the plan links

RoutingsLevelIdMaps holds 85,000 rows with only a primary key on its own identifier, so clearing a plan's links scans the table — about 117 ms of every save. An index on the plan identifier would remove it.
