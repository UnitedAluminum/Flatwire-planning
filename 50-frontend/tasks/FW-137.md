## 2. ⛔ The dependency that is not in the repository

**`@angular/service-worker` is absent from `package.json`** — measured in
`Second-Branch/ual-angular` on 27 Aug 2026, re-measured 28 Aug. Neither the app nor
any of the **30** library projects uses it, so there is **no PWA infrastructure to extend**: no
`ngsw-config.json`, no `ServiceWorkerModule` registration, no manifest. *(`angular.json` holds **31**
entries — 30 libraries and one application, `united-aluminum`. This read "31 library projects" until
28 Aug 2026; the count includes the host app, which is the one project a service worker would actually
be registered by, so the error pointed away from the file that owns the decision.)*

This is the same class of item as `G10`'s MessagePack package — **a provisioning decision, not a build
step** (`F-10`) — but it is larger, because a service worker changes how the whole application is
cached and served, not just one library.

**Three questions someone must answer before the 8 h is spendable:**

| | Question |
|---|---|
| 1 | Is a **service worker acceptable on this deployment** at all? It caches app shell assets globally, and the host app is served under `baseHref: /UA-APPS/` alongside other UAL modules |
| 2 | If not, is the **requirement satisfiable without one**? `FR-119` asks for cached state across a *short* drop — in-memory state plus `localStorage` would survive a dropped socket, though **not a page reload** |
| 3 | Who owns the **app-level** change? A service worker is registered by the host application, not by a lazy library, so this reaches outside `flat-wire` |

⚠ **Option 2 is worth taking seriously.** The requirement is *"an operator screen does not go blank
during a short network drop"* (`[SIG §4.3]`, `FR-119`). A dropped **WebSocket** does not reload the
page, so the cached-state half is satisfiable inside the library with no new dependency. **What needs a
service worker is surviving a refresh or an asset fetch failure** — which is a different, larger
promise than the AC makes.

**Recommendation:** split the story on that line. Build the banner and the in-memory/`localStorage`
last-known-state half now, and treat the service worker as a separate app-level decision. **Record which
half shipped** — otherwise the AC reads as met when only part of it is.

## 3. Build order

### Step 1 — the reconnect banner *(buildable today, no new dependency)*

- Driven by `FW-135`'s connection state, not by a timer or a failed HTTP call.
- **Replaces a blank screen**; the cached last-known state stays visible **behind** it.
- **Clears automatically on successful re-join** — and re-join means the group is rejoined, not merely that the socket is up (`[SIG §5.1]`).
- Uses `FW-134`'s `alert-banner` if its raise/clear shape fits; otherwise a sibling that follows the same visual language. ⚠ **Do not invent a third banner idiom.**

### Step 2 — last-known state *(buildable today)*

Cache the **pass schedule** and the **active-run snapshot** — the two things `FR-119` names. Keep them
in `run-state.service` / `line-context.service` (`FW-132`) and mirror to `localStorage` if survival
across a refresh is wanted without a service worker.

⚠ **Render the cached values as cached.** An operator must not read a frozen footage counter as live —
this is the same failure mode as substituting a fresher tick for a latched weight.

### Step 3 — the service worker *(blocked)*

Only after §2's questions are answered. If it proceeds: `@angular/service-worker` added,
`ngsw-config.json` scoped to the flat-wire assets, `ServiceWorkerModule.register(...)` in the **host**
app, and a cache strategy that does **not** serve a stale `config.json` — which would silently pin
`useMockData` and the API base URL to whatever was cached.

⚠ **That last point is the real hazard.** `environment.js` writes `src/assets/config.json` and the app
reads it at boot through `provideAppInitializer`. **A service worker caching that file can boot the
app against the wrong environment**, and the symptom would look like a backend fault.
