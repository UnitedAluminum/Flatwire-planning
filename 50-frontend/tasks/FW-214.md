### 1.2 ⛔ Three runtime defects, and no planning document records any of them

**(1) AC 9's lock-out probe is binary; the service has three answers.**
`FW-218`'s own measurement is *simulation **on** → `GET /sim/state` returns **401***, and with a token
carrying no `Engineer` / `Admin` claim it returns **403** — `FW-145` is unbuilt, so no role claim is
issued and `RequireAuthorization(Roles = "Engineer,Admin")` denies every caller. A console built to
*"404 → lock out, otherwise open"* therefore shows **the lock-out panel through the whole acceptance
run**, and reads to the room as a broken server rather than as an unbuilt role claim. `P-291` fixes
the shape.

**(2) Nothing configures a base URL, and the built code names this exact failure.**
`Program.cs:502`–`:505` calls `UsePathBase`, so the deployed surface is **`/API.FlatWire/sim/**`** and
**`/API.FlatWire/hubs/flatwire`**, while `Constants.Routes.Hub` is the bare `/hubs/flatwire`. The
comment at `Program.cs:175` calls the confusion *"the mistake that works on localhost and fails on the
panel"* — and a **desktop** client, pointed by hand at a deployed server, is where it bites hardest.
`P-292`.

**(3) The hub authenticates today; only `/sim` denies — and that is why (1) matters.**
`FW-145 §3.5` / `P-77`'s query-string token lift was pulled forward into `FW-080` and is in the built
`Program.cs:152`–`:187`; `FlatWireHub` carries a **bare `[Authorize]`** (`FlatWireHub.cs:61`), not a
role requirement. So an authenticated engineer's console **can connect to the hub and show live
telemetry** while every `/sim` control denies. A lock-out triggered by a 401 would suppress the one
surface that actually works.

## 2. The three rules that shape the code

### 2.0 The stream stays `FE`, and so does the folder

**`FE` is the user-facing surface, not "Angular"** (`D-33`). The card keeps `stream: FE` and the file
stays in `50-frontend/tasks/`, which is what keeps
[`tools/check_docs.py`](../../tools/check_docs.py)'s folder↔stream rule satisfied **with no tooling
change** — `FE` is an allowed stream for this folder, so no `FOLDER_STREAM_EXCEPTIONS` entry is
needed and none should be added.

### 2.1 It is not a dashboard, and since `D-33` that is structural

`[SIM §9.1]`: absent from the fifteen-dashboard inventory, from the navigation map and from the
topbar *More Options* tiles, and carrying **no `DB##` number** deliberately. It used to satisfy those
four rules by convention while shipping in the same bundle as the fifteen; it now satisfies them by
construction. **Do not add it to any operator-facing list**, and do not take a dependency on
`ual-angular` for any reason.

### 2.2 A thin client — the console adds no interface of its own

`[SIM §2.1]`, unchanged by `D-33`. The models stay in `FlatWire.API`. **Do not widen `SimLineState`
to fill the panels**, do not poll `GET /sim/state` after the first read — a console that polled it
would be *a second telemetry path competing with the hub*, which the built surface's own remark warns
against — and do not hand-write a DTO that `HubContracts.cs` already declares.

### 2.3 Greyed is a state, not an absence

Every control the mockup draws is present in the built UI. **Greying is data**: one capability map,
read at startup, driving `Enabled` and a tooltip that names the reason. `P-294`. This is what makes
*"each returns as configuration"* true rather than aspirational — when `FW-215` lands, the map
changes and the layout does not.

## 3. Build order

1. **Scaffold** — `ual-api/Tools/FlatWireSimConsole/`, `net8.0-windows`, `<OutputType>WinExe`, **its
   own `.sln`**, beside `Tools/ConfigureAPI`. It must build and release without `ual-angular` **and**
   without the `FlatWire.API` solution.
2. **Link the contract, do not copy it** — `<Compile Include>` for
   `FlatWire.Domain/Models/RealTime/HubContracts.cs` and `Enums/CanonicalEnums.cs`. ⚠ **Do not
   hand-write DTOs**: `HubContracts.cs`'s own header records that *"names are the contract on both
   ends"*.
3. **Configuration and base URL first** (`P-292`) — one server base URL, one setting. Every REST path
   and the hub URL compose from it. **Ship pointed at nothing**, so a first run must be configured
   rather than silently reaching localhost.
4. **Auth** — acquire a JWT, hold it, supply it to both the REST client and the hub's
   `AccessTokenProvider`.
5. **The startup probe, with three outcomes** (`P-291`) — §3.1.
6. **REST client** — the four `FW-218` endpoints, against the standard `{data, success, errors}`
   envelope.
7. **SignalR client** — WebSockets + `SkipNegotiation`, `WithAutomaticReconnect()`, **line-group
   re-join on reconnect**, and cached last-known state behind *"Reconnecting…"* — **never a blank
   screen** (`FR-119`). JSON protocol only.
8. **The line panel** — one `UserControl`, instantiated three times. Dual state badges (**run status
   and line state are different things**, `[SIM §4.4]`), readouts, target-vs-actual strips, speed
   slider, nudges, the seven fault buttons.
9. **The FL2 variant** — gauge and width strips render *"No live gauge · see Profile"*, **never a flat
   line at target**.
10. **The capability map and the greying rules** (`P-294`), including the whole FL3 panel.
11. **The global bar** — simulation on/off from the probe result, `lbPerFt` and the seed as explicit
    **unset** states (`P-290`), and a control log.
12. **Packaging and the `[DEP]` entry** — released independently, and **installable nowhere near a
    commissioned line** (`G66` is the procedural half).

### 3.1 The startup probe — three outcomes, one lock-out

| Response | Meaning | Console |
|---|---|---|
| **404** | Simulation is **off**; the routes were never mapped (`P-38`) | ⛔ **Lock-out panel and nothing else.** The only lock-out trigger |
| **401 / 403** | The surface exists; this caller may not drive it (`FW-145`) | ⚠ **Open, controls disabled, a banner naming the reason — and connect the hub anyway** |
| **200** | Simulation on, caller authorised | ✅ Open normally; seed the six fields |
| Transport failure | The server is unreachable | ⚠ A retry panel — **not** a lock-out; an unreachable server is not a commissioned line |

⚠ **The server-side 404 remains the actual control** (`[SEC §8.8b]`, `[SIM §9.4]`). This is the client
half of it, and the client half must not over-claim: a console that locked out on 401 would be
*guessing* that simulation is off from a message that says nothing of the kind.

## 4. Decisions this plan makes

> `P-##` is continuous across the backend folder and this one; `P-01`–`P-289` precede this story.

### `P-290` — `lbPerFt` and the seed render as an explicit *unset*, never blank and never zero

Neither value reaches the console. `SimLineState` carries six fields and `[SIM §9.2]` forbids widening
it; `[SIM §8.1]`'s five endpoints carry no configuration read; `HubContracts.cs` declares no such
member. **`[SIM §9.2]` nevertheless requires both displayed**, and `[SIM §5.3]` says `lbPerFt` *"must
not be buried"* because it is *"the single most load-bearing unverified number in this model"*.

So the console shows the label with a literal **`unset — no control-API route (G68)`** rather than a
blank, a dash or a zero. ⛔ **A zero is the wrong answer twice**: it reads as a measured value, and
`Reading` already uses null to mean *not read*.

**This is `G68`**, raised by this plan. **Fallback:** none available client-side — the fix is one
endpoint on `FW-215`, and until then honest absence beats invented presence.

### `P-291` — the startup probe has three outcomes, and only 404 locks out

Per §1.2 (1) and §3.1. **Written as a decision because the binary form looks correct in review and
fails on the day**: `[SIM §9.4]` and the card both describe the probe as *"on 404, show a lock-out
panel"*, which is true and incomplete, and the response the trial will actually see is **401**.

⚠ **`[SIM §9.4]`'s guarantee is unweakened.** The server-side 404 is still the control; this decision
only stops the client from inferring a 404's meaning from a different status code.

### `P-292` — the server base URL is one configured value, and every path composes from it

`UsePathBase` (`Program.cs:502`) means the deployed surface is `/API.FlatWire/sim/**` and
`/API.FlatWire/hubs/flatwire`, while `Constants.Routes.Hub` is `/hubs/flatwire`. The console composes
`{base}/sim/…` and `{base}{Constants.Routes.Hub}` and **hard-codes neither**.

The built code names this failure in terms — *"the mistake that works on localhost and fails on the
panel"* — and it is worse for a desktop tool than for a hosted app, because nothing about the
console's own origin hints at the right prefix. **It ships pointed at nothing**, so a first run is a
configuration step rather than a silent localhost attempt that looks like a dead server.

### `P-293` — steer fields are *commanded*, and neither state chip is seeded from `/sim/state`

Two consequences of two decisions the backend already took, and both are invisible in a UI review.

**(1) `GaugeOffsetIn` / `DriftPerTickIn` are labelled *commanded* and are never plotted on a
target-vs-actual strip.** `P-267`: they are a **running command echo** — the steer seeds the bias and
the commanded drift advances it every tick — not a measurement. A strip fed from them draws a reading
nobody took.

**(2) Both state chips come from the hub.** `SimLineState.Running` is a **lossy bool over four run
states** (`P-274`), so a run-status chip seeded from it shows `Paused` as stopped. Before the first
hub event, both chips read **awaiting hub** rather than guessing.

> ⛔ **Part (2) is WRONG, and the build corrected it — 31 Aug 2026.** `[SIG §5.2]` event 7 is
> `LineStatusEvent { LineId, Status, OrderId, Alpha }`, where `Status` is a `LineState` — and
> **no hub payload carries a run status at all** (`grep RunStatus HubContracts.cs` → 0). So the
> line-state chip does come from the hub and the **run chip cannot**. That is **`G69`**, and
> **`P-301`** records what the chip does instead. ⚠ **Part (1) stands unchanged and was built as
> written.**

### `P-301` — the run chip is labelled at the precision the wire actually carries *(minted by the build)*

`[SIM §9.2]` requires **two chips** — run status and line state, *"per §4.4, two separate chips"* —
and the wire carries **one vocabulary**. The line state arrives on `[SIG §5.2]` event 7. For run
status there is **no source**: no hub payload has the field, and `/sim/state`'s `Running` is a
**bool**, the lossy projection of the simulator's four-state `SimRunState` (`P-274`).

So the chip renders **`Run: running` / `Run: not running`**, seeded from `/sim/state` and refreshed on
demand — **a two-state chip, honestly labelled at two states**. It reads **`Run: unknown`** before any
state has been read.

⛔ **The alternative was a four-state chip fed from the bool**, which is what `P-274` warns against in
terms: it would show **`Paused` as stopped**, and a stopped-looking line that is actually paused is
precisely the `[SIM §4.4]` confusion the two chips exist to prevent.

⚠ **This is `P-290`'s posture applied to a chip rather than a value**: where the wire carries less
than the specification asks for, show what is knowable at the precision it is knowable, and record the
gap — **`G69`** — rather than inventing the rest.

### `P-294` — greying is one capability map, not `Enabled = false` scattered through the panel

One table read at startup: control → enabled? → reason. It drives `Enabled` and the tooltip, and the
FL3 panel is one entry rather than a special case threaded through the `UserControl`.

**This is the smaller option, not the bigger one.** The card's *"grey them, do not delete them — each
returns as configuration"* is otherwise a promise nobody can keep: with the state scattered, lighting
a control up when `FW-215` lands means finding every site. With the map, it is an entry. It also gives
