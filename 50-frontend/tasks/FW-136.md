## 2. What to emit

### 2.1 The fourteen events

| # | Event | Emit as |
|---|---|---|
| 1 | `GaugeReading[]` | **batched, ~10 Hz** — arrays, not scalars |
| 2 | `WidthReading[]` | **batched, ~10 Hz** |
| 3 | `SpeedFPM` | batched / decimated |
| 4 | `PayoffWeight` | batched |
| 5 | `FootageCounter` | batched |
| 6 | `ComponentStatus` | **on change only** |
| 7 | `LineStatus` | on change, immediate |
| 8 | `AlertRaised` | **immediate, unbatched** |
| 9 | `AlertCleared` | **immediate, unbatched** |
| 10 | `PayoffStateChanged` | ⚠ **immediate, unbatched — must never enter the ~100 ms batch** |
| 11 | `SpoolCompletionPromptDue` | immediate · **server-owned, durable** |
| 12 | `SpoolCompletionPromptResolved` | immediate |
| 13 | `OrderAllocationReached` | immediate · **server-owned, durable** |
| 14 | `OrderAllocationResolved` | immediate |

**Plus the six run-event markers** (`[SIG §5.4]`): `WeldJoinEvent` · `DieChangeEvent` · `PauseEvent` ·
`SPCCheckpoint` · `AlertEvent` · `RodCheckoutEvent`.

### 2.2 The cadence is specified — match it

**Batched ~10 Hz** (`[SIG §4.2]` *"fixed cadence ~100 ms / 10 Hz"*). ⚠ **`G9` does not leave the
cadence undefined** — it leaves the *targets* undefined (AGC publish rate at source → `PLC-Q11`,
client count, latency budget → `C8`). So the mock has a rate to match; what it has no basis for is a
pass/fail threshold. `[API §7.2]` requires the stub stream to run **"at the real cadence with real
batch shapes"**, because *"rendering performance is a design constraint, not an afterthought."*

### 2.3 ⚠ Three behaviours the mock must reproduce, not just the happy path

| Behaviour | Why it matters |
|---|---|
| ⛔ **FL2 emits `null` live gauge and width** | FL2 standalone suppresses both channels **forever, by design** (`FR-120`, `[SIG §5.3]`). Without this the FL2 variant is built against data it will never receive |
| **Re-delivery of an outstanding durable prompt on group re-join** | events 11 and 13 are server-owned state; a re-joining client receives them again, and **that is specified, not a fault** (`FR-144`, `TC-173`) |
| **Duplicate delivery of a durable prompt** | raised once per edge, so the client must be idempotent — the mock is where you prove it |

Also emit the **latched** weight on 11 and 13 and keep it fixed, so a consumer substituting a fresher
`PayoffWeight` tick fails visibly rather than subtly.

### 2.4 Simulated reconnect and group re-join

Drive `gauge-trace-chart` live, then simulate: drop → backoff → re-join → **re-deliver the outstanding
prompt**. This is the only place that path is exercised before a live hub exists.

## 3. Build order

1. **Timer-driven emitter** per line group (`FL1Data` / `FL2Data` / `FL3Data`), batching the hot channels at ~100 ms and sending the rare ones immediately.
2. **Implement the same interface as `FW-135`'s real service**, so the DI swap is one provider — the mock is not a separate API surface.
3. **Scenario switches** for the three behaviours in §2.3, reachable without editing code.
4. **Jest:** emitted events land in the ring buffer **with correct types** — the card's own criterion, and the one that catches a missing event outright.

## 6. Handoff

**`FW-133`'s `gauge-trace-chart` is this mock's first consumer, and DB1/DB3 shells are the second.**
Hand on:

1. **The mock emits fourteen events and six markers** — if a screen only handles nine, it was built to the card.
2. **FL2 nulls are correct behaviour.** Do not "fix" a screen that shows no live gauge on FL2.
3. **The durable prompts re-deliver.** Handlers must be idempotent, everywhere, not just on DB3.
