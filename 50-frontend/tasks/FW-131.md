## 2. ⛔ Read this before starting: there is no client-side role source

`[SEC §8]` was corrected on 27 Aug 2026 to split the `G6` residual across the wire. Measured in
`Second-Branch/ual-angular`:

| Looked for | Found |
|---|---|
| a role field on `LoginStatusDetails` | **none** — `userName`, `badgeNo`, `jwtToken`, `moduleId`, `machineType`, no role |
| a role vocabulary in `shared.constants.ts` | **none** |
| a JWT decoder — `atob`, a decode utility, anything | **none anywhere** in `projects/` or `src/` |
| what authorisation *does* exist | per-module **`ACCESS` / `WRITE`** (`UserPermissionModel`, `USER_PERMISSIONS`) — a different shape from six named roles |

**So `FlatWireRoleGuard` has nothing to read.** `F-12` tables three options — decode the JWT the
client already holds (recommended), extend the login response, or map onto `ACCESS`/`WRITE` and lose
`FR-212`'s granularity — and **`[SEC]` owns the choice.**

✅ **What you can build today:** the interceptor verification, the envelope type and the error
mapping. **That is most of the story.** Build the role guard's *shape* against a single constants
class and leave the source injectable.

⚠ **The role matrix's MVP-1 subject is not DB9/DB9A** — those are MVP-2. The live MVP-1 gate is
**`FR-212`**: reverting a roll-gap override on **DB11 Roll Adjust** is Operations-Manager-only, and an
operator may apply one but not undo it.

## 3. Build order

### Step 1 — authentication: nothing to build

**`shared`'s `AuthenticationGuard` is the guard**, and [`FW-N03`](FW-N03.md) already wires it on the
parent route exactly as `planning-routing.module.ts` does:

```typescript
canActivate: [AuthenticationGuard],
```

⛔ **Do not write a `FlatWireAuthGuard`.** `find projects -name "*.guard.ts"` returns exactly two
files, both in `shared` — `authentication.guard.ts` and `login-authentication.guard.ts` — and
**eleven routing modules consume them while no library defines one of its own**. A flat-wire guard
would be the first, wrapping a service that already does the job, and it would owe a spec on day
one: `collectCoverageFrom` globs `*.guard.ts` against a **95 %** gate (`F-08`).

✅ **`F-07` governs the role guard:** class guards in `canActivate: [...]`, not functional guards —
the live pattern in all eleven routing modules. JSDoc on every method is lint-enforced
(`jsdoc/require-jsdoc: error`), as is `inject()` over constructor injection. Read `shared`'s guard
for the session/redirect conventions — `getTokenForMultiUser()`, the `sessionStorage` redirect keys
— and follow them rather than inventing a redirect scheme.

### Step 2 — the interceptors, which are already wired

**Add no interceptors.** The mechanism, measured:

- `SharedModule`'s own `@NgModule.providers` carries **`provideHttpClient(withInterceptorsFromDi())`**, so a module importing it gets its **own `HttpClient`** in that injector;
- `SharedModule.forRoot()` adds the three `HTTP_INTERCEPTORS` — **token**, **correlation-id**, **error** — plus `{provide: ErrorHandler, useClass: GlobalErrorHandler}` into the same injector.

`FW-N03` already imports `SharedModule.forRoot()` in `FlatWireModule`. **That import is the wiring.**

✅ **This story's job here is verification, not construction:** issue a real FlatWire request and
confirm the `Authorization: Bearer …` header is present and a correlation id is attached. **Do not
assume it from this paragraph** — Angular's `withInterceptorsFromDi()` resolves the chain from the
injector that provided `HttpClient`, which is why the arrangement above matters.

### Step 3 — the envelope type

Define the library's own (`F-04`). `shared`'s `HTTPResponse<T>` is `{data?, success?, errorCode?, errorDescription?}` — **no `errors[]`** — and is neither extended nor reused.

```typescript
export interface FlatWireResponse<T> {
  data: T | null;              // null on any non-success
  success: boolean;
  errorCode?: number;          // int — the HTTP status
  errorDescription?: string;   // the [API §1.8] machine code, e.g. BAY_OCCUPIED
  errors?: string[];           // human-readable messages; always an array
  errorContext?: unknown;      // typed routing payload
}
```

Verified on the wire by `FW-138`: **camelCase**, `data · success · errors · errorCode` (`P-06`, `P-56`).

### Step 4 — ⚠ the error-display collision

`shared`'s `ErrorHandlerService` interceptor **pops a modal whenever a response carries
`body.errorDescription`** — and `[API §1.2]` defines that field as *the machine code*. So a FlatWire
error surfaces as a dialog reading **`BAY_OCCUPIED`**, while this story's AC specifies **toast + inline
field errors**.

The interceptor is global and comes from `SharedModule`, so this is a **design decision, not a bug to
route around**. Options, in ascending cost: map codes to operator-readable text before display; suppress
the shared modal for FlatWire responses; or have the backend leave `errorDescription` empty. **Decide it
here and record it — do not ship the raw code to an operator.** → `[API §1.2]`, `[P1A §6.5]`.

### Step 5 — `FlatWireRoleGuard`, as far as it goes

Build the guard and **bind it to one role-constants class**, as `FW-145` does server-side. Leave the
role *source* behind a single injectable so `F-12`'s outcome is a one-file change. Gate `FR-212`'s
revert action, not DB9/DB9A.
