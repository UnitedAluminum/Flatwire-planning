01

Executive summary

Three questions were asked. They are answered here before anything else, because the rest of this document is only the working behind them.

1. What has been established in Angular that should become the reference implementation?

The whole of flat-wire-landing.component — its composition, not its content. Specifically: the shell/wrapper/route triple that puts a screen at #/flat-wire; the flex height budget that fits 1920 × 1080 without scrolling or scaling; the card idiom; the consumed shared controls (lib-nav-rail, lib-trace-panel, lib-chart-canvas); the OnPush + typed-interface + private-builder component shape; content strings resolved through AppConfigService; popups through CommonPopupService; and the corner lib-spool-notification pattern for a non-modal advisory. It is already codified in [UIC], which is unusually good and should be treated as binding.

What must not be inherited is the data shape. Every figure on both screens comes from a private build*() method returning literals. Copy the builders' output types; do not copy the builders.

2. What can be directly reused for the remaining screens?

Immediately and without change: the eleven host integration points (all already wired, including useMockData in both config files and flatWireHubUrl); the routing pattern; the three shared controls; the card, context-bar, collapsible-table and modal markup idioms; SpoolNotificationComponent as the template for every corner advisory; TraceGraphPopupComponent as the template for every dialog; resolveSpoolMilestone as the template for every pure decision function; and the spec harness — declaring (not stubbing) the shared components, with jest-canvas-mock.

Reusable only after generalization: the trace section, the info tables, the payoff bars and the alert rows, which exist as inline markup on the two built screens and are owed as controls by FW-163, FW-134 and FW-133. Each must replace that markup, not sit beside it.

3. What is the recommended plan to build the rest on top of it?

Five phases, sequenced so nothing is built twice. Phase 1 stabilizes the baseline — the API client, the SignalR client, the two state services, and the replacement of DB3's builders by a real view-model mapper. That is roughly 100 h and it is the only work that every later screen depends on. Phase 2 builds the four core operator screens by copying DB3. Phase 3 turns the traces and prompts live. Phase 4 delivers the seven dialogs and the transactional screens. Phase 5 completes line variants, reports and admin.

The plan of record already contains almost all of these stories with correct ids and hours. What it needs is the record fixes and eleven new rows in §15, not a rewrite.

The lever

DependencyInjectionRegistry.cs registers twelve services twice — StubCheckInService … StubWipRejectionService when useMockData is true, the real ones when it is false. The Angular client can therefore be written against live HTTP today, against seeded fixtures, with no database and no PLC. This removes the usual reason to defer the data layer, and it is why Phase 1 below is scheduled first rather than in parallel.

Template composition — the pattern to copy

The height budget is the single most valuable thing on this screen and the easiest to get wrong. [UIC §4.1] holds the full reasoning; the shape is:

  <div class="d-flex align-items-stretch h-100">                         definite height

Three rules inside that carry real consequence, all learned the hard way and all recorded: min-w-0 and min-h-0 did not exist as classes until this screen needed them (every prior use in the repository was a silent no-op, which put a horizontal scrollbar on every resolution); the height chain must continue into the trace panel's host classes or the canvas overflows; and collapsing a section destroys its canvas, which lib-chart-canvas already handles by destroy-before-rebuild.

Real-time, validation, errors, loading, empty — the honest picture

  • Real-time: none. TracePanel.points is seven literals from GAUGE_TRACE_READINGS; isLive is left at its false default so the chart is drawn once. The plumbing for live is already in lib-chart-canvas — isLive switches it to chart.update('none') in place.
  • Validation: none, because there is no input on this screen. The first real validation lands with the dialogs.
  • Errors: nothing screen-level. The shell mounts lib-toast and lib-global-spinner, and ApiGatewayService raises the spinner per call — so the loading and error surfaces exist and are unused.
  • Empty states: none anywhere. This matters most for FL2, which broadcasts null gauge and width by design — the FL2 variant needs an explicit empty state, not a value resting at target.
  • Navigation: none out of the screen. There is no back control and no line switch.
Reference chain, as requested

Active Run → reference layout (§4.1 height budget, card idiom, context bar) → reference component (OnPush, typed public fields, inject(), content-data constructor) → reference child (signal inputs/outputs, as lib-spool-notification) → reference dialog (CommonPopupService + NgbActiveModal + cdkDrag, as TraceGraphPopupComponent) → reference pure logic (free function in a sibling file) → reference spec (declare the shared components, jest-canvas-mock, one describe per public method). Everything except the data path, which is Phase 1's job to author.

Events
Fourteen streaming events plus six run-event trace markers. Gauge and width arrive batched as arrays; FL2 standalone suppresses both. The markers are separate from the alerts — AlertEvent (marker) and AlertRaised (event) both exist and are not the same thing.
Protocol
MessagePack is enabled by default and switchable by config. This is a decision the client must take before writing enum mappers — see §10.
Tags

Open: PLC-Q04 FM2 station names, PLC-Q05 every measure name, G29 no edger tag path exists though edge type is in the push payload, G32/G33 the station and measure segments are ours not the controller's.
Simulation
A full OPC feed simulator, scenario and fault injection, a closed loop that consumes the push payload, and a standalone WinForms console — all done. The frontend can be driven end to end without a PLC.
NFRs
G9/OI-34: AGC sample rate, concurrent client count, latency target and reading retention are all absent. This blocks six stories and is the single most consequential open question for the live-trace design.

Protocol decision — take it before writing the client

The hub enables AddMessagePackProtocol() by default, switchable by the EnableMessagePack config value. Two consequences: @microsoft/signalr-protocol-msgpack is not in package.json (@microsoft/signalr 9.0.6 is), and — recorded in Program.cs — enums cross as strings under MessagePack and as integers under JSON. A client written against one protocol breaks the moment the flag is flipped.

Recommendation: set EnableMessagePack: false for test1 and build the client on JSON now; add the npm package and re-test under MessagePack as a separate, non-blocking story before UAT. Whichever is chosen, write the enum mappers to accept both forms.

Technical debt and risk

Three buckets, by whether the issue propagates into the screens built next. Nothing here is a style preference.

Must fix before using as the baseline

#IssueWhy it propagatesFix
1 No data seam. Seven build*() methods return literals directly into the fields the template binds. Copying DB3 copies the builders. Fifteen screens would each grow their own hardcoded constructor, and every one would need unpicking later. Introduce FlatWireApiService + a per-screen view-model mapper. Keep the ten interfaces exactly as they are — they are the mapper's return types.
2 Manual detectChanges() in four handlers, and mutable objects (table.isExpanded, alert.isAcknowledgeable) mutated in place under OnPush. It works only because nothing is async. Add a stream and it becomes intermittent — the worst possible failure mode to debug on a shop floor. Move screen state to signal()/computed(), as the two child components already do. Then detectChanges() disappears rather than multiplying.
3 SignalR protocol undecided, and enum wire form differs between the two options. Every DTO and every enum mapper is written against one form. Deciding after the client exists means rewriting the mappers. Decide now (§9). Recommend JSON for the build, MessagePack verified before UAT.
4 No loading, error or empty state anywhere, though the spinner and toast are mounted. These are per-screen decisions with a house style. Set it once on DB3 and every screen inherits; leave it and each of fifteen screens invents its own. Define the three states on DB3 as part of the data-seam work. FL2's null gauge and width make the empty state mandatory, not optional.
5 Fixture data in flat-wire.constants.ts — the trace readings, the placeholder percent — and the negative pass-schedule alpha used as the happy path. A constants file is the one place nobody thinks to clean. These will survive the data path and become "real" values. Delete them with the seam; take fixtures from [CMP §5.3]'s seed set only.

Should fix during the next cycle

  • No responsive reflow. Fixed col-4/col-6 only. [UIC §4.1] requires col-md-6→col-12; 99 of 315 templates in the repository already do this.
