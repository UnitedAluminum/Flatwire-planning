## 2. The four details

### 2.1 ⛔ Safe to create, unsafe to call — and the runner blurs that

`FlatWire_Scripts_RunAll.sql` chains `70_`, so a routine deploy **creates** the procedure. That
is correct: `CREATE PROCEDURE` uses deferred name resolution and touches no data.

**Calling it is a different act.** Its `proddb..wip_coil_orders` **DELETE** is not signed off for
a shared environment, and `Q40` is the open question — **delete the reqsum row, or leave an
orphan?**

✅ **`@deleteOrphan = 0` makes it a no-op** if the answer is *"leave it"*, which is why the
procedure could be written before the answer arrived. ⚠ **But the default matters**: verify the
parameter defaults to the safe direction, exactly as `WipCoilOrdersWritten` defaults to `0`.

### 2.2 The release value is a padded name, and NULL would be worse

AC 1: return `CoilNo` to **the station's own name padded to 9** — *"not NULL and not empty,
because a plain UNIQUE index admits only one of each"*.

⚠ **This is the whole trick.** Two stations released to `NULL` collide on the UNIQUE index, as
do two released to `''`. Releasing each to **its own name** guarantees uniqueness by
construction, and the padding is what makes it match the column's fixed width.

⛔ **Do not "tidy" this to `NULL`.** It reads like a placeholder and it is a constraint
satisfier.

### 2.3 Footage > 0 refuses, and that is a data-integrity rule

AC 6: the reversal **refuses when footage > 0**, because a Mode B mid-run removal has a reqsum
recording material **the order genuinely received**. Deleting it would make produced material
vanish.

⚠ **This is the rule most likely to be read as over-caution and relaxed.** It is not: the reqsum
is the order's record of receipt, and the reversal exists for the case where check-in created a
row **and nothing was produced against it**.

**`RodCheckin.WipCoilOrdersWritten` is the other half** (AC 7) — delete only when check-in
created the row. **Two independent guards**, and both are needed: the flag says *we made this
row*, the footage says *nothing was drawn against it*.

### 2.4 Release belongs to run completion, never coil completion

`FW-219` **correctly refused** to bolt the release onto coil completion, which left it owned by
nobody until this story. AC 3 lists the callers: FL1 spool completion, FL2/FL3 run completion,
and checkout modes A and B — **never at coil completion.**

⚠ **A run produces several coils.** Releasing the station on the first coil would free it
mid-run, and `FW-220` would then let another rod claim it while the line is still running.

## 4. Decisions this plan makes

> The `P-##` series belongs to [`Backend/tasks/`](../../Backend/tasks/)
> and is continuous across the repository; `P-01`–`P-195` precede this story.

### `P-196` — creating `70_` in the runner is correct, and calling it needs a second gate

§2.1. The chain creates the procedure and the procedure is inert until called with
`@deleteOrphan = 1`. **The gate belongs on the caller and on the parameter default**, not on the
deployment — otherwise the runner has to learn a per-environment exception, which is exactly the
complexity `10_`'s hand-run status already carries.

⚠ **Record it on the caller too.** A future `FW-174` developer reading only `70_`'s header
should find the `Q40` warning, and `Scripts/README.md` carries it today.

### `P-197` — the two reversal guards are independent and both stay

§2.3. `WipCoilOrdersWritten` answers *"did check-in create this row"*; footage answers *"was
anything produced against it"*. **Either alone permits a wrong delete**, and the footage guard
in particular will look redundant to someone who trusts the flag.
